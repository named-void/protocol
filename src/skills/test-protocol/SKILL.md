# Проверка завершённой UPL-задачи

## Триггер

Точное сообщение, которое после удаления внешних пробелов состоит из `test-protocol UPL-<code>`, запускает этот skill самостоятельно. Предварительный `read-protocol` не требуется. Команда не входит в постановку задачи, не открывает цикл доработки и не разрешает изменения Jira, Git, Wiki или файлов задачи.

Упоминание `test-protocol` внутри прозы, issue key без команды и тематическое совпадение не активируют skill. URL задачи вместо ключа не принимается.

## Bootstrap

Перед первым действием выполни одним shell-вызовом:

```bash
set -eu

TEST_PROTOCOL_SKILL_FILE='<абсолютный путь загруженного test-protocol/SKILL.md>'
TEST_PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
TEST_PROTOCOL_SKILL="$(dirname "$(realpath "$TEST_PROTOCOL_SKILL_FILE")")"
TEST_PROTOCOL_SRC="$(cd "$TEST_PROTOCOL_SKILL/../.." && pwd -P)"
TEST_PROTOCOL_INSTRUCTIONS="$TEST_PROTOCOL_SRC/instructions"
test -r "$TEST_PROTOCOL_INSTRUCTIONS/environment.md"
test -r "$TEST_PROTOCOL_SRC/lib/skills_config.py"
test -r "$TEST_PROTOCOL_SRC/skills/protocol/scripts/resolve_issue.py"
printf 'TEST_PROTOCOL_SKILL=%s\nTEST_PROTOCOL_SRC=%s\n' "$TEST_PROTOCOL_SKILL" "$TEST_PROTOCOL_SRC"
cat "$TEST_PROTOCOL_INSTRUCTIONS/environment.md"

TEST_PROTOCOL_AGENT_INSTRUCTIONS="$TEST_PROTOCOL_INSTRUCTIONS/agent-$TEST_PROTOCOL_AGENT.md"
test ! -e "$TEST_PROTOCOL_AGENT_INSTRUCTIONS" || cat "$TEST_PROTOCOL_AGENT_INSTRUCTIONS"
```

Сохрани абсолютные `TEST_PROTOCOL_SKILL` и `TEST_PROTOCOL_SRC` как константы контекста сессии. Отсутствующий справочник исполнителя не блокирует маршрут. Перед использованием project-specific окружения прочитай `<UPL_ROOT>/environment.md`.

## Локальные входы

1. Извлеки `UPL-<code>` из точного сообщения и передай его в `python3 "$TEST_PROTOCOL_SRC/skills/protocol/scripts/resolve_issue.py"`; сохрани нормализованный `KEY` и `project_roots`. Resolver используется только для локальной проверки ключа и карты проекта, Jira issue не читай.
2. Получи `DATA_ROOT` командой `python3 "$TEST_PROTOCOL_SRC/lib/skills_config.py" data-root`.
3. Проверь ровно один `<DATA_ROOT>/tasks/<KEY>/state.md`. Продолжай только при `status: completed`, заполненных `candidate` и `checked_candidate`, принятом результате и обязательных evidence.
4. Прочитай задачу, scope, требования, критерии приёмки и источники из `state.md`; затем прочитай только нужные перечисленные в нём локальные snapshots, `inputs`, `plan.md` или notes. История итераций не является самостоятельным источником требований.
5. Если для методного или ролевого контракта state ссылается на общую документацию, используй локальный snapshot, а при его отсутствии — только указанную проектной картой или state страницу через read-only `adapter-wiki`. Перед вызовом адаптера прочитай его `SKILL.md` из сохранённого `AGENT_SKILLS_DIR`. `adapter-issues` и `adapter-vcs` в этом маршруте не вызывай.

Если state отсутствует, найден неоднозначный кандидат, status не `completed`, candidate не проверен или evidence недостаточно, покажи конкретный блокер и остановись. Не выполняй Branch-Sync, не создавай worktree, новый цикл или артефакты и ничего не меняй.

## Построение полной схемы

Составь множество методов из всех уникальных HTTP-пар `[METHOD] /path`, явно затронутых в scope, требованиях или критериях приёмки конкретного `state.md`. Не добавляй методы по Jira status, MR, изменённому diff или предположению о соседнем API.

Для каждого метода собери объединение ролей, связанных именно с этим методом в требованиях задачи или общей документации. Включай роли, для которых реализация в этой задаче не менялась. Общий список ролей без связи с конкретным методом ячейку не создаёт. Не выводи роль из догадки или только из найденного пользователя; если документация задаёт группу ролей, используй раскрытие этой группы только по самой документации.

Требования задачи имеют приоритет для её метода и ожидаемого поведения; общая документация дополняет отсутствующие роли или контракт. Конфликт источников, неизвестный ожидаемый исход, отсутствие метода или роли в источниках блокируют выполнение до разрешения конфликта.

До первого запроса к стенду выдай пользователю полную схему: отдельный пункт для каждой пары «метод × роль». Каждый пункт содержит:

- `[METHOD] /path` и роль;
- источник требования и координату общей документации, если она использована;
- ожидаемый исход доступа и точный HTTP-контракт этой ячейки;
- безопасный запрос с параметрами, телом и заголовками, которые нужны для проверки;
- состояние разрешения `user_id` из dev БД без публикации полного идентификатора.

Не объединяй роли в один пункт и не показывай только изменённые роли. Если хотя бы одна ячейка не имеет полного ожидаемого исхода или входа, выдай всю схему с блокером и не запускай неполную проверку.

## Авторизация и вызов стенда

Для каждой ячейки UPL read-only найди `user_id` нужной роли в dev БД. Не используй ID из примера, локальной БД или Jira. Чтение dev БД выполняй read-only; отсутствие доступа или неоднозначное соответствие пользователя роли блокирует все вызовы до получения полной матрицы.

Для каждого пользователя или роли получи отдельную cookie-сессию запросом `POST https://develop.getblogger.ru/auth/dev/login` с телом:

```json
{
  "user_id": "<user_id из dev БД>",
  "auth_type": "cookie"
}
```

Поле `role` не передавай: роль определяется авторизацией по пользователю из dev БД. После login вызови соответствующий метод с этой cookie-сессией. Не подменяй результат dev-авторизации ручным `X-USER-ROLE` или другим ролевым заголовком; передавай только предусмотренные контрактом метода параметры и контуры.

Успешный dev login сам по себе не подтверждает доступ. Для каждой ячейки сравни фактический статус, тело и наблюдаемый результат с ожидаемым контрактом именно этой роли и метода. Зафиксируй результат рядом с пунктом схемы: `ожидалось`, `получено`, `итог`, безопасная координата запроса и доступное доказательство. Cookie, токены и секреты не выводи и не сохраняй в `state.md`, evidence, логах или комментариях QA.

Удалённые запросы, которые создают, изменяют или удаляют данные, не выполняй. Для такой ячейки укажи блокер и проверь её только на локальной инфраструктуре либо по явно заданному проектным профилем безопасному сценарию. Запрос dev login является единственным служебным шагом получения удалённой сессии; остальные удалённые запросы остаются read-only.

## Итог

Покажи полную матрицу без сокращения ролей: по одному результату на каждый метод и каждую роль. Отдельно перечисли пропущенные, заблокированные и не выполненные ячейки с причиной. Не объявляй проверку полной или успешной, если хотя бы одна обязательная ячейка не выполнена либо её ожидаемый контракт не подтверждён источником.
