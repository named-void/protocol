# Проверка завершённой UPL-задачи

## Триггер

Точное сообщение, которое после удаления внешних пробелов состоит из `test-protocol UPL-<code>`, запускает этот skill самостоятельно. Предварительный `read-protocol` не требуется. Команда не входит в постановку задачи, не открывает цикл доработки и не разрешает изменения Jira, Git, Wiki, кода или `state.md`; локальные manifests сценариев можно подготовить в `<TASK_DIR>/test-protocol/`.

Упоминание `test-protocol` внутри прозы, issue key без команды и тематическое совпадение не активируют skill. URL задачи вместо ключа не принимается.

## Bootstrap

Перед первым действием выполни одним shell-вызовом:

```bash
set -eu

TEST_PROTOCOL_SKILL_FILE='<абсолютный путь загруженного test-protocol/SKILL.md>'
TEST_PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
TEST_PROTOCOL_SKILL="$(dirname "$(realpath "$TEST_PROTOCOL_SKILL_FILE")")"
TEST_PROTOCOL_SRC="$(cd "$TEST_PROTOCOL_SKILL/../.." && pwd -P)"
TEST_PROTOCOL_INSTRUCTIONS="$TEST_PROTOCOL_SRC/instructions"
test -r "$TEST_PROTOCOL_INSTRUCTIONS/environment.md"
test -r "$TEST_PROTOCOL_SRC/lib/skills_config.py"
test -r "$TEST_PROTOCOL_SRC/skills/protocol/scripts/resolve_issue.py"
test -r "$TEST_PROTOCOL_SRC/../projects/upl/scripts/test_protocol_auth.py"
test -r "$TEST_PROTOCOL_SRC/../projects/upl/scripts/test_protocol_methods.py"
printf 'TEST_PROTOCOL_SKILL=%s\nTEST_PROTOCOL_SRC=%s\n' "$TEST_PROTOCOL_SKILL" "$TEST_PROTOCOL_SRC"
cat "$TEST_PROTOCOL_INSTRUCTIONS/environment.md"

TEST_PROTOCOL_AGENT_INSTRUCTIONS="$TEST_PROTOCOL_INSTRUCTIONS/agent-$TEST_PROTOCOL_AGENT.md"
test ! -e "$TEST_PROTOCOL_AGENT_INSTRUCTIONS" || cat "$TEST_PROTOCOL_AGENT_INSTRUCTIONS"
```

Сохрани абсолютные `TEST_PROTOCOL_SKILL` и `TEST_PROTOCOL_SRC` как константы контекста сессии. Отсутствующий справочник исполнителя не блокирует маршрут. Перед использованием project-specific окружения прочитай `<UPL_ROOT>/environment.md`.

## Локальные входы

1. Извлеки `UPL-<code>` из точного сообщения и передай его в `python3 "$TEST_PROTOCOL_SRC/skills/protocol/scripts/resolve_issue.py"`; сохрани нормализованный `KEY` и `project_roots`. Resolver используется только для локальной проверки ключа и карты проекта, Jira issue и auth-service не читай.
2. Получи `DATA_ROOT` командой `python3 "$TEST_PROTOCOL_SRC/lib/skills_config.py" data-root`.
3. Проверь ровно один `<DATA_ROOT>/tasks/<KEY>/state.md`. Продолжай только при `status: completed`, заполненных `candidate` и `checked_candidate`, принятом результате и обязательных evidence.
4. Прочитай задачу, scope, требования, критерии приёмки и источники из `state.md`; затем прочитай только нужные перечисленные в нём локальные snapshots, `inputs`, `plan.md` или notes. История итераций не является самостоятельным источником требований.
5. Если для методного или ролевого контракта state ссылается на общую документацию, используй локальный snapshot, а при его отсутствии — только указанную проектной картой или state страницу через read-only `adapter-wiki`. Перед вызовом адаптера прочитай его `SKILL.md` из сохранённого `AGENT_SKILLS_DIR`. `adapter-issues` и `adapter-vcs` в этом маршруте не вызывай.

Если state отсутствует, найден неоднозначный кандидат, status не `completed`, candidate не проверен или evidence недостаточно, покажи конкретный блокер и остановись. Не выполняй Branch-Sync, не создавай worktree, новый цикл или артефакты и ничего не меняй.

## Две фазы покрытия

Обязательная фаза `required` включает только пары «метод × роль», для которых в scope, требованиях или источниках этой задачи изменены метод и доступ этой роли к нему. Не расширяй обязательный блок до всех ролей метода только потому, что они перечислены в общей документации. Если задача меняет метод, но не позволяет однозначно определить изменённые роли, остановись с блокером вместо догадки.

Расширенная фаза `extended` включает те же затронутые методы и остальные роли, явно связанные с каждым из них в задаче или общей документации. Она запускается только после успешного прохождения всех ячеек `required` и отдельного согласия пользователя. До согласия пользователя не тестируй расширенную фазу и не включай её незапущенные ячейки в итог обязательной проверки.

Требования задачи имеют приоритет для её метода и ожидаемого HTTP-статуса; общая документация дополняет список ролей и отсутствующий контракт. Конфликт источников, неизвестный ожидаемый статус, отсутствие метода или роли в источниках блокируют соответствующую фазу.

До первого запроса к стенду выдай схему только выбранной фазы: отдельный пункт для каждой пары «метод × роль». Каждый пункт содержит `[METHOD] /path`, роль, источник и координату требования, ожидаемый HTTP-статус, сценарий подготовки данных и способ очистки. В `required` не включай роли, доступ которых задача не меняла.

## Автоматизация

Общие исполняемые скрипты лежат в `<UPL_ROOT>/scripts/test_protocol_auth.py` и `<UPL_ROOT>/scripts/test_protocol_methods.py`. Для каждого конкретного метода подготовь отдельный manifest в `<TASK_DIR>/test-protocol/methods/`; один сценарий manifest соответствует одной ячейке «метод × роль». Не объединяй разные методы в универсальный ручной shell-вызов.

Минимальная форма manifest:

```json
{
  "required": [
    {
      "id": "method-role",
      "role": "<role>",
      "method": "GET",
      "path": "/api/v1/<resource>",
      "expected_status": [200]
    }
  ],
  "extended": []
}
```

Для `PUT`/`PATCH` добавь `prepare` с `GET` и `save_as`, `json_from` с `json_patch`, а также cleanup с восстановлением; для `DELETE` добавь `prepare` с `POST`, capture идентификатора и cleanup.

Перед вызовом сначала покажи план без запросов:

```bash
python3 <UPL_ROOT>/scripts/test_protocol_methods.py --manifest <manifest> --phase required --plan-only
```

После показа плана запусти выбранную фазу тем же manifest без `--plan-only`. Для расширенной проверки используй `--phase extended` только после отдельного согласия пользователя.

`test_protocol_auth.py` read-only выбирает ровно одного активного пользователя каждой роли запросом к UPL service DB (`users.role_code`, `deleted_at IS NULL`) через `psql`, используя `UPL_DEV_DATABASE_URL` или PG* environment. Он не читает auth-service, permission-таблицы или сведения о ролях из auth. Для каждой роли скрипт держит отдельную cookie-сессию в памяти.

Все вызовы идут через общий домен `UPL_DEV_BASE_URL` (по умолчанию `https://develop.getblogger.ru`); конкретный сервис определяется только path manifest. Вход в сессию выполняется `POST /auth/dev/login` с `{"user_id":"<user_id из service DB>","auth_type":"cookie"}`. Поле `role` не передавай. Скрипт автоматически добавляет `XSRF-TOKEN` для изменяющего запроса и не добавляет ручной `X-USER-ROLE`.

Сценарий `GET` вызывает целевой path напрямую. Для `PUT` или `PATCH` сначала выполни `GET` существующего объекта, сохрани ответ в capture, сформируй минимальный `json_patch` поверх исходного тела и после проверки восстанови исходные значения. Для `DELETE` сначала выполни предусмотренный контрактом `POST` создания уникального fixture, удали именно созданный объект и выполни cleanup, если целевой DELETE не завершился ожидаемым статусом. Не используй произвольные записи или массовые операции.

Изменяющие запросы разрешены в runner, но только в объявленном manifest-сценарии с уникальным fixture или восстановлением исходного тела и обязательным cleanup. Если такой сценарий невозможно описать, заблокируй ячейку до запросов. Статус cleanup учитывай в результате.

## Авторизация и критерий результата

До первого вызова разреши `user_id` из service DB для всех ролей выбранной фазы; отсутствие доступа к БД, неоднозначность соответствия пользователя роли или отсутствие входа для одной ячейки блокирует запуск неполной фазы. Не используй ID из примера, локальной БД другого стенда или Jira.

Успешный login сам по себе не подтверждает доступ. Основной критерий каждой ячейки — HTTP-статус ответа целевого метода, сопоставленный с ожидаемым статусом для этой роли. Тело ответа, бизнес-логику и побочные поля не проверяй дополнительно, если это не является отдельным критерием задачи; для диагностики выводи только размер и SHA-256 тела. Не маскируй ошибку авторизации ошибкой payload: подготовительный и cleanup-запросы имеют свои ожидаемые статусы.

После выполнения выдай по одному результату на каждую ячейку выбранной фазы: `ожидалось`, `получено`, `PASS/FAIL`, method/path/role, статусы подготовки и cleanup, безопасную координату запроса и доказательство. Cookie, токены, `user_id` и секреты не выводи и не сохраняй в `state.md`, evidence, логах или комментариях QA.

Если все ячейки `required` имеют ожидаемый HTTP-статус и успешный cleanup, покажи результат обязательной фазы и задай пользователю отдельный вопрос о запуске `extended` для остальных ролей этих методов. Если пользователь откажется, итог пометь как `required passed; extended not run`; если согласится, выдай отдельный результат расширенной фазы. При любом FAIL обязательной ячейки вопрос о расширении не задавай.
