# Протокол задачи

## Термины

- protocol: этот маршрут; ведёт состояние задачи и принимает итоговые решения по findings и вопросам.
- checker: навык независимой read-only проверки; reviewer - отдельный субагент, выполняющий один проход checker в одном режиме.
- Режим checker: `requirements` (соответствие требованиям), `technical` (техническое качество диапазона) или `requirements-fix` (устранение названных целей).
- Проход: итерация `review-<M>` со всеми запущенными в ней режимами; считается одним проходом независимо от числа режимов.
- Manifest: запечатанный неизменяемый вход одного режима; `input_digest` - его контрольная сумма.
- Child-result: `result` одного режима; aggregate-result: сводный `review-<M>/result` прохода.
- Protocol-gate: отбор кандидатов прохода в findings; countercheck - независимая попытка опровергнуть каждого кандидата внутри protocol-gate.
- `base`, `candidate`, `checked_candidate`: SHA начала цикла, текущего результата и последнего снимка, принятого проходом checker.
- Блокер: открытый finding `Medium+`, `Low`, нарушающий явное требование, критерий приёмки или обязательное правило, либо существенный открытый вопрос.
- Человек-гейт: точка, где маршрут ждёт явного ответа пользователя (раздел "Состояние задачи").
- Цикл: работа задачи от Define до приёмки; первый цикл - исходная работа, следующие - доработки. Итерация - каталог `implementation-<N>` или `review-<M>` внутри цикла.

## Режимы запуска

Команда `read-protocol` и токен `/protocol` в постановку задачи не входят. Сообщение-команду сравнивай после удаления внешних пробелов.

- `read-protocol`: отдельное сообщение, состоящее ровно из `read-protocol`, запускает read-only подготовку общей protocol-сессии.
- Jira URL или ключ: если в сессии ранее успешно выполнено `read-protocol`, сообщение из одного полного Jira URL вида `https://<host>/browse/<KEY>` или ключа `UPL-<code>` запускает локальную инвентаризацию.
  Токен `/protocol` для этого не нужен. До анализа найденных артефактов и предложения дальнейшего действия обычное выполнение задачи не начинай.
- MR URL: если в сессии ранее успешно выполнено `read-protocol`, сообщение из одного прямого URL GitLab MR вида `https://<host>/<project>/-/merge_requests/<iid>` запускает поиск задачи MR по `$PROTOCOL_SKILL/references/mr-threads.md`.
  Токен `/protocol` для этого не нужен.
- `/protocol`: поручение с завершающим отдельным токеном `/protocol` маршрутизируй по URL-кандидатам:
  - единственный URL-кандидат прошёл Jira resolver: выполнение задачи с Jira URL;
  - URL-кандидатов нет: выполнение задачи по правилам раздела "Без Jira URL";
  - несколько URL-кандидатов или ошибка Jira resolver: маршрутизация блокируется.

Упоминание `read-protocol`, `/protocol`, Jira URL или MR URL внутри прозы, issue key и тематическое совпадение навык не активируют.

## Внешние записи

Issue tracker в protocol используй только для чтения.
  Push, создание remote-ветки или MR/PR, comments, discussions и reviews в VCS, смену статуса issue и публикацию описания результата выполняй только отдельным маршрутом по команде `/external-write <система> <действие> <цель>`.
  Этот маршрут в protocol не входит.

## Bootstrap

Перед первым действием любого режима:

1. Первым shell-вызовом protocol запусти скрипт из каталога, где загружен этот `SKILL.md`, и передай имя текущего CLI, а не имя оболочки:

   ```bash
   bash '<каталог загруженного protocol/SKILL.md>/scripts/bootstrap.sh' '<имя текущего CLI>'
   ```

2. Отсутствующий файл особенностей CLI `instructions/agent-<имя CLI>.md` не блокирует маршрут. Сохрани выведенные `PROTOCOL_SKILL` и `PROTOCOL_SRC` как константы контекста сессии.
   Shell-переменные между вызовами не сохраняются: в каждом следующем shell-вызове присваивай нужным переменным сохранённые абсолютные значения в этом же вызове.

## Подготовка общих инструкций

В режиме `read-protocol` после Bootstrap выполни по порядку:

1. Прочитай карту `upl`: `<projects-root>/upl/project.toml`, где `<projects-root>` выводит `python3 "$PROTOCOL_SRC/lib/skills_config.py" projects-root`.
2. Выбери `UPL_ROOT`: существующий корень из вывода `python3 "$PROTOCOL_SRC/lib/skills_config.py" roots --project upl`.
3. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, технологические профили из `profile_rules` карты для `upl/services` и все файлы каталога `<UPL_ROOT>/templates/templ-service/policy`.
   Путь вида `profiles/<файл>.md` из `profile_rules` отсчитывай от `$PROTOCOL_SRC`.
   Проектную прозу карты (`./`-пути из её `profile_rules`) на подготовке не читай: её читает сессия задачи, ключ которой начинается с `UPL-`.
4. Последними прочитай исходники адаптеров: `$PROTOCOL_SRC/skills/adapter/issues/SKILL.md`, `$PROTOCOL_SRC/skills/adapter/vcs/SKILL.md` и `$PROTOCOL_SRC/skills/adapter/wiki/SKILL.md`.

Отсутствующий обязательный файл или каталог блокирует подготовку.

Не читай issue, не вызывай адаптеры, не выполняй Branch-Sync, не выбирай сервис или checkout, не создавай task state и не меняй файлы или Git. После успешной загрузки кратко подтверди готовность и не переходи к выполнению задачи.

## Выполнение задачи

Выполняй задачу в подготовленном пользователем Git-репозитории. Если дорабатывается сам `protocol` (репозиторий, содержащий `PROTOCOL_SRC`), выполняй изменения только в его основном checkout на ветке `main`, без task-ветки и task worktree.
  Для задачи в другом репозитории checkout, содержащий `protocol`, в каталог исполнения не включай.

### Вход и рабочий каталог

`DATA_ROOT` получай командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root --path <каталог проекта>` либо `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root --project <проект>`.
  Вне опознанного проекта команда с этими аргументами завершается ошибкой.

#### С Jira URL

Используй `ISSUE_URL`, возвращённый resolver: он принимает полный Jira URL или issue key и возвращает нормализованные `url`, `key`, проект и разрешённые корни.
  Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.
  После выбора checkout продолжи по разделу "Состояние опознанной задачи".

#### Локальная предмаршрутная инвентаризация после `read-protocol`

После Bootstrap выполни `python3 "$PROTOCOL_SKILL/scripts/inventory.py" '<Jira URL или ключ>'`.
  Скрипт read-only: разрешает задачу тем же resolver, читает `<DATA_ROOT>/tasks/<KEY>/state.md` и перечень итераций, а в checkout под корнями проекта находит task worktree, локальные и remote-tracking ветки с ключом и состояние их деревьев.
  Расхождение tree `checked_candidate` с `checked_tree` или отсутствие `checked_tree` скрипт выводит в `reasons`, не меняя `route`.
  Код 2 блокирует маршрут.

Покажи пользователю краткий результат: `TASK_DIR`, `status` и `next` из `state.md`, worktree с состоянием дерева (`clean`, число изменений, `detached`), ветки и `reasons`.
  До выбора пользователя не вызывай `adapter-issues` или `adapter-vcs`, не выполняй Branch-Sync, не создавай `state.md` или task worktree и не меняй файлы или Git.

Дальше действуй по полю `route`:

- `continue`: предложи продолжить задачу с `work_root`, `branch`, `status` и `next` из `state.md`, не создавая новый `TASK_DIR`;
- `next-cycle`: предложи открыть следующий цикл задачи через существующий `state.md`;
- `ambiguous`: покажи кандидатов и `reasons` и предложи варианты продолжения или восстановления на человек-гейте;
- `new`: продолжи обычный старт по разделу "С Jira URL" с `url` из результата, включая resolver, чтение issue и выбор checkout.

#### Без Jira URL

Сначала покажи пользователю текущий каталог через `pwd` и текущую ветку через `git branch --show-current` либо признак `detached HEAD`.
  Дождись предварительного подтверждения и только после него используй текущий Git-репозиторий.

Каждый issue key постановки проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр.
  Единственный такой ключ без признака, что он является источником, примером или связанной задачей, считай ключом дорабатываемой задачи; отдельного подтверждения не требуй.

- Если в постановке указан URL merge request, разреши его через `adapter-vcs`; для однозначного MR возьми ключ из его ветки.
- Ключ, явно обозначенный как источник, пример или связанная задача, задачей не считай.
- Если после исключения ключей-источников, примеров и связанных задач осталось несколько ключей, попроси выбрать одну дорабатываемую задачу.
- Если Jira URL не указан и ключ задачи не найден, остановись и уточни у пользователя, какую задачу дорабатывать.

Каталог исполнения называет задачу сам, когда это task worktree: он создан под одну задачу и назван `<repo>-<KEY>`; дополнительное название задачи от команды не требуется. Получи ключ так:

```bash
source "$PROTOCOL_SKILL/../git-workflow/scripts/lib-git.sh"
task_key_from_worktree
```

Ненулевой код означает, что каталог не task worktree, и ключ нужно получить из постановки. Если ключ каталога и ключ, выбранный по постановке, расходятся, остановись и подтверди у пользователя, какую задачу дорабатывать.

Имя текущей ветки ключа не даёт: на ней репозиторий может стоять по любому поводу. Если task-ветка опознанной задачи выкачана здесь, Branch-Sync возвращает `current:`; продолжай по разделу "Изоляция" `git-lifecycle.md`.

Задаче без своего ключа в трекере выдели ключ по `$PROTOCOL_SKILL/references/task-key.md`.

Контекст выделенной работы бери из её `state.md` и итераций, указанных в `origin`; базу определяй Branch-Sync по `origin` (`git-lifecycle.md`), а не по текущей ветке.

#### Состояние опознанной задачи

Опознав задачу в любом маршруте, получи `DATA_ROOT` с `--path` выбранного checkout и прочитай `<DATA_ROOT>/tasks/<KEY>/state.md`, если файл существует.
  По правилу "Циклы и доработки" реши, продолжает ли поручение эту задачу: продолжение открывает новый цикл той же задачи, а собственные требования и собственный человек-гейт требуют отдельной задачи с `origin`.
  Отсутствующий `state.md` означает новую задачу. При неоднозначности, меняющей scope или приёмку, запроси подтверждение пользователя до фиксации состояния.

#### Рабочее дерево и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, выполни Branch-Sync и продолжай только в полученном `WORK_ROOT`.
   Репозиторий, добавленный в scope позже, проходит Branch-Sync тогда же по правилам того же файла.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORK_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORK_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define, а в цикле, где Define заменён подтверждённым выбором тредов MR, до первой правки в `WORK_ROOT`.
   Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут.
   Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
3. Используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`, получив `DATA_ROOT` с `--path "$WORK_ROOT"`. Отсутствующие каталог и `state.md` создай после Branch-Sync и до Define.
4. Убери деревья завершённых задач этого репозитория по разделу "Уборка деревьев" `git-lifecycle.md`.
   Шаг стоит здесь: скрипту уборки нужен `<DATA_ROOT>/tasks`.

## Состояние задачи

`TASK_DIR` - каталог `<key>`; ключ несёт он, поэтому имена внутри префикса не повторяют. Единственная точка агрегации - `<TASK_DIR>/state.md`.
  В нём только актуальное: состояние маршрута, координаты, определение задачи, реестр findings и открытых вопросов, а также указатели на итерации.
  История, обоснования и выводы прогонов живут в каталогах итераций; `state.md` на них ссылается, а не повторяет их.

`state.md` состоит из четырёх частей:

1. Состояние: `status` (`define`, `implement`, `accept`, `completed` или `blocked`), `task`, `next` (одна строка с первым действием следующей сессии), `cycle` и его `kind`.
   Для каждого репозитория блок `### repo: <имя>` со строками `- <поле>: <значение>`: `work_root`, `branch`, `isolation` (`worktree` или `checkout`), `base`, `candidate`, `checked_candidate`, `checked_tree`.
   `checked_candidate` и `checked_tree` описывают последний снимок, принятый проходом checker: меняй их только на шаге 5 финализации прохода (`references/checker-run.md`) и в ветке hash-only Git-финализации (`git-lifecycle.md`).
   Правка в `implement` меняет только `candidate`.
   При наличии также `mr`, `origin`, `spawned` и `evidence` с путём и SHA-256 каждого обязательного файла вне Git.
2. Задача: цель, scope, требования, критерии приёмки, источники. Одна на задачу, по циклам не раздваивается; меняет её только цикл вида `extend`.
3. Findings: строка на finding или открытый вопрос, включая активный риск и решение, ожидающее пользователя.
   Существенен вопрос, ответ на который может изменить scope, требование, критерий приёмки или решение по finding; остальные открытые вопросы неблокирующие.
   Строка содержит стабильный идентификатор, статус `open`, `resolved`, `accepted` (риск принят) или `rejected`, суть, доказательство либо недостающее доказательство и итерацию, где запись заведена.
   Finding дополнительно содержит severity, а запись `accepted` - кто принял риск и почему.
4. Итерации: строка на каталог итерации текущего цикла с его итогом и одна сводная строка прошлых циклов.

Этих четырёх частей достаточно, чтобы продолжить задачу в новой сессии; отдельный промпт возобновления не собирай.

Файлы итераций читай только по ссылке из `state.md` и только когда без них нельзя принять решение текущего шага, например в цикле `recheck`, при споре по finding, разборе тредов MR или recovery.
  Маршрут может продолжаться в нескольких сессиях.

Внутри каждой фазы выполняй один прогон.
  Прочитанный в сессии файл (`state.md`, `references/*.md`, профиль, policy-файл, код) повторно читай только после его изменения или под конкретный вопрос.

Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.

На человек-гейте покажи пользователю вопрос и завершай сессию. Подтверждением гейта считай только явный ответ пользователя.
  Выбор по умолчанию, выбор по таймауту и напоминание исполнителя подтверждением не являются: до явного ответа не выполняй действий, которые гейт разрешает.

Перед каждым переходом обнови `state.md`; затем продолжи следующее состояние, если нет человек-гейта, блокера, конфликта требований или недоступной обязательной проверки.

Обновляя `state.md`, переписывай затронутую часть по текущему состоянию, а не дописывай к ней: изменение задачи вноси в единую часть "Задача", устаревшие значения удаляй.
  Хронологию, события и обоснования записывай в `notes.md` текущей итерации.

Перед установкой `status: completed` сверни в `state.md` завершаемый цикл вместе с прошлыми:

- в части "Итерации" замени строки всех завершённых циклов одной сводной строкой с диапазоном циклов, каталогами итераций, итогом и `base` первого цикла каждого репозитория: от него строится комментарий для QA;
- в реестре findings сократи записи `resolved` и `rejected` до ID, статуса и итерации, записи `accepted` сохрани полностью; ID не удаляй и не переиспользуй;
- сохрани пути manifest и aggregate-result последнего принятого прохода.

### Итерации

Работа идёт итерациями двух видов; каждая итерация - каталог в `TASK_DIR` со сквозной нумерацией, которая не сбрасывается между циклами:

- `implementation-<N>/`: итерация реализации. Содержит `notes.md` с решениями, обоснованиями и событиями, сохранённые выводы прогонов `*.log` и копии обязательных evidence-файлов вне Git.
- `review-<M>/`: итерация независимой проверки. Для каждого режима `requirements`, `technical` и `requirements-fix` содержит отдельные `<режим>/manifest`, `<режим>/progress` и `<режим>/result`, а в корне итерации - агрегированный `result`.
  Каждому режиму назначай свой reviewer.

При входе в Define создай первую итерацию `implementation-<N>` текущего цикла и веди в ней `notes.md`; отдельного носителя у Define нет.

Задача не заводит других носителей состояния: ни файла стадии, ни общего каталога логов или приёмки, ни ручной префиксации имён номером цикла.

Снимок входного источника, без которого нельзя воспроизвести решение, клади в `<TASK_DIR>/inputs/`; секреты не копируй.

`plan.md` и `adr.md` принадлежат задаче и лежат в корне `TASK_DIR`.

Если у итерации, finding или вопроса уже есть нативный идентификатор (iid MR, id discussion или комментария, ключ issue), ссылайся на него вместо собственного. Собственный назначай только там, где нативного нет.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии.

Перед переходом из `implement` в `accept` и перед завершением сессии допиши в конец `notes.md` текущей итерации итог пакета: сделанное, оставшееся и ссылки на логи.
  Открыв `notes.md` по ссылке, читай последний итог, а остальное - только под конкретный вопрос.

### Циклы и доработки

Доработка принятого результата (изменение требований, findings или существенные вопросы независимого ревью, отложенная работа, просьба перепроверить готовое) открывает следующий цикл той же задачи и возвращает `status` в `define`.
  Цикл имеет один из двух видов, и вид определяет `base`:

- `extend`: цикл добавляет работу поверх принятого результата. `base` - полный SHA `HEAD` на входе в `implement`. Цикл 1 всегда `extend`.
- `recheck`: требования не меняются, перепроверяется уже принятый результат.
  Нового `base` не фиксируй: `base` цикла равен `base` того цикла, чей результат перепроверяется, иначе диапазон пуст и режимы `requirements` и `technical` не увидят изменений.
  Итерацию реализации такой цикл всё равно открывает: она не меняет код, а подтверждает снимок, догон базы и обязательные проверки перед проходом checker.

Открывай новый цикл только после завершения текущего по разделу "Завершение"; иначе продолжи текущий цикл с последнего валидного состояния и не запускай полный аудит.

Открывая цикл, включи все записи реестра со статусом `open` в его scope и реши их вместе с остальной работой цикла.

Отдельную задачу заводи только в двух случаях:

- Работа требует собственных требований и собственного человек-гейта: например, затрагивает другую подсистему, добавляет новую межсервисную зависимость или меняет чужой публичный контракт.
- Работу нельзя принять вместе с текущим результатом.

Во всех остальных случаях открывай цикл той же задачи. Суффикс индекса обозначает выделенную работу со своей приёмкой и никогда не заменяет цикл; клон `<KEY>-N` или второй `TASK_DIR` вместо цикла запрещён.

У выделенной задачи заполни `origin: <KEY> cycle <N>`, у исходной - `spawned` с ключом выделенной задачи; связь должна читаться в обе стороны без чтения прозы.

Ветка выделенной задачи растёт от task-ветки источника, пока та не влита в базовую ветку проекта (`git-lifecycle.md`); фактическую базу запиши как `depends_on`.

### Реестр findings

Реестр findings и открытых вопросов в `state.md` является каноническим между прогонами checker.

Protocol присваивает каждой записи стабильный ID из одной сквозной серии на задачу и хранит её статус.

Дедуплицируй записи по общей причине и нарушенному требованию или последствию; изменение формулировки либо координаты само по себе не создаёт новый finding.
  Общая причина при другом нарушенном требовании или другом достижимом последствии даёт новую запись, в том числе когда прошлая запись с той же причиной уже закрыта как `resolved`.

Protocol принимает окончательное решение по каждому finding и открытому вопросу и может обоснованно изменить scope, изменить severity finding или отклонить запись как дубликат, малозначительную или не относящуюся к задаче.

Сохрани в итерации, породившей решение, кандидатов и предварительную классификацию checker, итоговое решение и конкретное обоснование с опорой на зафиксированные scope, требования, доказательства и достижимое последствие.

Определи статус ранее сохранённого finding или вопроса по текущему снимку и доступным доказательствам.
  Учитывай отсутствие записи в результате checker как сигнал, но не считай его самостоятельным подтверждением наличия или устранения проблемы; отдельный прогон для закрытия не обязателен.

Не отклоняй, не принимай как риск и не снижай до неблокирующего подтверждённое нарушение явного требования, критерия приёмки или обязательного правила профиля либо policy-файла и не считай отсутствие доказательства устранением проблемы.

Если подтверждённый дефект существовал до задачи (его код вне `base..candidate`), а исправление меняет общий код или поведение вне scope, до исправления вынеси на человек-гейт выбор:

- исправить в этой задаче, расширив часть "Задача";
- выделить отдельную задачу по разделу "Циклы и доработки".

## Define

Для issue с типом `Bug` до фиксации scope и плана разбери пункты постановки по `$PROTOCOL_SKILL/references/item-review.md`.

Зафиксируй цель, scope и единый набор обязательных требований с наблюдаемыми критериями проверки.
  Включай в него обязательные ограничения безопасности, совместимости, миграций, данных и применимых project/policy-правил; отдельной классификации обязательных требований по источнику или виду не вводи.
  Безопасные допущения, не меняющие обязательств, фиксируй отдельно. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Путь вида `/api/...`, указанный в задаче, относится к дорабатываемому сервису, если задача явно не говорит обратного.
  Сам по себе такой путь - координата контракта внутри этого сервиса: не считай его отдельным источником требований или указанием на другой компонент при Define.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `state.md`.
  Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы одно high-risk условие:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен конкретизировать выполнение уже зафиксированных требований: инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. План не добавляет требований к задаче.
  Если требуется архитектурное решение, создай `<TASK_DIR>/adr.md` с вариантами и последствиями, а в `plan.md` укажи ссылку на ADR.
  Выбор решения вынеси на отдельный человек-гейт и до Implement зафиксируй выбранный вариант в ADR.
Если scope и требования уже зафиксированы, противоречий и существенных открытых вопросов нет, а план не требует выбора пользователя, после его фиксации сразу переходи в Implement без отдельного подтверждения плана.

Перед переходом в `implement` зафиксируй неизменный `base` текущего цикла по его виду ("Циклы и доработки").

## Implement

Используй созданную в Define итерацию `implementation-<N>` и веди её `notes.md`.

Перед первым изменением:

1. Прочитай отдельные правила Implement и их приоритет, явно названные применимыми профилями, и разреши конфликты по этому приоритету.
2. Сверь в `notes.md` применимые обязательные требования и известные ограничения. Если для их выполнения нужен выбор реализации, зафиксируй его как рабочее решение без расширения scope, требований или критериев приёмки.

Затем выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать обязательному требованию; технические решения, примеры и порядок реализации сами по себе не становятся критериями приёмки.
  Контракты вне scope сохраняй.

Для issue с типом `Bug` в конце Implement добавь в `notes.md` текущей итерации секцию `Bug-Causal-Analysis`.
  Включи отдельную запись по каждому незачёркнутому пункту Issue с вердиктом `согласен`; пункты, исключённые как `исключён: зачёркнут` или `исключён: отклонён`, перечисли отдельно без записи причинного анализа.
  Каждая запись содержит `Первопричина`, `Пропуск исходной задачей` и `Профилактика`. Заверши раздел до Accept.

Доработку по тредам MR начинай с раздела "Правила из замечаний" `references/mr-threads.md`.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения.

До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`. После merge базы повтори prepare и все проверки.

Выполни запланированные проверки. Если профиль задаёт read-only project verify, выполни его. При ненулевом результате или предупреждении, требующем исправления, верни задачу в `implement`, устрани проблему и повтори весь затронутый набор проверок.
  Если проверка изменила рабочее дерево, проверь diff, прими только допустимые изменения и повтори зависимые проверки; не фиксируй evidence до получения стабильного clean candidate.

После успешных проверок и получения стабильного clean candidate создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `candidate` цикла, сверь `base..candidate` с требованиями и переведи задачу в `accept`.
  Хешируй файл вне Git SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Для каждого репозитория сверь, что его `HEAD == candidate`, task-ветка верна, рабочее дерево чисто и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256.
  Прочитай отдельные правила Accept и их приоритет, явно названные применимыми профилями.

Для issue с типом `Bug` передай checker секцию `Bug-Causal-Analysis` из `notes.md` как обязательный артефакт; критерий её полноты - состав, заданный в Implement.

Проведи проход checker по `$PROTOCOL_SKILL/references/checker-run.md`.

### Решение после прохода

После финализации прохода выбери продолжение по реестру:

| Состояние | Действие |
|---|---|
| Блокеров нет | Перейди к итоговому принятию. |
| Блокеры есть | Верни задачу в `implement` текущего цикла: обнови реестр, устрани все блокеры одним пакетом, повтори проверки и commit, обнови `candidate`. Затем оцени устранение по текущему снимку и обязательным проверкам. |
| После пакета устранение всех блокеров подтверждено снимком и проверками | Перейди к итоговому принятию без нового прохода. |
| После пакета устранение нельзя подтвердить снимком и проверками; последний проход первый в цикле или дал улучшение; лимит проходов не исчерпан | Запусти повторный проход. |
| После пакета блокер остался открытым либо нужен повторный проход, но последний проход не дал улучшения или лимит исчерпан | Установи `blocked`, запиши в `state.md` нерешённые блокеры и неподтверждённые устранения и первое действие в `next`, вынеси решение на человек-гейт. |

Улучшение и лимит проходов определяет `references/checker-run.md`.

Если блокер найден вне checker после принятого прохода, например на стенде или человеком, и его устранение изменило tree `candidate`, перед итоговым принятием запусти `requirements-fix`.
  Целью прохода служит этот finding, `BASE = checked_candidate`; до результата прохода finding остаётся `open`.

Неблокирующий `Low` и неблокирующий вопрос, решение по которым отложено, оставь `open` до следующего цикла, если он будет: приёмку они не блокируют.

Подтверждённый finding, который решено не исправлять, переведи в `accepted`: `Low` - решением protocol с обоснованием, `Medium+` - только явным решением пользователя на человек-гейте.
  `accepted` - конечный статус: в следующий цикл запись не переносится.

### Итоговое принятие

После итогового принятия и до сбора комментария для QA выполни Git-финализацию по [разделу "Результат" в `git-lifecycle.md`](references/git-lifecycle.md#результат).

После успешной Git-финализации собери комментарий для QA по `$PROTOCOL_SKILL/references/result-report.md` и покажи его пользователю.
  Сверь условия раздела "Завершение" и только после этого атомарно установи `status: completed` и очисти `next`.
  При любой несогласованности сохрани `accept` или `blocked` с причиной и первым действием в `next`; нового reviewer из-за этого не запускай.

Если задача выполнялась в отдельном task worktree, сразу после установки `status: completed` удали именно этот task worktree через `remove-task-worktree.sh` по разделу "Уборка деревьев" `git-lifecycle.md`; отдельная команда пользователя не нужна.

## Описание результата

Запрос описания сделанного (отчёт заказчику, разбор для смежной команды, ответ о состоянии задачи) собирай по `$PROTOCOL_SKILL/references/result-report.md`.

## Завершение

Задача завершена, когда выполнены все условия:

1. Требования и критерии приёмки подтверждены, обязательные проверки успешны.
2. Последний проход принят: aggregate-result и все обязательные child-result на месте, reviewer и protocol-gate завершены без `stale` и `blocked`.
   Manifest каждого режима проходит `review_manifest.py verify --integrity <manifest> --digest <input_digest из state.md>`: флаг `--integrity` нужен, потому что Git-финализация меняет SHA `candidate`.
   Snapshots сверяет раздел "Результат" `git-lifecycle.md`.
3. Блокеров нет, protocol принял итоговый реестр.
4. Локальный результат закоммичен, Git-финализация выполнена, evidence сохранили зафиксированный SHA-256.
5. Комментарий для QA собран и показан пользователю.
6. `state.md` свёрнут по разделу "Состояние задачи".
