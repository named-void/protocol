# Протокол задачи

## Режимы запуска

Команда `read-protocol` и токен `/protocol` в постановку задачи не входят. Сообщение-команду сравнивай после удаления внешних пробелов.

- `read-protocol`: отдельное сообщение, состоящее ровно из `read-protocol`, запускает read-only подготовку общей protocol-сессии.
- Jira URL или ключ: если в сессии ранее успешно выполнено `read-protocol`, сообщение из одного полного Jira URL вида `https://<host>/browse/<KEY>` или ключа `UPL-<code>` запускает локальную инвентаризацию.
  Токен `/protocol` для этого не нужен. До анализа найденных артефактов и предложения дальнейшего действия обычное выполнение задачи не начинай.
- MR URL: если в сессии ранее успешно выполнено `read-protocol`, сообщение из одного прямого URL GitLab MR вида `https://<host>/<project>/-/merge_requests/<iid>` запускает поиск задачи MR (раздел "MR URL после `read-protocol`").
  Токен `/protocol` для этого не нужен.
- `/protocol`: поручение с завершающим отдельным токеном `/protocol` маршрутизируй по URL-кандидатам:
  - единственный URL-кандидат прошёл Jira resolver: выполнение задачи с Jira URL;
  - URL-кандидатов нет: выполнение задачи по правилам раздела "Без Jira URL";
  - несколько URL-кандидатов или ошибка Jira resolver: маршрутизация блокируется.

Упоминание `read-protocol`, `/protocol`, Jira URL или MR URL внутри прозы, issue key и тематическое совпадение навык не активируют.

## Внешние записи

Issue tracker в protocol используй только для чтения.
  Push, создание remote-ветки или MR/PR, comments, discussions и reviews в VCS, смену статуса issue и публикацию описания результата выполняй только отдельным маршрутом по команде `/external-write <система> <действие> <цель>`.
  Этот маршрут в protocol не входит.

## Bootstrap

Перед первым действием любого режима:

1. В первом shell-вызове protocol используй абсолютный путь, по которому загружен этот `SKILL.md`, подставь имя текущего CLI и выполни весь блок целиком:

   ```bash
   set -eu

   PROTOCOL_SKILL_FILE='<абсолютный путь загруженного protocol/SKILL.md>'
   PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
   PROTOCOL_SKILL="$(dirname "$(realpath "$PROTOCOL_SKILL_FILE")")"
   PROTOCOL_SRC="$(cd "$PROTOCOL_SKILL/../.." && pwd -P)"
   PROTOCOL_INSTRUCTIONS="$PROTOCOL_SRC/instructions"

   test -r "$PROTOCOL_INSTRUCTIONS/environment.md"
   test -r "$PROTOCOL_SRC/lib/skills_config.py"
   printf 'PROTOCOL_SKILL=%s\nPROTOCOL_SRC=%s\n' "$PROTOCOL_SKILL" "$PROTOCOL_SRC"
   cat "$PROTOCOL_INSTRUCTIONS/environment.md"

   PROTOCOL_AGENT_INSTRUCTIONS="$PROTOCOL_INSTRUCTIONS/agent-$PROTOCOL_AGENT.md"
   test ! -e "$PROTOCOL_AGENT_INSTRUCTIONS" || cat "$PROTOCOL_AGENT_INSTRUCTIONS"
   ```

2. Отсутствующий справочник исполнителя не блокирует маршрут. Сохрани выведенные `PROTOCOL_SKILL` и `PROTOCOL_SRC` как константы контекста сессии.
   Shell-переменные между вызовами не сохраняются: в каждом следующем shell-вызове присваивай нужным переменным сохранённые абсолютные значения в этом же вызове.

## Подготовка общих инструкций

В режиме `read-protocol` после Bootstrap выполни по порядку:

1. Прочитай карту `upl`: `<projects-root>/upl/project.toml`, где `<projects-root>` выводит `python3 "$PROTOCOL_SRC/lib/skills_config.py" projects-root`.
2. Выбери `UPL_ROOT`: существующий корень из вывода `python3 "$PROTOCOL_SRC/lib/skills_config.py" roots --project upl`.
3. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, технологические профили из `profile_rules` карты для `upl/services` и все файлы каталога `<UPL_ROOT>/templates/templ-service/policy`.
   Путь вида `profiles/<файл>.md` из `profile_rules` отсчитывай от `$PROTOCOL_SRC`.
   Проектную прозу карты (`./`-пути из её `profile_rules`) на подготовке не читай: её читает сессия задачи, ключ которой начинается с `UPL-`.
4. Последними прочитай исходники адаптеров: `$PROTOCOL_SRC/skills/adapter/issues/SKILL.md`, `$PROTOCOL_SRC/skills/adapter/vcs/SKILL.md` и `$PROTOCOL_SRC/skills/adapter/wiki/SKILL.md`.

Отсутствующий обязательный файл или каталог блокирует подготовку.

Не читай issue, не вызывай адаптеры, не выполняй Branch-Sync, не выбирай сервис или checkout, не создавай task state и не меняй файлы или Git. После успешной загрузки кратко подтверди готовность и не переходи к выполнению задачи.

## Выполнение задачи

Выполняй задачу в подготовленном пользователем Git-репозитории. Если дорабатывается сам `protocol` (репозиторий, содержащий `PROTOCOL_SRC`), выполняй изменения только в его основном checkout на ветке `main`, без task-ветки и task worktree.
  Для задачи в другом репозитории checkout, содержащий `protocol`, в каталог исполнения не включай.

### Вход и рабочий каталог

`DATA_ROOT` получай только с контекстом проекта: `cd <каталог проекта> && python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root` либо `AGENTS_PROJECT=<проект> python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root`.
  Аргументы команда игнорирует, а без контекста молча возвращает `projects/_common/.data` без артефактов задачи.

#### С Jira URL

Используй `ISSUE_URL`, возвращённый resolver: он принимает полный Jira URL или issue key и возвращает нормализованные `url`, `key`, проект и разрешённые корни.
  Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.
  После выбора checkout продолжи по разделу "Состояние опознанной задачи".

#### Локальная предмаршрутная инвентаризация после `read-protocol`

После Bootstrap передай исходный полный Jira URL или ключ `UPL-<code>` в `"$PROTOCOL_SKILL/scripts/resolve_issue.py"`.
  Сохрани из JSON-результата нормализованные `KEY`, `ISSUE_URL` и `project_roots`; для ключа URL формирует resolver из настроенного Jira host.
  Получи `DATA_ROOT` в каталоге `project_roots[0]`. Ничего не создавай и не меняй.

В read-only режиме проверь `<DATA_ROOT>/tasks/<KEY>/state.md` и соседние артефакты задачи, включая `status`, `next`, `work_root`, `branch`, `candidate`, `checked_candidate` и перечень итераций.
В каждом доступном локальном checkout под корнями `project.roots` текущей карты проектов проверь `git worktree list --porcelain`, локальные ветки и remote-tracking refs с ключом задачи.
  Для текущего checkout и каждого найденного task worktree выполни `git status --short --branch`.
  Отдельно зафиксируй `clean`, `dirty`, `detached` и наличие незакоммиченных изменений.

Собери для пользователя краткий инвентаризационный результат: найденные `TASK_DIR` и `state.md`, статусы задач, пути worktree, ветки, состояние деревьев, `next` и неоднозначности.
  До выбора пользователя не вызывай `adapter-issues` или `adapter-vcs`, не выполняй Branch-Sync, не создавай `state.md` или task worktree и не меняй файлы или Git.

Если найден один продолжаемый `state.md` со статусом `define`, `implement`, `accept` или `blocked`, предложи продолжить ту же задачу с указанными в нём `work_root`, `branch`, `status` и `next`, не создавая новый `TASK_DIR`.
  Если найден `status: completed`, предложи открыть следующий цикл той же задачи через существующий `state.md`.
Если найдено несколько кандидатов, отсутствует `state.md` при наличии worktree или состояние дерева не позволяет безопасно продолжить, покажи кандидатов и предложи варианты продолжения или восстановления.
  До явного выбора пользователя маршрут не продолжай.

Если локальных артефактов, веток и worktree с этим ключом не найдено, продолжи обычный старт по разделу "С Jira URL" с сохранённым `ISSUE_URL`, включая resolver, чтение issue и последующий выбор checkout.

#### MR URL после `read-protocol`

До подтверждения выбора пользователем файлы, Git и `state.md` не меняй.

1. Разреши MR командой `python3 "$PROTOCOL_SKILL/scripts/resolve_mr.py" '<MR_URL>'`: она выводит JSON с `host`, `project_path`, `iid`, проектом `profile` и локальным checkout `local_path`.
   Код 2 блокирует маршрут. Код 3 означает, что локальный checkout не совпадает с MR; JSON при этом выведен, и для поиска задачи его достаточно.
2. Получи `DATA_ROOT` с `AGENTS_PROJECT=<profile>`, а source-ветку MR через `adapter-vcs`.
3. Найди задачи, у которых в `<DATA_ROOT>/tasks/*/state.md` поле `mr` указывает на этот MR либо `branch` совпадает с source-веткой MR.
   - Задача не найдена: сообщи пользователю, что MR не связан с задачами, реализованными через protocol на этой машине, и останови маршрут.
   - Найдено несколько задач: покажи их и дождись выбора пользователя; дальше работай с выбранной задачей.
   - У задачи `status: blocked`: покажи блокер и `next` из её `state.md` и останови маршрут до решения пользователя.
   - У задачи другой статус: перейди к разбору тредов.

Разбери незакрытые треды MR:

1. Через `adapter-vcs` получи SHA head MR и все discussions с учётом pagination. Оставь незакрытые треды: discussions, которые можно закрыть и которые ещё не закрыты.
   Тред - один discussion со всеми его комментариями в порядке публикации; обозначай его native id discussion.
2. Каждый тред проверь по снимку head MR с учётом требований задачи из её `state.md`, применимых правил и контрактов. Вынеси вердикт:
   - `согласен`: замечание подтверждено доказательством и не противоречит требованиям, правилам и контрактам;
   - `согласен с уточнением`: замечание верно по сути, но требует уточнения объёма, способа исправления или формулировки;
   - `не согласен`: замечание не подтверждено, противоречит требованиям, правилам или контракту либо для его проверки недостаточно данных.
   Если тред уже разобран в прошлом заходе этой задачи и в нём нет новых комментариев, а затронутые им файлы не менялись между сохранённым и текущим head MR, оставь вердикт из `notes.md` без повторной проверки.
3. Для вердиктов `не согласен` и `согласен с уточнением` сформулируй ответ в тред как самостоятельный комментарий.
   Назови проверенные условия и фактический результат либо конфликтующее требование с координатой, а для уточнения - что именно уточняется и почему. Не ссылайся на внутренний ход рассуждений.
4. Покажи пользователю весь список незакрытых тредов в формате `Тред | Автор | Координата | Суть | Вердикт | Обоснование или ответ`.
   Это человек-гейт: предложи выбрать треды для доработки.

После подтверждения выбора открой доработку в задаче MR по её `status`:

- `completed`: открой следующий цикл вида `extend` по правилу "Циклы и доработки"; выбранные треды становятся источниками требований цикла, а подтверждённый выбор тредов заменяет человек-гейт Define этого цикла;
- `define`: добавь выбранные треды в источники требований текущего цикла;
- `implement` или `accept`: внеси выбранные треды в реестр findings текущего цикла со статусом `open` и severity, которую назначает protocol, и верни задачу в `implement`.

Сохрани SHA head MR, список тредов, вердикты, ответы и выбор пользователя в `notes.md` итерации реализации текущего цикла; в реестре findings ссылайся на треды по native id discussion.
  Дальше веди задачу с `work_root` и `branch` из её `state.md`, начиная с раздела "Рабочее дерево и правила проекта".

#### Без Jira URL

Сначала покажи пользователю текущий каталог через `pwd` и текущую ветку через `git branch --show-current` либо признак `detached HEAD`.
  Дождись предварительного подтверждения и только после него используй текущий Git-репозиторий.

Каждый issue key постановки проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр.
  Единственный такой ключ без признака, что он является источником, примером или связанной задачей, считай ключом дорабатываемой задачи; отдельного подтверждения не требуй.

- Если в постановке указан URL merge request, разреши его через `adapter-vcs`; для однозначного MR возьми ключ из его ветки.
- Ключ, явно обозначенный как источник, пример или связанная задача, задачей не считай.
- Если после исключения ключей-источников, примеров и связанных задач осталось несколько ключей, попроси выбрать одну дорабатываемую задачу.
- Если Jira URL не указан и ключ задачи не найден, остановись и уточни у пользователя, какую задачу дорабатывать.

Каталог исполнения называет задачу сам, когда это task worktree: он создан под одну задачу и назван `<repo>-<KEY>`; дополнительное название задачи от команды не требуется. Получи ключ так:

```bash
source "$PROTOCOL_SKILL/../git-workflow/scripts/lib-git.sh"
task_key_from_worktree
```

Ненулевой код означает, что каталог не task worktree, и ключ нужно получить из постановки. Если ключ каталога и ключ, выбранный по постановке, расходятся, остановись и подтверди у пользователя, какую задачу дорабатывать.

Имя текущей ветки ключа не даёт: на ней репозиторий может стоять по любому поводу.
  Оно нужно только для сверки: когда task-ветка опознанной задачи выкачана здесь, Branch-Sync возвращает `current:`. Это человек-гейт: спроси, отколоть worktree или вести доработку прямо в этой ветке (`git-lifecycle.md`).

Задаче без своего ключа в трекере ключ выделяется от того, к чему она относится, а не из общей нумерации:

1. База: ключ задачи-источника, из которой работа выделена, то есть задачи той ветки или того MR (`UPL-940`). Он берётся из `origin` выделенной работы.
   Ветка источника может быть ещё не запушена: на выбор базы это не влияет. Источник, названный MR, разрешай через `adapter-vcs`.
2. Базой служит имя рабочего каталога репозитория (`ord-service`), только когда источника нет вовсе: работа не выделена ни из какой задачи и `origin` у неё пуст.

Индекс к базе выдели командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-task-key <база> --path "$WORK_ROOT"`: он продолжает максимальный уже видимый индекс этой базы в каталогах задач, ветках, worktree и заголовках коммитов.
  Выделение идемпотентно до создания `TASK_DIR`, поэтому ключ занимает именно созданный каталог.

Производный ключ наследует регистр базы: `UPL-940-6` остаётся в верхнем, `ord-service-1` в нижнем.

Контекст выделенной работы бери из её `state.md` и итераций, указанных в `origin`; базу определяй Branch-Sync по `origin` (`git-lifecycle.md`), а не по текущей ветке.

#### Состояние опознанной задачи

Опознав задачу в любом маршруте, получи `DATA_ROOT` в выбранном checkout и прочитай `<DATA_ROOT>/tasks/<KEY>/state.md`, если файл существует.
  Если этот `state.md` уже прочитан в сессии и с тех пор не менялся, используй прочитанное.
  По правилу "Циклы и доработки" реши, продолжает ли поручение эту задачу: продолжение открывает новый цикл той же задачи, а собственные требования и собственный человек-гейт требуют отдельной задачи с `origin`.
  Отсутствующий `state.md` означает новую задачу. При неоднозначности, меняющей scope или приёмку, запроси подтверждение пользователя до фиксации состояния.

#### Рабочее дерево и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, если он ещё не прочитан в этой сессии, выполни Branch-Sync и продолжай только в полученном `WORK_ROOT`.
   Репозиторий, добавленный в scope позже, проходит Branch-Sync тогда же по правилам того же файла.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORK_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORK_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define. Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут.
   Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
   Профиль или policy-файл, уже прочитанный в этой сессии, повторно не читай.
3. Используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`, получив `DATA_ROOT` в `$WORK_ROOT`. Отсутствующие каталог и `state.md` создай после Branch-Sync и до Define.
4. Убери деревья завершённых задач этого репозитория по разделу "Уборка деревьев" `git-lifecycle.md`.
   Шаг стоит здесь: скрипту уборки нужен `<DATA_ROOT>/tasks`.

## Состояние задачи

`TASK_DIR` - каталог `<key>`; ключ несёт он, поэтому имена внутри префикса не повторяют. Единственная точка агрегации - `<TASK_DIR>/state.md`.
  В нём только актуальное: состояние маршрута, координаты, определение задачи, реестр findings и открытых вопросов, а также указатели на итерации.
  История, обоснования и выводы прогонов живут в каталогах итераций; `state.md` на них ссылается, а не повторяет их.

`state.md` состоит из четырёх частей:

1. Состояние: `status` (`define`, `implement`, `accept`, `completed` или `blocked`), `task`, `next` (одна строка с первым действием следующей сессии), `cycle` и его `kind`.
   Для каждого репозитория: `work_root`, `branch`, `isolation` (`worktree` или `checkout`), `base`, `candidate`, `checked_candidate`, `checked_tree`.
   При наличии также `mr`, `origin`, `spawned` и `evidence` с путём и SHA-256 каждого обязательного файла вне Git.
2. Задача: цель, scope, требования, критерии приёмки, источники. Одна на задачу, по циклам не раздваивается; меняет её только цикл вида `extend`.
3. Findings: строка на finding или открытый вопрос, включая активный риск и решение, ожидающее пользователя.
   Существенен вопрос, ответ на который может изменить scope, требование, критерий приёмки или решение по finding; остальные открытые вопросы неблокирующие.
   Строка содержит стабильный идентификатор, статус `open`, `resolved` или `rejected`, суть, доказательство либо недостающее доказательство и итерацию, где запись заведена.
   Finding дополнительно содержит severity.
4. Итерации: строка на каталог итерации текущего цикла с его итогом и одна сводная строка прошлых циклов.

Этих четырёх частей достаточно, чтобы продолжить задачу в новой сессии; отдельный промпт возобновления не собирай.

Файлы итераций читай только по ссылке из `state.md` и только когда без них нельзя принять решение текущего шага, например в цикле `recheck`, при споре по finding, разборе тредов MR или recovery.
  Маршрут может продолжаться в нескольких сессиях.

Внутри каждой фазы выполняй один прогон; неизменившиеся правила и код повторно не перечитывай без конкретного вопроса. На человек-гейте завершай сессию.

Расход фазы в `state.md` не фиксируй: он не влияет на решения маршрута.

Перед каждым переходом обнови `state.md`; затем продолжи следующее состояние, если нет человек-гейта, блокера, конфликта требований или недоступной обязательной проверки.

Обновляя `state.md`, переписывай затронутую часть по текущему состоянию, а не дописывай к ней: изменение задачи вноси в единую часть "Задача", устаревшие значения удаляй.
  Хронологию, события и обоснования записывай в `notes.md` текущей итерации.

Перед установкой `status: completed` сверни в `state.md` завершаемый цикл вместе с прошлыми:

- в части "Итерации" замени строки всех завершённых циклов одной сводной строкой с диапазоном циклов, каталогами итераций, итогом и `base` первого цикла каждого репозитория: от него строится комментарий для QA;
- в реестре findings сократи записи `resolved` и `rejected` до ID, статуса и итерации; ID не удаляй и не переиспользуй;
- сохрани пути manifest и aggregate-result последнего принятого прохода.

### Итерации

Работа идёт итерациями двух видов; каждая итерация - каталог в `TASK_DIR` со сквозной нумерацией, которая не сбрасывается между циклами:

- `implementation-<N>/`: итерация реализации. Содержит `notes.md` с решениями, обоснованиями и событиями, сохранённые выводы прогонов `*.log` и копии обязательных evidence-файлов вне Git.
- `review-<M>/`: итерация независимой проверки. Для каждого режима `requirements`, `technical` и `requirements-fix` содержит отдельные `<режим>/progress` и `<режим>/result`, а в корне итерации - агрегированный `result`.
  Каждому режиму назначай свой checker-thread и пути `progress` и `result`.

При входе в Define создай первую итерацию `implementation-<N>` текущего цикла и веди в ней `notes.md`; отдельного носителя у Define нет.

Задача не заводит других носителей состояния: ни файла стадии, ни общего каталога логов или приёмки, ни ручной префиксации имён номером цикла.

Снимок входного источника, без которого нельзя воспроизвести решение, клади в `<TASK_DIR>/inputs/`; секреты не копируй.

`plan.md` и `adr.md` принадлежат задаче и лежат в корне `TASK_DIR`.

Если у итерации, finding или вопроса уже есть нативный идентификатор (iid MR, id discussion или комментария, ключ issue), ссылайся на него вместо собственного. Собственный назначай только там, где нативного нет.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии.

Перед переходом из `implement` в `accept` и перед завершением сессии допиши в конец `notes.md` текущей итерации итог пакета: сделанное, оставшееся и ссылки на логи.
  Открыв `notes.md` по ссылке, читай последний итог, а остальное - только под конкретный вопрос.

### Циклы и доработки

Доработка принятого результата (изменение требований, findings или существенные вопросы независимого ревью, отложенная работа, просьба перепроверить готовое) открывает следующий цикл той же задачи и возвращает `status` в `define`.
  Цикл имеет один из двух видов, и вид определяет `base`:

- `extend`: цикл добавляет работу поверх принятого результата. `base` - полный SHA `HEAD` на входе в `implement`. Цикл 1 всегда `extend`.
- `recheck`: требования не меняются, перепроверяется уже принятый результат.
  Нового `base` не фиксируй: `base` цикла равен `base` того цикла, чей результат перепроверяется, иначе диапазон пуст и режимы `requirements` и `technical` не увидят изменений.
  Итерацию реализации такой цикл всё равно открывает: она не меняет код, а подтверждает снимок, догон базы и обязательные проверки перед проходом checker.

Открывая цикл, включи все записи реестра со статусом `open` в его scope и реши их вместе с остальной работой цикла.

Отдельную задачу заводи только в двух случаях:

- Работа требует собственных требований и собственного человек-гейта: например, затрагивает другую подсистему, добавляет новую межсервисную зависимость или меняет чужой публичный контракт.
- Работу нельзя принять вместе с текущим результатом.

Во всех остальных случаях открывай цикл той же задачи. Суффикс индекса обозначает выделенную работу со своей приёмкой и никогда не заменяет цикл; клон `<KEY>-N` или второй `TASK_DIR` вместо цикла запрещён.

У выделенной задачи заполни `origin: <KEY> cycle <N>`, у исходной - `spawned` с ключом выделенной задачи; связь должна читаться в обе стороны без чтения прозы.

Ветка выделенной задачи растёт от task-ветки источника, пока та не влита в базовую ветку проекта (`git-lifecycle.md`); фактическую базу запиши как `depends_on`.

### Реестр findings

Реестр findings и открытых вопросов в `state.md` является каноническим между прогонами checker.

Protocol присваивает каждой записи стабильный ID из одной сквозной серии на задачу и хранит её статус.

Дедуплицируй записи по общей причине и нарушенному требованию или последствию; изменение формулировки либо координаты само по себе не создаёт новый finding.
  Общая причина при другом нарушенном требовании или другом достижимом последствии даёт новую запись, в том числе когда прошлая запись с той же причиной уже закрыта как `resolved`.

Protocol принимает окончательное решение по каждому finding и открытому вопросу и может обоснованно изменить scope, изменить severity finding или отклонить запись как дубликат, малозначительную или не относящуюся к задаче.

Сохрани в итерации, породившей решение, кандидатов и предварительную классификацию checker, итоговое решение и конкретное обоснование с опорой на зафиксированные scope, требования, доказательства и достижимое последствие.

Определи статус ранее сохранённого finding или вопроса по текущему снимку и доступным доказательствам.
  Учитывай отсутствие записи в результате checker как сигнал, но не считай его самостоятельным подтверждением наличия или устранения проблемы; отдельный прогон для закрытия не обязателен.

Не отклоняй и не снижай до неблокирующего подтверждённое нарушение явного требования, критерия приёмки или обязательного правила профиля либо policy-файла и не считай отсутствие доказательства устранением проблемы.

## Define

Для issue с типом `Bug` до фиксации scope и плана выполни разбор актуальной постановки:

1. Сохрани порядок и идентификаторы всех пунктов источника; составной пункт раздели только на независимые требования.
   Зачёркнутые пункты и фрагменты явно пометь как `исключён: зачёркнут`; не воспроизводи их, не выдавай по ним вердикт, не переноси их в требования или scope и не задавай о них вопросов.
   Если зачёркнута только часть пункта, анализируй оставшийся текст; если содержательного текста не осталось, пометь весь пункт как `исключён: зачёркнут` и пропусти его.
2. Каждый незачёркнутый пункт проверь отдельно по текущему снимку кода и контракта.
   Зафиксируй `Воспроизведение: подтверждено`, `не подтверждено`, `неприменимо` для требования о новом поведении либо `недостаточно данных` с точным названием недостающего доказательства.
3. По каждому незачёркнутому пункту вынеси итоговый вердикт `согласен` или `не согласен`.
   Используй `согласен`, только если утверждение о дефекте подтверждено либо пункт о новом поведении неприменим к воспроизведению и не противоречит актуальным требованиям, спецификациям, контрактам и правилам, применимым на Define.
   При неподтверждённом дефекте, недостатке данных или конфликте используй `не согласен`.
4. Обоснование `не согласен` сформулируй как самостоятельный комментарий к issue: назови отклоняемый пункт, условия и фактический результат проверки либо конфликтующее требование с координатой.
   Объясни, почему пункт нельзя принять, и укажи минимально необходимое уточнение или исправление постановки.
   Не ссылайся на внутренний ход рассуждений и не требуй от читателя контекста из сессии.
5. Покажи пользователю весь список пунктов источника, включая исключённые, в формате `Пункт | Состояние | Воспроизведение | Вердикт | Обоснование`.
   - Для зачёркнутых пунктов укажи `исключён: зачёркнут`, `не выполнялось` и `не требуется`.
   - Для незачёркнутых пунктов укажи `Состояние: активен` и заполни воспроизведение, вердикт и обоснование.
   - Сохрани список и решение пользователя в `notes.md` первой итерации реализации текущего цикла.
   - Это человек-гейт: до явного подтверждения пользователя не фиксируй итоговые требования и не переходи в Implement.
     После подтверждения включи в scope и требования только незачёркнутые пункты с вердиктом `согласен`; пункты с вердиктом `не согласен` явно пометь как `исключён: отклонён`.

Зафиксируй цель, scope и единый набор обязательных требований с наблюдаемыми критериями проверки.
  Включай в него обязательные ограничения безопасности, совместимости, миграций, данных и применимых project/policy-правил; отдельной классификации обязательных требований по источнику или виду не вводи.
  Безопасные допущения, не меняющие обязательств, фиксируй отдельно. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Путь вида `/api/...`, указанный в задаче, относится к дорабатываемому сервису, если задача явно не говорит обратного.
  Сам по себе такой путь - координата контракта внутри этого сервиса: не считай его отдельным источником требований или указанием на другой компонент при Define.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `state.md`.
  Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы одно high-risk условие:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен конкретизировать выполнение уже зафиксированных требований: инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. План не добавляет требований к задаче.
  Если требуется архитектурное решение, создай `<TASK_DIR>/adr.md` с вариантами и последствиями, а в `plan.md` укажи ссылку на ADR.
  Выбор решения вынеси на отдельный человек-гейт, после него зафиксируй выбранный вариант в ADR и не переходи в Implement без него.
Если scope и требования уже зафиксированы, противоречий и существенных открытых вопросов нет, а план не требует выбора пользователя, после его фиксации сразу переходи в Implement без отдельного подтверждения плана.

Перед переходом в `implement` зафиксируй неизменный `base` текущего цикла по его виду ("Циклы и доработки").

## Implement

Используй созданную в Define итерацию `implementation-<N>` и веди её `notes.md`.

Перед первым изменением:

1. Прочитай отдельные правила Implement и их приоритет, явно названные применимыми профилями, и разреши конфликты по этому приоритету.
2. Для HTTP JSON-входа сверь [профиль HTTP/API](../../profiles/http-api.md) и примени его правила binding, типизации DTO и ответов об ошибке.
   Binding не заменяет доменную защиту для не-HTTP вызовов; при дублировании сверяй одинаковые поле, код и смысл ошибки.
3. Сверь в `notes.md` применимые обязательные требования и известные ограничения. Если для их выполнения нужен выбор реализации, зафиксируй его как рабочее решение без расширения scope, требований или критериев приёмки.

Затем выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать обязательному требованию; технические решения, примеры и порядок реализации сами по себе не становятся критериями приёмки.
  Контракты вне scope сохраняй.

Для issue с типом `Bug` в конце Implement добавь в `notes.md` текущей итерации секцию `Bug-Causal-Analysis`.
  Включи отдельную запись по каждому незачёркнутому пункту Issue с вердиктом `согласен`; пункты, исключённые как `исключён: зачёркнут` или `исключён: отклонён`, перечисли отдельно без записи причинного анализа.
  Каждая запись содержит `Первопричина`, `Пропуск исходной задачей` и `Профилактика`. Заверши раздел до Accept.

Если подтверждённое техническое замечание из discussions MR требует доработки, до изменения реализации проверь, отражена ли его общая причина или нарушенное требование в применимых версионируемых правилах.

Если отражения нет, сначала добавь обобщённый проверяемый инвариант в самый узкий доступный для записи источник правил, охватывающий сценарий.

Перед записью сверь Git-статус его репозитория и не затрагивай чужие изменения. Не переноси отклонённые замечания, требования только конкретной задачи, неподтверждённые выводы и смысловые дубли. Проверяемый checkout MR остаётся read-only.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения.

До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`. После merge базы повтори prepare и все проверки.

Выполни запланированные проверки. Если профиль задаёт read-only project verify, выполни его. При ненулевом результате или предупреждении, требующем исправления, верни задачу в `implement`, устрани проблему и повтори весь затронутый набор проверок.
  Если проверка изменила рабочее дерево, проверь diff, прими только допустимые изменения и повтори зависимые проверки; не фиксируй evidence до получения стабильного clean candidate.

После успешных проверок и получения стабильного clean candidate создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `candidate` цикла, сверь `base..candidate` с требованиями и переведи задачу в `accept`.
  Хешируй файл вне Git SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Для каждого репозитория сверь, что его `HEAD == candidate`, task-ветка верна, рабочее дерево чисто и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256.
  Прочитай отдельные правила Accept и их приоритет, явно названные применимыми профилями.

Для issue с типом `Bug` передай checker секцию `Bug-Causal-Analysis` из `notes.md` как обязательный артефакт; критерий её полноты - состав, заданный в Implement.

Подготовь в маршруте checker самодостаточные объекты проверки для отдельных `reviewer`.

Передай каждый объект отдельному reviewer-thread; reviewer выполняет единственный независимый проход по правилам checker.

После завершения используй статус и путь каждого назначенного `result` для продолжения приёмки.

Допускай в одном цикле задачи один первичный и не более четырёх повторных завершённых агрегированных проходов checker. Считай два child-thread режимов `requirements` и `technical` одним проходом `review-<M>`, а не двумя.

Лимит считай по итерациям `review-<M>`, отнесённым в `state.md` к текущему циклу: сквозной номер итерации в лимит не переносится, проходы прошлых циклов в него не входят, `stale` и `blocked` проходами не считаются.

### Immutable вход checker и recovery

Перед созданием любого reviewer атомарно подготовь `<TASK_DIR>/review-<M>/manifest`; он является единственным замороженным входом прохода и не изменяется после запуска reviewer.

Manifest фиксирует режим, репозитории, `BASE`/`CANDIDATE` Git trees, digest правил и evidence и абсолютные пути child- и aggregate-result; для `requirements-fix` после переписывания `BASE` включи `CHECKED_TREE`.
  Номер review и runtime-состояние в объект манифеста не входят: их отсутствие задаёт структура манифеста, а не сериализация.

Для каждого сочетания режима и репозитория вычисли отдельный `input_digest`, чтобы одинаковый результат можно было переиспользовать независимо от других репозиториев:

1. Удали из объекта манифеста ключи `input_digest`, `progress` и `result`.
2. Сериализуй остаток `json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))` и захешируй UTF-8 SHA-256.

Запиши manifest во временный файл в том же каталоге, проверь snapshots, ancestry либо `CHECKED_TREE` по правилу режима, clean worktrees, правила и evidence, затем атомарно переименуй его и только после этого запиши его путь в `state.md`.
  При несовпадении входов не запускай reviewer и не меняй `checked_candidate`: сдвиг snapshot возвращает задачу в `implement`, повреждённый manifest, evidence или result - в `accept` или `blocked` с причиной и `next`.

Переиспользуй только завершённый child-result с тем же `input_digest`, подтверждёнными final snapshot и SHA-256 evidence.
  При recovery собери aggregate-result из таких child-result и выполни protocol-gate без reviewer, если aggregate-result отсутствует; запускай reviewer только для отсутствующих или изменившихся режимов и репозиториев.
  Для принятых открытых целей запускай только `requirements-fix` с `checked_candidate`, а не полный `requirements`/`technical`.

До открытия нового цикла проверь, что `status: completed` подтверждён принятым aggregate-result, завершёнными checker и protocol-gate, Git-финализацией, evidence и QA-комментарием.
  Иначе продолжи текущий цикл с последнего валидного состояния и не запускай полный аудит.

### Подготовка и запуск checker

Если цикл `extend` открыт только тредами MR, которые не меняют цель, scope и критерии приёмки, первичный проход составь из `requirements-fix` и `technical`, без `requirements`.
  Целями `requirements-fix` служат выбранные треды, `BASE` - `checked_candidate` прошлого цикла; `technical` проверяет `base..candidate` текущего цикла.

1. Проверь наличие перечня итераций цикла, `checked_candidate`, предыдущих manifest и result в `state.md`; валидные результаты с совпадающим `input_digest`, final snapshot и SHA-256 evidence переиспользуй.
2. Перед созданием итерации проверь, исчерпан ли лимит завершённых проходов текущего цикла:
   - если лимит исчерпан, установи `blocked`, запиши в `state.md` перечень нерешённых блокеров или неподтверждённых устранений и первое действие в `next`, затем останови маршрут;
   - иначе перейди к шагу 3.
3. Заведи следующую итерацию `review-<M>`.
4. Назначь пути `progress` и `result` для режимов и aggregate-result; включи их в manifest, атомарно проверь его до reviewer и передай только путь manifest, `input_digest`, режим и `result`.
5. Собери в manifest mode-specific входы по правилам режимов; для `requirements-fix` используй `BASE = checked_candidate`, только принятые открытые цели и, если `BASE` уже не предок `CANDIDATE`, `CHECKED_TREE = BASE^{tree}`.
6. Перед новым проходом подтверди обязательные проверки и evidence текущего clean candidate; при изменении дерева верни задачу в `implement` и повтори затронутые проверки.
7. Запусти только отсутствующие режимы и репозитории, одновременно для первичных `requirements`/`technical` и отдельно для `requirements-fix`; неизменившиеся результаты переиспользуй.
8. Дождись запущенных thread, прочитай result и собери aggregate-result и protocol-gate из полного набора; отсутствие только aggregate-result не запускает reviewer.
9. При `stale`, несовпадении manifest, отсутствии result, `failed` или `blocked` не обновляй `checked_candidate`; сдвиг snapshot верни в `implement`, остальные причины запиши как `blocked` с первым действием в `next`.

Выполни общий protocol-gate после получения всех обязательных результатов:

1. Объедини кандидатов всех запущенных наборов и сохрани их источник.
2. Отбрось один раз кандидатов с confidence `Вероятно`.
3. Проверь scope, включая предварительные `out-of-scope` из requirements и технические кандидаты без task-контекста.
4. Выполни общую дедупликацию по реестру.
5. Проверь наличие кандидатов:
   - при отсутствии заверши gate без countercheck;
   - при наличии:
     1. Передай countercheck immutable снимки, кандидатов, task-контекст, применимые правила и evidence.
     2. Поручи countercheck только поиск опровержения каждого кандидата и запрети ему проводить новое полное ревью или менять файлы и Git.
     3. Запусти один независимый countercheck для объединённого списка.
6. Оставь только кандидатов со статусом `confirmed` из ответов `confirmed`, `rejected` или `unproven`.

После protocol-gate выполни финализацию прохода:

1. Запиши в агрегированный `result` следующие данные:
   - `input_digest`, режим, запущенные и переиспользованные наборы проверок, проверенные диапазоны и репозитории;
   - состояния всех child-проходов, итоговое состояние `completed`, `stale` или `blocked` и рекомендацию `accepted` или `revision-required`;
   - решения scope и дедупликации, подтверждённые countercheck findings с источниками, результаты целей и открытые вопросы.
2. Перечитай записанный `result`. Если он нечитаем или не совпадает с manifest, установи `blocked` и останови финализацию.
3. Вычисли по итоговой классификации подтверждённых открытых блокеров всех репозиториев и всех запущенных наборов `score = 2 * High + Medium`.
4. Внеси итерацию с её итогом и score в `state.md`.
5. Сохрани проверенный `CANDIDATE` по каждому репозиторию как его новый `checked_candidate`.
6. Сопоставь подтверждённые findings, открытые вопросы и результаты целей текущего прогона с каноническим реестром по правилу дедупликации.
7. Обнови существующие записи и назначь ID только новым проблемам.
8. Прими итоговое решение по реестру.

Со второго прохода считай результат улучшением, только если score уменьшился и число `High` не выросло; результат без блокеров принимай без сравнения.

Откатывай коммиты последнего пакета доработки отдельным `git revert` только когда доказано, что этот пакет создал новый блокер или повысил его severity; после отката реализуй альтернативу.
  Иначе сохрани полезные исправления и не выполняй автоматический откат.

Открытый блокирующий finding или существенный открытый вопрос возвращает задачу в `implement` внутри текущего цикла.

Обнови реестр, устрани все принятые блокеры одним пакетом, повтори проверки и commit, обнови `candidate`, затем определи их статус по текущему снимку и обязательным проверкам.

Если блокеров больше нет, продолжай приёмку без отдельного прохода checker.
  Если последний проход не дал улучшения, новый проход не запускай. Иначе запускай повторный проход, только когда текущего снимка и обязательных проверок недостаточно для итогового решения.

Неустранённый `Low` и неблокирующий вопрос оставь `open` до следующего цикла, если он будет: приёмку они не блокируют.
  Исключение - `Low`, нарушающий явное требование, критерий приёмки или обязательное правило (раздел "Реестр findings").
  Открытые `Medium+` и существенные открытые вопросы блокируют приёмку.

После итогового принятия и до сбора комментария для QA выполни Git-финализацию по [разделу "Результат" в `git-lifecycle.md`](references/git-lifecycle.md#результат).

После успешной Git-финализации собери комментарий для QA по разделу "Комментарий для QA" и покажи его пользователю.
  Повторно сверь manifest, aggregate-result, все обязательные child-result, Git, snapshots и evidence и только после этого атомарно установи `status: completed` и очисти `next`.
  При любой несогласованности сохрани `accept` или `blocked` с причиной и первым действием в `next`.
  Новый reviewer из-за этого не запускай.

Если задача выполнялась в отдельном task worktree, сразу после установки `status: completed` удали именно этот task worktree через `remove-task-worktree.sh` по разделу "Уборка деревьев" `git-lifecycle.md`; отдельная команда пользователя не нужна.
  Task-ветку всегда сохраняй локально и не предлагай её удаление.

## Описание результата

Запрос описания сделанного (отчёт заказчику, разбор для смежной команды, ответ о состоянии задачи) собирай по этому формату из текущего снимка задачи. Это внутреннее описание: оно называет координаты и адресовано тому, кто может открыть код.
  Комментарий для QA собирается иначе, см. следующий раздел.

1. Координаты: ключ задачи и перечень изменённых репозиториев, строка на репозиторий: имя, ветка, диапазон `base..candidate` и объём diff.
2. Суть: не более трёх строк о том, что изменилось по существу.
3. Изменения контракта: строка на изменение в виде `было: ...; стало: ...` с координатой. Несовместимое изменение помечай отдельно.
4. Данные и миграции: идентификатор миграции, её действие над существующими данными и обратимость.
5. Проверки: имя команды, её результат и координата сохранённого вывода. Невыполненную обязательную проверку называй невыполненной.
6. Вне scope и ограничения: строка на пункт, включая известные риски для проверяющего.

Каждое утверждение описания подтверждай координатой из снимка; непроверенное называй допущением. Аналитику, историю итераций и реестр findings и вопросов в описание не включай: их носители - `state.md` и каталоги итераций.
  Секреты и пути вне репозитория не публикуй. Само описание отдавай пользователю.

## Комментарий для QA

Комментарий для QA - обязательный шаг Accept. До итогового принятия его не готовь: в процессе могут измениться требования, `candidate` или реестр findings.

Адресат комментария - тестировщик, предмет - наблюдаемое поведение внешнего контракта.

Координаты кода, имена файлов, слоёв, функций и миграций в него не входят: проверяющий воспроизводит изменение через контракт, а не читает реализацию.

Источник - весь результат задачи: от `base` её первого цикла до текущего `candidate` каждого репозитория, а не диапазон одного цикла.

Комментарий всегда описывает задачу целиком: изменение, отменённое последующим циклом или не наблюдаемое снаружи, в него не включай.

Каждую уникальную пару `[METHOD] /path` выводи во всём QA-блоке не более одного раза.
  Если endpoint одновременно добавлен и доработан, не повторяй его в разных группах или строках: выбери одну группу по итоговому контракту и объедини в одной строке все его наблюдаемые изменения.
  Группы описывают уникальные единицы контракта, а не этапы или циклы работы.

Состав:

1. Целевой стенд, если проект его называет.
2. Изменения контракта, сгруппированные по виду: доработанные, добавленные, удалённые. Пустую группу не выводи.
3. На каждое изменение - единица контракта и суть изменения одной строкой, в терминах наблюдаемого поведения.
4. Несовместимое изменение помечай явно.
5. Недостаточно подтверждённое выноси отдельной строкой в конце как требующее уточнения, а не растворяй в описании изменений.

Форму разметки задаёт проектный слой: комментарий вставляется в трекер как есть, и его синтаксис принадлежит продукту трекера, а не этому документу.

Если у проекта есть шаблон, следуй ему дословно: прочитай шаблон перед сборкой и сверь с ним готовый текст. Не добавляй заголовки, группы и секции сверх шаблона.

Готовый комментарий выведи в сессию дословно одним блоком, пригодным для копирования целиком; пересказ, ссылка на файл и цитата по частям его не заменяют.

Непосредственно перед блоком выведи ключ задачи и перечень изменённых репозиториев: строка на репозиторий с веткой и диапазоном от `base` первого цикла до `candidate`. Внутрь блока перечень не входит.

В трекер комментарий не публикуй: вставка всегда остаётся ручным шагом человека.

## Завершение

Завершай задачу, когда требования и критерии подтверждены, обязательные проверки успешны, все обязательные checker-thread и protocol-gate завершены без `stale` или `blocked`, protocol принял итоговый реестр.
  Открытых блокирующих findings и существенных открытых вопросов нет.
  Локальный результат закоммичен, комментарий для QA собран и отдан пользователю, а `state.md` свёрнут по разделу "Состояние задачи" и содержит `status: completed`.

## Носители правил и состояния

Пользовательские предпочтения храни в `AGENTS.md`, актуальное состояние одной задачи - в её `state.md`, историю её итераций - в каталогах итераций.
  Порядок работы, scope задачи, итоговую классификацию и реестр findings и вопросов храни в `protocol`, независимую проверку findings одного прогона - в `checker`.

Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.
