# Протокол задачи

## Bootstrap

Перед первым действием протокола:

1. В первом shell-вызове protocol используй абсолютный путь, по которому загружен этот `SKILL.md`, подставь имя текущего CLI и выполни весь блок целиком:

   ```bash
   set -eu

   PROTOCOL_SKILL_FILE='<абсолютный путь загруженного protocol/SKILL.md>'
   PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
   PROTOCOL_SKILL="$(dirname "$(realpath "$PROTOCOL_SKILL_FILE")")"
   PROTOCOL_SRC="$(cd "$PROTOCOL_SKILL/../.." && pwd -P)"
   PROTOCOL_INSTRUCTIONS="$PROTOCOL_SRC/instructions"

   test -r "$PROTOCOL_INSTRUCTIONS/environment.md"
   test -r "$PROTOCOL_SRC/lib/skills_config.py"
   printf 'PROTOCOL_SKILL=%s\nPROTOCOL_SRC=%s\n' "$PROTOCOL_SKILL" "$PROTOCOL_SRC"
   cat "$PROTOCOL_INSTRUCTIONS/environment.md"

   PROTOCOL_AGENT_INSTRUCTIONS="$PROTOCOL_INSTRUCTIONS/agent-$PROTOCOL_AGENT.md"
   test ! -e "$PROTOCOL_AGENT_INSTRUCTIONS" || cat "$PROTOCOL_AGENT_INSTRUCTIONS"
   ```

2. Отсутствующий справочник исполнителя не блокирует маршрут. Сохрани выведенные `PROTOCOL_SKILL` и `PROTOCOL_SRC` как константы контекста сессии. Shell-переменные между вызовами не сохраняются: в каждом следующем shell-вызове присваивай нужным переменным сохранённые абсолютные значения в этом же вызове.

Протокол выполняется в подготовленном пользователем Git-репозитории и не инициализирует его. Репозиторий, содержащий сам `protocol`, не используй как каталог исполнения задачи.

## Вход и рабочий каталог

### С Jira URL

Для одного явного Jira URL сначала выполни `"$PROTOCOL_SKILL/scripts/resolve_issue.py" '<ISSUE_URL>'`. Resolver принимает абсолютный HTTP(S) URL с точным путём `/browse/<KEY>` и возвращает ключ, проект и разрешённые корни. Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.

### Без Jira URL

Без Jira URL используй текущий Git-репозиторий. Идентификатором служит один явный ключ из команды или текущей ветки. При конфликте или нескольких ключах спроси пользователя. Если ключа нет, выдели `common-N` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-common-task`.

Issue key проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр; `common-N` сохраняй как есть. Завершённую задачу не клонируй в `<KEY>-2`: при явной доработке добавь в её журнал новый цикл и верни состояние в `define`.

### Task worktree и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, выполни Branch-Sync и продолжай только в полученном `WORKTREE_ROOT`.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORKTREE_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORKTREE_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define. Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут. Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
3. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root` и используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`.

## Журнал задачи

Единственный обязательный runtime-файл — `<TASK_DIR>/task.md`. Храни в нём текущее состояние `define`, `implement`, `accept` или `completed`, номер цикла, `WORKTREE_ROOT`, task-ветку, `BASE`, актуальный `CANDIDATE`, цель, scope, требования, критерии приёмки, решения, findings, число завершённых проходов checker текущего цикла, score каждого прохода и результаты проверок.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии. Копируй источник в `<TASK_DIR>/inputs/` только когда без локального снимка нельзя воспроизвести решение; секреты не копируй.

Реестр findings в `task.md` является каноническим между прогонами checker. Protocol присваивает finding стабильный ID, хранит статус `open`, `resolved` или `rejected` и дедуплицирует записи по общей причине и нарушенному требованию или последствию; изменение формулировки либо координаты само по себе не создаёт новый finding.

Protocol принимает окончательное решение по каждому finding и может обоснованно изменить scope или severity либо отклонить finding как дубликат, малозначительный или не относящийся к задаче. Сохрани рекомендацию и классификацию checker, итоговое решение и конкретное обоснование с опорой на зафиксированные scope, требования, доказательства и достижимое последствие.

Статус ранее сохранённого finding определи по текущему снимку и доступным доказательствам. Отсутствие finding в рекомендации checker учитывай как сигнал, но само по себе оно не подтверждает ни наличие, ни устранение проблемы; отдельный прогон для закрытия не обязателен.

Не отклоняй и не снижай до неблокирующего подтверждённое нарушение явного требования, критерия приёмки или обязательного правила профиля либо policy-файла и не считай отсутствие доказательства устранением проблемы.

Перед переходом обнови `task.md`, затем немедленно продолжай следующее состояние. Остановись только на человек-гейте, блокере, конфликте требований или недоступной обязательной проверке.

## Define

Зафиксируй цель, scope, обязательные требования, безопасные допущения и наблюдаемый критерий успеха. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `task.md`. Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы один high-risk критерий:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен содержать инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. Если требуется архитектурное решение, создай `<TASK_DIR>/adr.md` с вариантами, выбранным решением и последствиями, а в `plan.md` укажи ссылку на ADR. Перед Implement передай план пользователю на человек-гейт и дождись явного подтверждения.

Перед переходом в `implement` зафиксируй текущий полный SHA `HEAD` как неизменный `BASE` текущего цикла.

## Implement

Перед первым изменением прочитай отдельные правила Implement и их приоритет, явно названные применимыми профилями, и разреши конфликты по этому приоритету. Затем выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать требованию; контракты вне scope сохраняются.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения. До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`; после merge базы повтори prepare и все проверки. Выполни запланированные проверки и read-only project verify, если он задан профилем.

После успешных проверок создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `CANDIDATE`, сверь `BASE..CANDIDATE` с требованиями и переведи задачу в `accept`. Файл вне Git хешируй SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Убедись, что `HEAD == CANDIDATE`, task-ветка верна, worktree чист и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256. Прочитай отдельные правила Accept и их приоритет, явно названные применимыми профилями.

В одном цикле задачи допускается один первичный и не более одного повторного завершённого прохода checker. Учитывай все уже завершённые проходы текущего цикла; `stale` и `blocked` проходами не считаются. Если счётчика ещё нет в `task.md`, перед действием восстанови его по сохранённым результатам текущего цикла. Перед запуском checker сверь счётчик в `task.md`; после двух завершённых проходов новый не запускай.

Для текущего прохода назначь отдельные абсолютные пути `progress` и `result` внутри `TASK_DIR`. Сформируй и передай checker самодостаточный объект проверки: `WORKTREE_ROOT`, `BASE`, `CANDIDATE`, scope, требования, критерии, применимые профили, policy-файлы, правила Accept и их приоритет, условный `plan.md`, обязательные внешние evidence-файлы и их SHA-256, а также пути `progress` и `result`. Runtime-историю и реестр findings не передавай.

После получения состояния завершения прочитай переданный `result`; отсутствующий или нечитаемый результат означает `blocked`. После рекомендации `accepted` или `revision-required` увеличь счётчик завершённых проходов, сопоставь findings текущего прогона с каноническим реестром по правилу дедупликации, обнови существующие записи и назначь ID только новым проблемам, затем прими итоговое решение по реестру.

Для каждого завершённого прохода вычисли по итоговой классификации подтверждённых открытых блокеров `score = 2 × High + Medium`. Со второго прохода считай результат улучшением, только если score уменьшился и число `High` не выросло; результат без блокеров принимай без сравнения. При отсутствии улучшения новый checker не запускай. Откатывай коммиты последнего пакета доработки отдельным `git revert` только когда доказано, что этот пакет создал новый блокер или повысил его severity; после отката реализуй альтернативу. Иначе сохрани полезные исправления и не выполняй автоматический откат.

Открытый блокирующий finding или существенный вопрос возвращает задачу в `implement`: сохрани реестр, устрани все принятые блокеры одним пакетом, повтори проверки и commit, обнови `CANDIDATE`, затем сам определи их статус по текущему снимку и обязательным проверкам. Если блокеров больше нет, продолжай приёмку без отдельного прохода checker. Повторный проход запускай только когда этих доказательств недостаточно для итогового решения. Если после двух завершённых проходов остаётся неподтверждённое устранение или открытый блокер, установи `blocked` с их конкретным перечнем вместо нового прохода. Оставшийся открытым `Low` сохраняй и считай неблокирующим, если применимый профиль не назначил соответствующему набору правил блокирующий приоритет.

`stale` возвращает задачу в `implement` для восстановления снимка; `blocked` останавливает маршрут.

После итогового принятия снова сверь `HEAD`, чистоту worktree и внешние SHA-256, затем установи `status: completed`. Task-ветка и worktree остаются локально; push, создание MR/PR и удаление worktree выполняются только по отдельной явной команде пользователя.

## Завершение

Задача завершена, когда требования и критерии подтверждены, обязательные проверки успешны, checker завершил проход без `stale` или `blocked`, protocol принял итоговый реестр, открытых блокирующих findings нет, локальный результат закоммичен и `task.md` содержит `status: completed`.

Пользовательские предпочтения храни в `AGENTS.md`, runtime одной задачи — в её `TASK_DIR`, порядок работы, scope задачи, итоговую классификацию и реестр findings — в `protocol`, независимую проверку findings одного прогона — в `checker`. Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.
