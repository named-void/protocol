# Протокол задачи

Каждый этап должен быть принят до начала следующего. Проверку через `checker`
выполняй только по явной политике этапа.

## Жёсткое правило прохождения

В начале работы создай в `task.md` журнал этапов 0–6. Значение `7` зарезервировано для терминального состояния `completed`. Каждую итерацию записывай по формату раздела «Журнал итераций»: две строки выполнения и, когда политика требует проверку, две строки проверки.

В каждый момент текущим является ровно один этап или терминальное состояние. Перед обязательной или активированной условной проверкой прочитай и примени skill `checker`. После принятия этапа сначала зафиксируй решение в `task.md`, затем переведи `task_stage.md` на следующий номер штатной командой. Если обязательный skill недоступен, журнал этапа неполон или машинный гейт не пропускает действие, остановись и сообщи о блокере.

В финальном отчёте перечисли этапы 0–6 по порядку и терминальное состояние `7 completed`.

## Обязательный каталог исполнения

После разрешения входа протокол выполняется в уже подготовленном пользователем
Git-репозитории. Не инициализируй репозиторий. Репозиторий, содержащий сам
`protocol`, не используй как каталог исполнения задачи.

### Вход по ссылке Jira

Если поручение содержит один явный URL задачи Jira, до проверки Git-каталога:

1. Запусти:

   ```bash
   "$AGENT_SKILLS_DIR/protocol/scripts/resolve_issue.py" '<ISSUE_URL>'
   ```

   Resolver принимает абсолютный HTTP(S) URL с точным путём `/browse/<KEY>`,
   проверяет host, формат ключа и его однозначный проектный маршрут по карте
   carrier, затем возвращает JSON с ключом, проектом и корнями проекта.
2. Остановись при неизвестном host или префиксе ключа, неоднозначном маппинге,
   отсутствующей карте или недоступном корне проекта. Не подбирай проект по
   текущему каталогу и не обходи домашний каталог.
3. Прочитай задачу через `adapter-issues`, используя разрешённый проектный
   периметр. Затем через confidence gate `adapter-vcs` определи один целевой
   checkout по данным задачи и GitLab. При нескольких равнозначных кандидатах
   попроси пользователя выбрать репозиторий.
4. Продолжай из выбранного checkout. Branch-Sync обязан найти существующую
   каноническую ветвь `<type>/<KEY>` локально или в `origin`; если её нет,
   действует штатное правило создания ветви.

При входе через `/protocol` без Jira URL используй текущий Git-репозиторий.

### Идентификатор задачи и Git-гигиена

В команде продолжения полный идентификатор задачи имеет приоритет. Голое число `N` означает задачу, каталог которой в текущем `<data-root>/tasks/` оканчивается на `-N`; продолжай только при единственном совпадении. Этап определяется по `<TASK_DIR>/task_stage.md` и читается из пользовательской команды только при явном указании контекста этапа.

Если пользователь явно поручил доработать задачу в состоянии `7 completed`, создай её редакцию. Идентификатор первой редакции — `<KEY>-2`, следующих — `<KEY>-3`, `<KEY>-4` и далее. Выбери номер на единицу больше максимального существующего номера редакции; исходную задачу и завершённые редакции не переоткрывай. Для первой редакции базой служит каноническая ветвь `<type>/<KEY>`, для следующей — каноническая ветвь предыдущей редакции. Тип ветви сохрани от базы. Исходный `<KEY>` остаётся ключом внешней задачи, а полный идентификатор редакции используется для runtime, ветвей, worktree и коммитов.

До начала этапа 0 из рабочего каталога целевого Git-репозитория:

1. Получи текущую ветку командой `git symbolic-ref --short HEAD`. Detached `HEAD` блокирует старт.
2. Извлеки идентификатор задачи из явной ссылки или текста поручения: issue key проверь по
   `issue_tracker.key_pattern` текущего carrier, его редакцию — по `<KEY>-<N>`, где `N >= 2`, а `common-N` — по `^common-[0-9]+$`. Если кандидатов несколько и
   один нельзя выбрать однозначно, спроси пользователя.
3. Независимо извлеки из имени текущей ветки issue key, его редакцию или `common-N` по тем же правилам. Несколько разных
   идентификаторов в ветке блокируют старт.
4. Если явный идентификатор и идентификатор ветки различаются, остановись и сообщи о конфликте. Issue key
   нормализуй в верхний регистр; `common-N` сохраняй как есть.
5. Перед созданием новой редакции проверь состояние `7` исходной задачи или предыдущей редакции и отсутствие выбранного полного идентификатора в runtime и Git; существующую незавершённую редакцию продолжай по её журналу. Если это не редакция и ключа нет ни в поручении, ни в ветке, выдели глобальный идентификатор командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-common-task`. Команда атомарно возвращает `common-<index>`; не подбирай индекс вручную и не переиспользуй пропуски.
6. Выполни Branch-Sync по `references/git-lifecycle.md` навыка и все дальнейшие действия веди в
   полученном worktree. Зафиксируй в `task.md` исходную ветвь, выбранный идентификатор и его
   источник (`input`, `branch`, `revision` или `common-index`), каноническую ветвь, ветвь исполнителя, базу и
   `WORKTREE_ROOT` — абсолютный путь целевого worktree.
7. После получения `WORKTREE_ROOT` определи проект и разреши применимые профили:
   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORKTREE_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORKTREE_ROOT"
   ```
   Ответ `- outside` означает работу вне известного проектного периметра: профили
   отсутствуют, документы другой карты не подставляй. Ошибка любой команды
   блокирует маршрут. Вывод `profiles` — обязательный набор входных инструкций,
   а не справочная подсказка: для каждой непустой строки проверь наличие файла
   (`test -f <путь>`) и полностью прочитай его до начала этапа 0. Отсутствующий
   или нечитаемый профиль блокирует маршрут.

   После чтения профилей разреши все явно указанные в них каталоги `policy`.
   Относительный путь к каталогу разрешай от корня проекта, полученного через
   `roots --project`; путь внутри названного профилем шаблона сохраняй как
   ссылку на этот проект, но не обходи остальное содержимое шаблона. Для каждого
   каталога `policy` проверь существование и доступность, перечисли все обычные
   файлы рекурсивно в стабильном лексикографическом порядке и полностью прочитай
   каждый файл до этапа 0. Отсутствующий каталог, файл или недоступное чтение
   блокирует маршрут. Пустой или не содержащий обычных файлов каталог не даёт
   права пропустить проверку его существования.

   Проектные профили и загруженные `policy`-файлы образуют обязательный слой
   правил с высоким приоритетом: применяй их выше общих навыков, технологических
   допущений и локальных эвристик. Системные инструкции и явные требования
   пользователя имеют приоритет. Сам проект шаблона читай только когда этого
   требует задача для проверки или реализации; его `policy` загрузи по правилам
   выше. При создании `task.md` зафиксируй абсолютные пути профилей и всех
   загруженных `policy`-файлов и держи их правила до завершения задачи.
   При передаче работы `checker` или сабагенту Acceptance передавай те же пути
   профилей и `policy`-файлов и требуй прочитать их; содержимое инструкций в
   другие артефакты не переписывай.

Разреши корень runtime штатной командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root`, где `PROTOCOL_SRC` получен по правилу `AGENTS.md` через физический target установленного симлинка. Создай для задачи каталог `<data-root>/tasks/<task>/`, где `<task>` — выбранный стабильный идентификатор. Зафиксируй абсолютные `DATA_ROOT` и `TASK_DIR` в `task.md` и используй их до завершения задачи. До начала этапа 0 в каталоге задачи должны существовать два файла:

- `<TASK_DIR>/task.md` — журнал задачи: цель, требования, решения и хронология итераций со ссылками на план, результаты и findings;
- `<TASK_DIR>/task_stage.md` — указатель на номер текущего этапа или терминальное состояние `7`.

### Машинный гейт этапа

Считай `<TASK_DIR>/task_stage.md` единственным источником текущего этапа. Файл должен содержать ровно `<N>\n`, где `N` — число от 0 до 7. Значения `0..6` обозначают этапы, `7` — завершённую задачу. Не определяй текущий этап по журналу, плану, пользовательской формулировке или памяти диалога.

Используй только `python3 "$AGENT_SKILLS_DIR/protocol/scripts/task_stage.py"`:

- `init "$TASK_DIR"` — единожды создать этап 0;
- `current "$TASK_DIR"` — определить этап при продолжении задачи;
- `describe "$TASK_DIR"` — получить номер, техническое имя и явную политику проверки этапа;
- `require "$TASK_DIR" N` — подтвердить этап непосредственно перед каждым действием его выполнения или проверки;
- `advance "$TASK_DIR" N` — атомарно перевести принятый этап `N` в `N+1`;
- `return-to-implementation "$TASK_DIR"` — атомарно вернуть Acceptance с этапа 6 на Implementation этапа 5 при подтверждённом finding `Medium+`.

При старте создай каталог задачи и выполни `init`. Не создавай и не изменяй `task_stage.md` вручную. Перед каждым действием этапа `N`, включая возобновление после паузы, выполни `require`, а перед началом этапа — `describe`. Ненулевой код любой команды означает блокер: не исправляй состояние догадкой и не продолжай этап.

После принятия этапа 0–5 сохрани решение в `task.md`, выполни `advance` с номером принятого этапа и `require` для следующего. Finding `Medium+` проверки Implementation возвращает результат в фазу выполнения без смены номера `5`. Если на Acceptance подтверждена проблема реализации, выполни `return-to-implementation`, затем `require 5`. После успешного Acceptance сохрани решение, выполни `advance 6` и `require 7`; состояние `7 completed` не выполняется и не проверяется.

Вводные данные из нескольких источников храни отдельно в `<TASK_DIR>/inputs/`: один источник — один файл со стабильным именем. В `task.md` для каждого источника фиксируй путь к файлу, происхождение, назначение и доступный маркер версии или состояния. Не дублируй содержимое источника в журнале. При повторном обращении к источнику проверь его актуальное состояние и зафиксируй изменение в журнале. Секреты и данные, непригодные для хранения из-за размера, формата или ограничений доступа, не копируй: создай вместо них файл-описатель с координатой источника и маркером состояния без чувствительного содержимого.

Возврат `6 → 5` начинает новый цикл Implementation от текущего проверенного коммита. Finding проверки внутри Implementation сохраняет номер `5` и начинает следующую итерацию того же этапа.

### Журнал итераций

Каждая строка начинается с фактического локального времени в формате `MM-DD HH:MM` без года и часового пояса,
затем содержит компактный идентификатор `<этап>-<итерация>-<событие>`, например `1-1-start`.
Каждая итерация содержит две строки выполнения:

```text
MM-DD HH:MM | E-N-start | вход: …; START: …; BASE: …
MM-DD HH:MM | E-N-result | результат: …; CANDIDATE: …
```

Для `check=required` и активированного `check=conditional` добавляй две строки проверки:

```text
MM-DD HH:MM | E-N-check-start | вход: …; checker: …
MM-DD HH:MM | E-N-check-result | решение: принят|возврат; findings: …
```

Первая строка каждой фазы перечисляет её вход, вторая фиксирует итог. Между фазами и соседними итерациями оставляй одну пустую строку. Подробности плана, результатов и findings храни в профильных артефактах; в строке журнала оставляй итог и ссылки. При возврате на доработку добавляй новую итерацию, сохраняя историю предыдущих.

Runtime-артефакты задачи должны быть актуальны и относиться к одной задаче. Изменения продукта должны входить в проверяемую Git-дельту этапа, когда этап меняет версионируемые файлы. При нарушении этого условия восстанови артефакты до продолжения протокола.

Перед запуском `checker` сохрани результат этапа и актуальный журнал в `<TASK_DIR>`. Если этап изменил версионируемые файлы, после предусмотренных локальных проверок создай кандидатный Git-коммит. Все версионируемые результаты этапа должны входить в `CANDIDATE`; относящиеся к этапу изменения в index или рабочем дереве блокируют проверку. Для каждого переданного в `checker` файла вне `CANDIDATE` вычисли SHA-256 и передай вместе с путём. После ответа сохрани эти SHA-256 в журнале с результатом проверки. Не создавай пустой или служебный коммит только ради runtime-журнала.

## Политика проверки

Политика части 2 задаётся явно для каждого этапа и не имеет значения по умолчанию:

| Этап | Имя | Проверка |
|---|---|---|
| 0 | `preflight` | `none` |
| 1 | `task-definition` | `none` |
| 2 | `discovery` | `required` |
| 3 | `adr` | `conditional` |
| 4 | `planning` | `required` |
| 5 | `implementation` | `required` |
| 6 | `acceptance` | `none` |
| 7 | `completed` | `none` |

Штатная команда `describe` должна вернуть ту же политику. Отсутствующее или неизвестное значение блокирует этап. `conditional` этапа ADR активируется, только если ADR создан; обоснование `ADR не требуется` принимается без части 2.

Политика `none` завершает этап после успешной фазы выполнения, `required`
требует вердикта `accepted` от `checker`, `conditional` применяет явно заданный
предикат этапа.

Для каждого проверяемого этапа зафиксируй `START` как последний коммит на входе
и установи `BASE = START`. Перед проверкой зафиксируй `CANDIDATE` как текущий
`HEAD`; для этапа без изменений версионируемых файлов он может совпадать с
`BASE`. Передай все три точки в `checker`, а после ответа сохрани возвращённый
`next_base` как новый `BASE`. Передай также пути и SHA-256 всех проверяемых
файлов, содержимое которых не входит в `CANDIDATE`.

### Обработка вердикта checker

Вердикт `checker` имеет значение `accepted` или `revision-required`;
переходами и доработкой управляет этот навык. При `revision-required`
зафиксируй findings в общем реестре, верни текущий этап в фазу выполнения,
после доработки создай новый `CANDIDATE` и повтори предусмотренную проверку.
`Low` сохраняй, но не блокируй ими переход.

Со второй проверяемой итерации Implementation сравни результат с предыдущей.
Для каждой итерации вычисли оценку подтверждённых блокирующих findings её
кандидатной дельты: `score = 2 × High + Medium`. Итерация улучшилась, только
если новый `score` меньше предыдущего и число `High` не увеличилось; результат
без `Medium+` принимай без сравнения.

При отсутствии улучшения зафиксируй регрессию и решение `откат`. Не меняя
номер этапа `5`, отмени коммиты регрессировавшей итерации отдельным
`git revert`, затем реализуй альтернативное решение с подсказкой:

> Не используй решения из откатанных коммитов. Учти findings: …

Не используй `git reset` и не переписывай историю. Первый finding
Implementation возвращает результат на доработку без сравнения и отката.

## Workflow протокола

Перед началом фазы выполнения (части 1) этапов 3–5 учти раздел «Главные правила» в `AGENTS.md`. На этапе 5 также учти: в тестах проверяй только контракт и существенные риски.

0. [Preflight](#preflight)
1. [Task Definition](#task-definition)
2. [Discovery](#discovery)
3. [ADR](#adr)
4. [Planning](#planning)
5. [Implementation](#implementation)
6. [Acceptance](#acceptance)
7. `Completed` — терминальное состояние, не этап.

## 0. Preflight

Проверить, что исходный каталог находится внутри подготовленного пользователем Git-репозитория,
`HEAD` указывает на существующий коммит, репозиторий не содержит сам `protocol`, Branch-Sync завершён и
целевой worktree доступен для выполнения задачи. Несоответствие блокирует Task Definition.

## 1. Task Definition

Зафиксировать цель, границы задачи и один проверяемый критерий успеха. Способ реализации фиксировать только при наличии соответствующего требования.

## 2. Discovery

Разделить известные факты, допущения и блокеры. Явно спросить только о неоднозначностях, которые заметно меняют поведение, объём или критерии результата. Безопасные допущения назвать и продолжить работу. Для каждого обязательного требования определить наблюдаемый результат.

Часть 2 проверяет общий результат Task Definition и Discovery: цель, scope, критерий успеха, факты, требования, допущения, блокеры и наблюдаемые результаты.

## 3. ADR

Создать ADR только для решения, которое меняет публичный контракт, владение данными, топологию компонентов или способ хранения. Зафиксировать инварианты, рассмотренные варианты, отказные сценарии, последствия выбора и условия пересмотра. Если таких решений нет, обосновать `не требуется`.

Если ADR создан, выполни условную часть 2. После её принятия обязателен человек-гейт, когда выполняется хотя бы один критерий значительного объёма:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- требуется миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, периода обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных модулях или подсистемах.

На человек-гейт передай выбранное решение, отклонённые варианты, затронутые компоненты и данные, схему внедрения и отката, основные риски. До явного подтверждения пользователя сохрани этап `3` и не начинай Planning. Решение пользователя зафиксируй в журнале перед переходом.

## 4. Planning

Создать обязательный `<TASK_DIR>/plan.md` с минимальным порядком работ и способом приёмки. Для каждого пункта указать зависимости, точные артефакты или пути, ожидаемый результат, конкретную команду или наблюдение для проверки и успешный исход. Отдельно зафиксировать критерии приёмки полного результата и способ подтверждения каждого из них. Покрыть обязательные требования, изменённое поведение и соразмерные риску отказные сценарии. Объект проверки этапа 4 — `plan.md`; `task.md` хранит журнал этапа и решение проверки.

После принятия результата Planning и перед переходом `4 → 5` зафиксируй в `task.md` полный SHA текущего `HEAD` как `IMPLEMENTATION_START`. Не изменяй его при итерациях этапа 5 и возвратах `6 → 5`.

## 5. Implementation

Выполнить минимальное корректное изменение по плану. Каждое содержательное изменение должно соответствовать требованию; контракты вне scope сохраняются. Для изменённого поведения по возможности сначала получить воспроизводимое отрицательное доказательство, затем положительное. Сохраняй строгость тестов, проверок и контрактов; дополнительную инфраструктуру вводи только по требованию или для доказанного риска.

Запустить предусмотренные планом локальные проверки. После их успешного завершения создать кандидатный Git-коммит и передать его в `checker`. Недоступность запланированной локальной проверки блокирует создание кандидата.

В конце фазы выполнения зафиксируй в `task.md` сверку плана с фактом:

- каждый пункт плана — выполнен, изменён или отклонён с обоснованием;
- запланированные артефакты — фактическая Git-дельта;
- запланированные проверки — команда, рабочий каталог, время начала и завершения, лог, код завершения, SHA кандидата и использование кеша;
- ожидаемые результаты — фактические доказательства;
- незапланированные изменения — перечень и обоснование.

Невыполненный пункт или отсутствующее доказательство блокирует часть 2. Передай `checker` принятые требования, `plan.md`, сверку плана с фактом, общий реестр findings и `START`, `BASE`, `CANDIDATE`. Часть 2 применяет общий контур проверки в режиме full без отдельного повторения его правил. Finding `Medium+` возвращает результат в фазу выполнения с тем же номером этапа `5`.

## 6. Acceptance

Проверь целостность снимка в `WORKTREE_ROOT`: `HEAD` должен совпадать с последним принятым `CANDIDATE`, `git status --short` должен быть пуст, а SHA-256 файлов вне Git — соответствовать зафиксированным значениям. Несоответствие блокирует Acceptance.

Поручи проверку критериев приёмки новому сабагенту с пустым контекстом. Передай `WORKTREE_ROOT`, `<TASK_DIR>`, `IMPLEMENTATION_START`, `CANDIDATE` и снимки файлов вне Git. Сабагент проверяет критерии из `plan.md` для результата `IMPLEMENTATION_START..CANDIDATE`; детали реализации не проверяет.

Для длительного Acceptance передай сабагенту отдельный файл progress и отдельный
файл итогового результата. В progress он записывает текущий этап сразу после
старта и не реже `thresholds.heartbeat_seconds`, в том числе во время долгого
инструментального вызова. Если progress не обновлялся в течение
`thresholds.heartbeat_seconds × thresholds.heartbeat_ping_multiplier`,
координатор отправляет один ping с просьбой обновить этап. Если обновления нет
до `thresholds.heartbeat_seconds × thresholds.heartbeat_dead_multiplier`,
независимый контур считается недоступным: вердикт — `blocked` или
`revision-required`, но не `accepted`. Ping не обновляет heartbeat и не
продлевает stale-порог. Итоговый файл создаётся или дописывается только после
завершения проверки; его mtime не заменяет heartbeat.

Если сабагент не подтвердил хотя бы один обязательный критерий, зафиксируй причину и выполни `return-to-implementation`.

После подтверждения всех обязательных критериев выполни локальную Git-интеграцию.

## Правило перехода

Если пользовательская команда означает продолжение задачи, после принятия текущего этапа немедленно начинай следующий. Остановись при обязательном человек-гейте, блокере, конфликте требований или недоступности обязательной проверки; причину зафиксируй в журнале задачи и сообщи пользователю.

Принимай этап после получения всех обязательных доказательств. Недоступное доказательство фиксируй как блокер текущего этапа.

Начинай Implementation после принятия этапов 0–4, а Acceptance — после принятия этапа 5.

Перед каждым переходом проверь, что `<TASK_DIR>/task.md` содержит запись о принятом текущем этапе. После перехода подтверди машинным гейтом номер следующего этапа. Несоответствие журнала, гейта и фактического состояния блокирует работу; не возвращай и не продвигай этап вручную.

Для продолжения или расширения завершённой задачи используй редакцию по правилу раздела «Идентификатор задачи и Git-гигиена» и укажи исходную задачу и её артефакты как вход.

Перед проверкой зафиксируй `CANDIDATE` как текущий `HEAD` и сохрани актуальный runtime-журнал. Кандидатный коммит обязателен только при наличии проверенного изменения версионируемых файлов. Сверь полный результат этапа с `CANDIDATE` и зафиксированными SHA-256 файлов вне него; неполный или изменившийся снимок блокирует проверку.

При подтверждённых findings `Medium+` часть 2 возвращает Implementation в фазу выполнения без смены номера этапа. Исполнитель изучает общий реестр и историю Git, устраняет замечания и создаёт новый коммит.

Коммит создавай после предусмотренной этапом локальной проверки результата.

## Завершение задачи

Задача завершена только после успешного Acceptance, полного журнала этапов 0–6 в `<TASK_DIR>/task.md`, перехода `6 → 7` и подтверждения значения `7` в `<TASK_DIR>/task_stage.md`: требования выполнены, критерии приёмки подтверждены, открытые findings `Medium+` отсутствуют, обязательные и активированные условные проверки приняты. При продолжении задачи значение `7` означает завершение и не запускает повторный Acceptance.

## Размещение правил и данных

- Пользовательские предпочтения и границы репозитория храни в `AGENTS.md`.
- Runtime-состояние, требования и решения одной задачи храни в `<data-root>/tasks/<task>/task.md`, вводные данные — в `inputs/`, остальные данные — в специализированных артефактах этого каталога.
- Порядок этапов, циклы доработки и откаты изменяй в `protocol`.
- Контуры проверки и классификацию findings изменяй в `checker`.
- Каждое правило размещай в самом узком слое, который владеет поведением.

Изменённое правило протокола применяй к последующим действиям. Уже принятые этапы пересматривай только по явной команде пользователя.
