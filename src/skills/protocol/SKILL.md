# Протокол задачи

## Bootstrap

Перед первым действием протокола:

1. В первом shell-вызове protocol используй абсолютный путь, по которому загружен этот `SKILL.md`, подставь имя текущего CLI и выполни весь блок целиком:

   ```bash
   set -eu

   PROTOCOL_SKILL_FILE='<абсолютный путь загруженного protocol/SKILL.md>'
   PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
   PROTOCOL_SKILL="$(dirname "$(realpath "$PROTOCOL_SKILL_FILE")")"
   PROTOCOL_SRC="$(cd "$PROTOCOL_SKILL/../.." && pwd -P)"
   PROTOCOL_INSTRUCTIONS="$PROTOCOL_SRC/instructions"

   test -r "$PROTOCOL_INSTRUCTIONS/environment.md"
   test -r "$PROTOCOL_SRC/lib/skills_config.py"
   printf 'PROTOCOL_SKILL=%s\nPROTOCOL_SRC=%s\n' "$PROTOCOL_SKILL" "$PROTOCOL_SRC"
   cat "$PROTOCOL_INSTRUCTIONS/environment.md"

   PROTOCOL_AGENT_INSTRUCTIONS="$PROTOCOL_INSTRUCTIONS/agent-$PROTOCOL_AGENT.md"
   test ! -e "$PROTOCOL_AGENT_INSTRUCTIONS" || cat "$PROTOCOL_AGENT_INSTRUCTIONS"
   ```

2. Отсутствующий справочник исполнителя не блокирует маршрут. Сохрани выведенные `PROTOCOL_SKILL` и `PROTOCOL_SRC` как константы контекста сессии. Shell-переменные между вызовами не сохраняются: в каждом следующем shell-вызове присваивай нужным переменным сохранённые абсолютные значения в этом же вызове.

Протокол выполняется в подготовленном пользователем Git-репозитории и не инициализирует его. Репозиторий, содержащий сам `protocol`, не используй как каталог исполнения задачи.

## Вход и рабочий каталог

### С Jira URL

Для одного явного Jira URL сначала выполни `"$PROTOCOL_SKILL/scripts/resolve_issue.py" '<ISSUE_URL>'`. Resolver принимает абсолютный HTTP(S) URL с точным путём `/browse/<KEY>` и возвращает ключ, проект и разрешённые корни. Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.

### Без Jira URL

Без Jira URL используй текущий Git-репозиторий. Задачу называет только команда: её ключ в роли дорабатываемой, Jira URL или URL merge request. MR однозначен — он относится к конкретной ветке, из имени которой и берётся ключ; разрешай его через `adapter-vcs`. Ключ, встреченный в прозе постановки, идентификатором не является: текст называет задачи по разным поводам и может назвать несколько. Команда задачу не назвала — остановись и спроси, какую дорабатываем; названо несколько кандидатов или ключ дан без роли — подтверди вычисленный ключ у пользователя до первого действия.

Каталог исполнения называет задачу сам, когда это task worktree: он создан под одну задачу и назван `<repo>-<KEY>`. Уточнения такой запуск не требует — получи ключ так:

```bash
source "$PROTOCOL_SKILL/../git-workflow/scripts/lib-git.sh"
task_key_from_worktree
```

Ненулевой код означает, что каталог не task worktree, и ключ остаётся за командой. Ключ каталога и ключ команды расходятся — остановись и подтверди у пользователя, какая задача дорабатывается.

Имя текущей ветки ключа не даёт: на ней репозиторий может стоять по любому поводу. Оно нужно только для сверки: когда task-ветка опознанной задачи выкачана здесь, Branch-Sync возвращает `current:` — это человек-гейт, спроси, отколоть worktree или вести доработку прямо в этой ветке (`git-lifecycle.md`).

Опознав задачу, прочитай её `state.md` и сам реши по правилу `Циклы и доработки`, продолжает ли поручение её — тогда это новый цикл той же задачи — или требует собственных требований и человек-гейта, тогда это отдельная задача с `origin` на неё. Этот выбор пользователь не делает и координат источника не перечисляет.

Задаче без своего ключа в трекере ключ выделяется от того, к чему она относится, а не из общей нумерации:

1. База — ключ источника, если он есть в удалённом git: задача той ветки или того MR, из которых выделена работа (`UPL-940`). Разрешай источник через `adapter-vcs`.
2. Источника в удалённом git нет — базой служит имя рабочего каталога репозитория (`ord-service`).

Индекс к базе выдели командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-task-key <база> --path "$WORK_ROOT"`: он продолжает максимальный уже видимый индекс этой базы — в каталогах задач, ветках, worktree и заголовках коммитов. Выделение идемпотентно до создания `TASK_DIR`, поэтому ключ занимает именно созданный каталог.

Issue key проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр. Производный ключ наследует регистр базы: `UPL-940-6` остаётся в верхнем, `ord-service-1` — в нижнем. Для доработки завершённой задачи не заводи ни клон `<KEY>-2`, ни второй `TASK_DIR`: доработку ведут циклы одного `state.md` (`Циклы и доработки`).

Контекст выделенной работы — `state.md` и итерации задачи из `origin`; читай их сам, а не по перечислению пользователя. Базу выделенной работы Branch-Sync определяет по `origin` (`git-lifecycle.md`), а не по ветке, на которой стоит репозиторий.

### Рабочее дерево и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, выполни Branch-Sync и продолжай только в полученном `WORK_ROOT`. Репозиторий, добавленный в scope позже, проходит Branch-Sync тогда же — по правилам того же файла.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORK_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORK_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define. Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут. Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
3. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root` и используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`.

## Состояние задачи

`TASK_DIR` — каталог `<key>`; ключ несёт он, поэтому имена внутри префикса не повторяют. Единственная точка агрегации — `<TASK_DIR>/state.md`. В нём только актуальное: состояние маршрута, координаты, определение задачи, реестр findings и указатели на итерации. История, обоснования и выводы прогонов живут в каталогах итераций; `state.md` на них ссылается, а не повторяет их.

`state.md` состоит из четырёх частей:

1. Состояние: `status` (`define`, `implement`, `accept`, `completed` или `blocked`), `task`, `next` — одна строка с первым действием следующей сессии, `cycle` и его `kind`, для каждого репозитория `work_root`, `branch`, `isolation` (`worktree` или `checkout`), `base`, `candidate` и `checked_candidate`, а при наличии — `mr`, `origin`, `spawned` и `evidence` с путём и SHA-256 каждого обязательного файла вне Git.
2. Задача: цель, scope, требования, критерии приёмки, источники. Одна на задачу, по циклам не раздваивается; меняет её только цикл вида `extend`.
3. Findings: строка на finding — идентификатор, severity, статус `open`, `resolved` или `rejected`, суть и итерация, где он заведён.
4. Итерации: строка на каталог итерации — её цикл и итог.

Этих четырёх частей достаточно, чтобы продолжить задачу в новой сессии: отдельный промпт возобновления не собирай, файлы прошлых итераций читай только под конкретный вопрос. Маршрут не обязан идти одной сессией. Внутри фазы держи один прогон — правила и код прочитаны один раз и дальше идут по цене чтения кэша; останавливай сессию на человек-гейте, где кэш истекает и так. Замер расхода фазы в `state.md` не клади: ни на одно решение маршрута он не влияет.

Перед переходом обнови `state.md`, затем немедленно продолжай следующее состояние. Остановись только на человек-гейте, блокере, конфликте требований или недоступной обязательной проверке.

### Итерации

Работа идёт итерациями двух видов; каждая — каталог в `TASK_DIR` со сквозной нумерацией, которая не сбрасывается между циклами:

- `implementation-<N>/` — итерация реализации: `notes.md` с решениями, обоснованиями и событиями, сохранённые выводы прогонов `*.log`, копии обязательных evidence-файлов вне Git;
- `review-<M>/` — итерация независимой проверки: `progress` и `result` одного прохода checker, которые ты назначаешь ему абсолютными путями.

События и решения фазы Define пиши в `notes.md` первой итерации реализации того же цикла: отдельного носителя у Define нет.

Задача не заводит других носителей состояния: ни файла стадии, ни общего каталога логов или приёмки, ни клона `<KEY>-2`, ни ручной префиксации имён номером цикла. Снимок входного источника, без которого нельзя воспроизвести решение, клади в `<TASK_DIR>/inputs/`; секреты не копируй. `plan.md` и `adr.md` принадлежат задаче и лежат в корне `TASK_DIR`.

Если у итерации или finding уже есть нативный идентификатор — iid MR, id discussion или комментария, ключ issue, — ссылайся на него вместо собственного. Собственный назначай только там, где нативного нет.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии.

### Циклы и доработки

Доработка принятого результата — изменение требований, findings независимого ревью, отложенная работа, просьба перепроверить готовое — открывает следующий цикл той же задачи и возвращает `status` в `define`. Цикл имеет один из двух видов, и вид определяет `base`:

- `extend` — цикл добавляет работу поверх принятого результата. `base` — полный SHA `HEAD` на входе в `implement`. Цикл 1 всегда `extend`.
- `recheck` — требования не меняются, перепроверяется уже принятый результат. Нового `base` не фиксируй: `base` цикла равен `base` того цикла, чей результат перепроверяется, иначе диапазон пуст и режим `full` не увидит ничего. Итерацию реализации такой цикл всё равно открывает: она не меняет код, а подтверждает снимок, догон базы и обязательные проверки перед проходом checker.

Отдельную задачу заводи, только когда работа требует собственных требований и собственного человек-гейта — другая подсистема, новая межсервисная зависимость, изменение чужого публичного контракта — или когда её нельзя принять вместе с текущим результатом. Во всех остальных случаях это цикл. Суффикс индекса означает именно такую выделенную работу со своей приёмкой; продолжение той же задачи он не означает никогда, поэтому клон `<KEY>-N` вместо цикла остаётся запрещённым. У выделенной задачи заполни `origin: <KEY> cycle <N>`, у исходной — `spawned` с ключом выделенной; связь обязана читаться в обе стороны без чтения прозы. Ветка выделенной задачи растёт от task-ветки источника, пока та не влита в базовую ветку проекта (`git-lifecycle.md`); фактическую базу запиши как `depends_on`.

### Реестр findings

Реестр findings в `state.md` является каноническим между прогонами checker. Protocol присваивает finding стабильный ID из одной сквозной серии на задачу, хранит его статус и дедуплицирует записи по общей причине и нарушенному требованию или последствию; изменение формулировки либо координаты само по себе не создаёт новый finding. Общая причина при другом нарушенном требовании или другом достижимом последствии даёт новый finding — в том числе когда прошлый finding с той же причиной уже закрыт как `resolved`.

Protocol принимает окончательное решение по каждому finding и может обоснованно изменить scope или severity либо отклонить finding как дубликат, малозначительный или не относящийся к задаче. Рекомендацию и классификацию checker, итоговое решение и конкретное обоснование с опорой на зафиксированные scope, требования, доказательства и достижимое последствие сохрани в итерации, породившей решение.

Статус ранее сохранённого finding определи по текущему снимку и доступным доказательствам. Отсутствие finding в рекомендации checker учитывай как сигнал, но само по себе оно не подтверждает ни наличие, ни устранение проблемы; отдельный прогон для закрытия не обязателен.

Не отклоняй и не снижай до неблокирующего подтверждённое нарушение явного требования, критерия приёмки или обязательного правила профиля либо policy-файла и не считай отсутствие доказательства устранением проблемы.

## Define

Зафиксируй цель, scope, обязательные требования, безопасные допущения и наблюдаемый критерий успеха. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `state.md`. Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы один high-risk критерий:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен содержать инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. Если требуется архитектурное решение, создай `<TASK_DIR>/adr.md` с вариантами, выбранным решением и последствиями, а в `plan.md` укажи ссылку на ADR. Перед Implement передай план пользователю на человек-гейт и дождись явного подтверждения.

Перед переходом в `implement` зафиксируй неизменный `base` текущего цикла по его виду (`Циклы и доработки`).

## Implement

Заведи следующую итерацию `implementation-<N>` и веди её `notes.md`. Перед первым изменением прочитай отдельные правила Implement и их приоритет, явно названные применимыми профилями, и разреши конфликты по этому приоритету. Затем выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать требованию; контракты вне scope сохраняются.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения. До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`; после merge базы повтори prepare и все проверки. Выполни запланированные проверки и read-only project verify, если он задан профилем.

После успешных проверок создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `candidate` цикла, сверь `base..candidate` с требованиями и переведи задачу в `accept`. Файл вне Git хешируй SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Убедись, что `HEAD == candidate`, task-ветка верна, рабочее дерево чисто и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256. Прочитай отдельные правила Accept и их приоритет, явно названные применимыми профилями.

В одном цикле задачи допускается один первичный и не более четырёх повторных завершённых проходов checker. Лимит считай по итерациям `review-<M>`, отнесённым в `state.md` к текущему циклу: сквозной номер итерации в лимит не переносится, проходы прошлых циклов в него не входят, `stale` и `blocked` проходами не считаются. Если перечня итераций цикла или `checked_candidate` в `state.md` ещё нет, перед действием восстанови их по сохранённым `review-<M>/result`. После пяти завершённых проходов текущего цикла новый не запускай.

Для первичного прохода передай checker режим `full`, сохранённый `base` цикла и текущий `candidate`. Для повторного прохода передай режим `fixes`, `base = checked_candidate`, текущий `candidate` и только принятые открытые блокеры и существенные вопросы как цели проверки. В обоих режимах передай `WORK_ROOT`, scope, требования, критерии, применимые профили, policy-файлы, правила Accept и их приоритет, условный `plan.md`, обязательные внешние evidence-файлы и их SHA-256. Runtime-историю и полный реестр findings не передавай.

Заведи следующую итерацию `review-<M>`, назначь проходу абсолютные пути `<TASK_DIR>/review-<M>/progress` и `<TASK_DIR>/review-<M>/result` и включи их в объект проверки.

После получения состояния завершения прочитай переданный `result`; отсутствующий или нечитаемый результат означает `blocked`. После рекомендации `accepted` или `revision-required` внеси итерацию с её итогом и score в `state.md`, сохрани проверенный `candidate` как новый `checked_candidate`, сопоставь findings и результаты целей текущего прогона с каноническим реестром по правилу дедупликации, обнови существующие записи и назначь ID только новым проблемам, затем прими итоговое решение по реестру.

Для каждого завершённого прохода вычисли по итоговой классификации подтверждённых открытых блокеров `score = 2 × High + Medium`. Со второго прохода считай результат улучшением, только если score уменьшился и число `High` не выросло; результат без блокеров принимай без сравнения. При отсутствии улучшения новый checker не запускай. Откатывай коммиты последнего пакета доработки отдельным `git revert` только когда доказано, что этот пакет создал новый блокер или повысил его severity; после отката реализуй альтернативу. Иначе сохрани полезные исправления и не выполняй автоматический откат.

Открытый блокирующий finding или существенный вопрос возвращает задачу в `implement` внутри текущего цикла: обнови реестр, устрани все принятые блокеры одним пакетом, повтори проверки и commit, обнови `candidate`, затем сам определи их статус по текущему снимку и обязательным проверкам. Если блокеров больше нет, продолжай приёмку без отдельного прохода checker. Повторный проход запускай только когда этих доказательств недостаточно для итогового решения. Если после пяти завершённых проходов остаётся неподтверждённое устранение или открытый блокер, установи `blocked` с их конкретным перечнем вместо нового прохода. Оставшийся открытым `Low` сохраняй и считай неблокирующим, если применимый профиль не назначил соответствующему набору правил блокирующий приоритет.

`stale` возвращает задачу в `implement` для восстановления снимка; `blocked` останавливает маршрут.

После итогового принятия снова сверь `HEAD`, чистоту рабочего дерева и внешние SHA-256, затем установи `status: completed` и очисти `next`. Task-ветка и её дерево остаются локально; push, создание MR/PR и удаление worktree выполняются только по отдельной явной команде пользователя и по правилам `git-lifecycle.md`.

## Завершение

Задача завершена, когда требования и критерии подтверждены, обязательные проверки успешны, checker завершил проход без `stale` или `blocked`, protocol принял итоговый реестр, открытых блокирующих findings нет, локальный результат закоммичен и `state.md` содержит `status: completed`.

Пользовательские предпочтения храни в `AGENTS.md`, актуальное состояние одной задачи — в её `state.md`, историю её итераций — в каталогах итераций, порядок работы, scope задачи, итоговую классификацию и реестр findings — в `protocol`, независимую проверку findings одного прогона — в `checker`. Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.
