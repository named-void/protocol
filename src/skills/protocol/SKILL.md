# Протокол задачи

## Режимы запуска

- Отдельное сообщение, которое после удаления внешних пробелов состоит ровно из `read-protocol`, запускает read-only подготовку общей protocol-сессии. Команда не входит в постановку задачи.
- В сессии, где ранее успешно выполнено `read-protocol`, сообщение, которое после удаления внешних пробелов состоит ровно из полного Jira URL вида `https://<host>/browse/<KEY>` или ключа `UPL-<code>`, запускает общий read-only маршрут локальной инвентаризации; для полного URL сохрани его как источник, для ключа сформируй канонический URL. Обычное выполнение задачи не начинай до анализа найденных артефактов и предложения дальнейшего действия; `/protocol` не требуется.
- Поручение с завершающим отдельным токеном `/protocol` маршрутизируй по URL-кандидатам:
  - Единственный URL-кандидат, прошедший GitLab MR resolver: read-only ревью MR.
  - Единственный URL-кандидат, прошедший Jira resolver: выполнение задачи с Jira URL.
  - URL-кандидатов нет: выполнение задачи по правилам «Без Jira URL».
  - Несколько URL-кандидатов или ошибка соответствующего resolver: блокировка маршрутизации.
- Токен `/protocol` не входит в постановку задачи.
- Упоминание `read-protocol` или `/protocol` внутри прозы, Jira URL внутри прозы, issue key и тематическое совпадение не активируют навык. Одиночный Jira URL без `/protocol` активирует навык только в сессии, где ранее успешно выполнен `read-protocol`.

## Bootstrap

Перед первым действием любого режима:

1. В первом shell-вызове protocol используй абсолютный путь, по которому загружен этот `SKILL.md`, подставь имя текущего CLI и выполни весь блок целиком:

   ```bash
   set -eu

   PROTOCOL_SKILL_FILE='<абсолютный путь загруженного protocol/SKILL.md>'
   PROTOCOL_AGENT='<имя текущего CLI, не имя оболочки>'
   PROTOCOL_SKILL="$(dirname "$(realpath "$PROTOCOL_SKILL_FILE")")"
   PROTOCOL_SRC="$(cd "$PROTOCOL_SKILL/../.." && pwd -P)"
   PROTOCOL_INSTRUCTIONS="$PROTOCOL_SRC/instructions"

   test -r "$PROTOCOL_INSTRUCTIONS/environment.md"
   test -r "$PROTOCOL_SRC/lib/skills_config.py"
   printf 'PROTOCOL_SKILL=%s\nPROTOCOL_SRC=%s\n' "$PROTOCOL_SKILL" "$PROTOCOL_SRC"
   cat "$PROTOCOL_INSTRUCTIONS/environment.md"

   PROTOCOL_AGENT_INSTRUCTIONS="$PROTOCOL_INSTRUCTIONS/agent-$PROTOCOL_AGENT.md"
   test ! -e "$PROTOCOL_AGENT_INSTRUCTIONS" || cat "$PROTOCOL_AGENT_INSTRUCTIONS"
   ```

2. Отсутствующий справочник исполнителя не блокирует маршрут. Сохрани выведенные `PROTOCOL_SKILL` и `PROTOCOL_SRC` как константы контекста сессии. Shell-переменные между вызовами не сохраняются: в каждом следующем shell-вызове присваивай нужным переменным сохранённые абсолютные значения в этом же вызове.

## Подготовка общих инструкций

В режиме `read-protocol` после Bootstrap прочитай карту `upl`, `$PROTOCOL_SKILL/references/git-lifecycle.md`, общие для `upl/services` проектный и технологический профили и все файлы каталога `<UPL_ROOT>/templates/templ-service/policy`. В самом конце этого чтения, восстановив сохранённый при discovery абсолютный `AGENT_SKILLS_DIR`, прочитай `$AGENT_SKILLS_DIR/adapter-issues/SKILL.md`, `$AGENT_SKILLS_DIR/adapter-vcs/SKILL.md` и `$AGENT_SKILLS_DIR/adapter-wiki/SKILL.md`. Выбери существующий `UPL_ROOT` из `project.roots`; отсутствующий обязательный файл или каталог блокирует подготовку.

Не читай issue, не вызывай адаптеры, не выполняй Branch-Sync, не выбирай сервис или checkout, не создавай task state и не меняй файлы или Git. После успешной загрузки кратко подтверди готовность и не переходи к выполнению задачи.

### Ревью GitLab MR

Выполняй `<MR URL> /protocol` в текущем thread. `mreviewer` сам запускает одну независимую контрпроверку кандидатов с `fork_turns=none` и выдаёт только подтверждённые findings. Human-gate или блокер ревью передай пользователю и продолжай тот же thread. Публикация comments, discussions или reviews требует отдельной команды `/external-write vcs-host ...`.

## Выполнение задачи

Выполняй задачу в подготовленном пользователем Git-репозитории. Если дорабатывается сам `protocol` (репозиторий, содержащий `PROTOCOL_SRC`), выполняй изменения только в его основном checkout на ветке `main`, без task-ветки и task worktree; для задачи в другом репозитории checkout, содержащий `protocol`, в каталог исполнения не включай.

## Вход и рабочий каталог

В protocol используй issue tracker только для чтения. Смена статуса issue относится к отдельному маршруту, который активирует точная команда `/external-write issue-tracker ...`; этот маршрут не входит в protocol.

### С Jira URL

При переходе в обычный старт используй `ISSUE_URL`, возвращённый resolver; он принимает полный Jira URL или issue key, возвращает нормализованные `url`, `key`, проект и разрешённые корни. Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.

### Локальная предмаршрутная инвентаризация после `read-protocol`

После Bootstrap передай исходное полное Jira URL или ключ `UPL-<code>` в `"$PROTOCOL_SKILL/scripts/resolve_issue.py"`. Сохрани из JSON-результата нормализованные `KEY`, `ISSUE_URL` и `project_roots`; для ключа URL формирует resolver из настроенного Jira host. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root`, но ничего не создавай и не меняй.

В read-only режиме проверь `<DATA_ROOT>/tasks/<KEY>/state.md` и соседние артефакты задачи, включая `status`, `next`, `work_root`, `branch`, `candidate`, `checked_candidate` и перечень итераций. В каждом доступном локальном checkout под корнями `project.roots` текущей карты проектов проверь `git worktree list --porcelain`, локальные ветки и remote-tracking refs с ключом задачи, а для текущего checkout и каждого найденного task worktree — `git status --short --branch`; отдельно зафиксируй `clean`, `dirty`, `detached` и наличие незакоммиченных изменений.

Собери для пользователя краткий инвентаризационный результат: найденные `TASK_DIR` и `state.md`, статусы задач, пути worktree, ветки, состояние деревьев, `next` и неоднозначности. До выбора пользователя не вызывай `adapter-issues` или `adapter-vcs`, не выполняй Branch-Sync, не создавай `state.md` или task worktree и не меняй файлы или Git.

Если найден один продолжаемый `state.md` со статусом `define`, `implement`, `accept` или `blocked`, предложи продолжить ту же задачу с указанными в нём `work_root`, `branch`, `status` и `next`, не создавая новый `TASK_DIR`. Если найден `status: completed`, предложи открыть следующий цикл той же задачи через существующий `state.md`, а не заводить `<KEY>-2`. Если найдено несколько кандидатов, отсутствует `state.md` при наличии worktree или состояние дерева не позволяет безопасно продолжить, покажи кандидатов и предложи варианты продолжения или восстановления; до явного выбора пользователя маршрут не продолжай.

Если локальных артефактов, веток и worktree с этим ключом не найдено, продолжи обычный старт по разделу «С Jira URL» с сохранённым `ISSUE_URL`, включая resolver, чтение issue и последующий выбор checkout.

### Без Jira URL

Для маршрута «Без Jira URL» сначала покажи пользователю текущий каталог через `pwd` и текущую ветку через `git branch --show-current` либо признак `detached HEAD`, дождись предварительного подтверждения и только после него используй текущий Git-репозиторий. Этот раздел не применяй к точному сообщению после успешного `read-protocol`, состоящему из полного Jira URL или `UPL-<code>`: для обеих форм действует локальная инвентаризация выше. После проверки по `issue_tracker.key_pattern` единственный issue key, упомянутый в постановке без признака, что он является источником, примером или связанной задачей, считай ключом дорабатываемой задачи; отдельного подтверждения не требуй.

- Если в постановке указан URL merge request, разреши его через `adapter-vcs`; для однозначного MR возьми ключ из его ветки.
- Ключ, явно обозначенный как источник, пример или связанная задача, задачей не считай.
- Если после исключения ключей-источников, примеров и связанных задач осталось несколько ключей, попроси выбрать одну дорабатываемую задачу.
- Если Jira URL не указан и ключ задачи не найден, остановись и уточни у пользователя, какую задачу дорабатывать.

Каталог исполнения называет задачу сам, когда это task worktree: он создан под одну задачу и назван `<repo>-<KEY>`; дополнительное название задачи от команды не требуется. Получи ключ так:

```bash
source "$PROTOCOL_SKILL/../git-workflow/scripts/lib-git.sh"
task_key_from_worktree
```

Ненулевой код означает, что каталог не task worktree, и ключ нужно получить из постановки. Ключ каталога и ключ, выбранный по постановке, расходятся — остановись и подтверди у пользователя, какую задачу дорабатывать.

Имя текущей ветки ключа не даёт: на ней репозиторий может стоять по любому поводу. Оно нужно только для сверки: когда task-ветка опознанной задачи выкачана здесь, Branch-Sync возвращает `current:` — это человек-гейт, спроси, отколоть worktree или вести доработку прямо в этой ветке (`git-lifecycle.md`).

Опознав задачу, прочитай её `state.md`, если файл существует, и по правилу `Циклы и доработки` реши, продолжает ли поручение эту задачу. Продолжение открывает новый цикл той же задачи, а собственные требования и собственный человек-гейт — отдельную задачу с `origin`. Отсутствующий `state.md` означает новую задачу; создай его после получения `TASK_DIR` и до Define. При неоднозначности, меняющей scope или приёмку, запроси подтверждение пользователя до фиксации состояния.

Задаче без своего ключа в трекере ключ выделяется от того, к чему она относится, а не из общей нумерации:

1. База — ключ задачи-источника, из которой работа выделена: задачи той ветки или того MR (`UPL-940`). Он берётся из `origin` выделенной работы. Ветка источника может быть ещё не запушена — на выбор базы это не влияет. Источник, названный MR, разрешай через `adapter-vcs`.
2. Базой служит имя рабочего каталога репозитория (`ord-service`), только когда источника нет вовсе: работа не выделена ни из какой задачи и `origin` у неё пуст.

Индекс к базе выдели командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-task-key <база> --path "$WORK_ROOT"`: он продолжает максимальный уже видимый индекс этой базы — в каталогах задач, ветках, worktree и заголовках коммитов. Выделение идемпотентно до создания `TASK_DIR`, поэтому ключ занимает именно созданный каталог.

Issue key проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр. Производный ключ наследует регистр базы: `UPL-940-6` остаётся в верхнем, `ord-service-1` — в нижнем. Для доработки завершённой задачи не заводи ни клон `<KEY>-2`, ни второй `TASK_DIR`: доработку ведут циклы одного `state.md` (`Циклы и доработки`).

Контекст выделенной работы бери из её `state.md` и итераций, указанных в `origin`; базу определяй Branch-Sync по `origin` (`git-lifecycle.md`), а не по текущей ветке.

### Рабочее дерево и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, выполни Branch-Sync и продолжай только в полученном `WORK_ROOT`. Репозиторий, добавленный в scope позже, проходит Branch-Sync тогда же — по правилам того же файла.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORK_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORK_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define. Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут. Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
3. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root` и используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`; отсутствующие каталог и `state.md` создай после Branch-Sync и до Define.
4. Убери деревья завершённых задач этого репозитория по разделу «Уборка деревьев» `git-lifecycle.md`. Шаг стоит здесь: `status` и `evidence` кандидата читаются из его `state.md` в `<DATA_ROOT>/tasks/`, а дерево текущей задачи уже занято Branch-Sync и под уборку не попадает.

## Состояние задачи

`TASK_DIR` — каталог `<key>`; ключ несёт он, поэтому имена внутри префикса не повторяют. Единственная точка агрегации — `<TASK_DIR>/state.md`. В нём только актуальное: состояние маршрута, координаты, определение задачи, реестр findings и существенных открытых вопросов, а также указатели на итерации. История, обоснования и выводы прогонов живут в каталогах итераций; `state.md` на них ссылается, а не повторяет их.

`state.md` состоит из четырёх частей:

1. Состояние: `status` (`define`, `implement`, `accept`, `completed` или `blocked`), `task`, `next` — одна строка с первым действием следующей сессии, `cycle` и его `kind`; для каждого репозитория — `work_root`, `branch`, `isolation` (`worktree` или `checkout`), `base`, `candidate`, `checked_candidate`, а при наличии — `mr`, `origin`, `spawned` и `evidence` с путём и SHA-256 каждого обязательного файла вне Git.
2. Задача: цель, scope, требования, критерии приёмки, источники. Одна на задачу, по циклам не раздваивается; меняет её только цикл вида `extend`.
3. Findings: строка на finding или существенный открытый вопрос — стабильный идентификатор, статус `open`, `resolved` или `rejected`, суть, доказательство либо недостающее доказательство и итерация, где запись заведена; finding дополнительно содержит severity.
4. Итерации: строка на каталог итерации — её цикл и итог.

Этих четырёх частей достаточно, чтобы продолжить задачу в новой сессии; отдельный промпт возобновления не собирай.

Историю и выводы прошлых итераций читай только под конкретный вопрос. Маршрут может продолжаться в нескольких сессиях.

Внутри каждой фазы выполняй один прогон; неизменившиеся правила и код повторно не перечитывай без конкретного вопроса. На человек-гейте завершай сессию.

Расход фазы в `state.md` не фиксируй: он не влияет на решения маршрута.

Перед каждым переходом обнови `state.md`; затем продолжи следующее состояние, если нет человек-гейта, блокера, конфликта требований или недоступной обязательной проверки.

### Итерации

Работа идёт итерациями двух видов; каждая — каталог в `TASK_DIR` со сквозной нумерацией, которая не сбрасывается между циклами:

- `implementation-<N>/` — итерация реализации: `notes.md` с решениями, обоснованиями и событиями, сохранённые выводы прогонов `*.log`, копии обязательных evidence-файлов вне Git;
- Храни в `review-<M>/` итерацию независимой проверки: для `requirements` отдельные `requirements/progress` и `requirements/result`, для `technical` отдельные `technical/progress` и `technical/result`, для `requirements-fix` отдельные `requirements-fix/progress` и `requirements-fix/result`; каждому режиму назначай свой checker-thread и пути `progress` и `result`, а в корне итерации храни агрегированный `result`.

При входе в Define создай первую итерацию `implementation-<N>` текущего цикла и веди в ней `notes.md`; отдельного носителя у Define нет.

Задача не заводит других носителей состояния: ни файла стадии, ни общего каталога логов или приёмки, ни клона `<KEY>-2`, ни ручной префиксации имён номером цикла.

Снимок входного источника, без которого нельзя воспроизвести решение, клади в `<TASK_DIR>/inputs/`; секреты не копируй.

`plan.md` и `adr.md` принадлежат задаче и лежат в корне `TASK_DIR`.

Если у итерации, finding или вопроса уже есть нативный идентификатор — iid MR, id discussion или комментария, ключ issue, — ссылайся на него вместо собственного. Собственный назначай только там, где нативного нет.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии.

### Циклы и доработки

Доработка принятого результата — изменение требований, findings или существенные вопросы независимого ревью, отложенная работа, просьба перепроверить готовое — открывает следующий цикл той же задачи и возвращает `status` в `define`. Цикл имеет один из двух видов, и вид определяет `base`:

- `extend` — цикл добавляет работу поверх принятого результата. `base` — полный SHA `HEAD` на входе в `implement`. Цикл 1 всегда `extend`.
- `recheck` — требования не меняются, перепроверяется уже принятый результат. Нового `base` не фиксируй: `base` цикла равен `base` того цикла, чей результат перепроверяется, иначе диапазон пуст и режимы `requirements` и `technical` не увидят изменений. Итерацию реализации такой цикл всё равно открывает: она не меняет код, а подтверждает снимок, догон базы и обязательные проверки перед проходом checker.

Отдельную задачу заводи только в двух случаях:

- Работа требует собственных требований и собственного человек-гейта: например, затрагивает другую подсистему, добавляет новую межсервисную зависимость или меняет чужой публичный контракт.
- Работу нельзя принять вместе с текущим результатом.

Во всех остальных случаях открывай цикл той же задачи. Суффикс индекса обозначает выделенную работу со своей приёмкой и никогда не заменяет цикл; клон `<KEY>-N` вместо цикла запрещён.

У выделенной задачи заполни `origin: <KEY> cycle <N>`, у исходной — `spawned` с ключом выделенной задачи; связь должна читаться в обе стороны без чтения прозы.

Ветка выделенной задачи растёт от task-ветки источника, пока та не влита в базовую ветку проекта (`git-lifecycle.md`); фактическую базу запиши как `depends_on`.

### Реестр findings

Реестр findings и существенных открытых вопросов в `state.md` является каноническим между прогонами checker.

Protocol присваивает каждой записи стабильный ID из одной сквозной серии на задачу и хранит её статус.

Дедуплицируй записи по общей причине и нарушенному требованию или последствию; изменение формулировки либо координаты само по себе не создаёт новый finding. Общая причина при другом нарушенном требовании или другом достижимом последствии даёт новую запись — в том числе когда прошлая запись с той же причиной уже закрыта как `resolved`.

Protocol принимает окончательное решение по каждому finding и существенному открытому вопросу и может обоснованно изменить scope, изменить severity finding или отклонить запись как дубликат, малозначительную или не относящуюся к задаче.

Сохрани в итерации, породившей решение, кандидатов и предварительную классификацию checker, итоговое решение и конкретное обоснование с опорой на зафиксированные scope, требования, доказательства и достижимое последствие.

Определи статус ранее сохранённого finding или вопроса по текущему снимку и доступным доказательствам. Учитывай отсутствие записи в результате checker как сигнал, но не считай его самостоятельным подтверждением наличия или устранения проблемы; отдельный прогон для закрытия не обязателен.

Не отклоняй и не снижай до неблокирующего подтверждённое нарушение явного требования, критерия приёмки или обязательного правила профиля либо policy-файла и не считай отсутствие доказательства устранением проблемы.

## Define

Для issue с типом `Bug` до фиксации scope и плана выполни разбор актуальной постановки:

1. Сохрани порядок и идентификаторы всех пунктов источника; составной пункт раздели только на независимые требования. Зачёркнутые пункты и фрагменты явно пометь как `исключён: зачёркнут`; не воспроизводи их, не выдавай по ним вердикт, не переноси их в требования или scope и не задавай о них вопросов. Если зачёркнута только часть пункта, анализируй оставшийся текст; если содержательного текста не осталось, пометь весь пункт как `исключён: зачёркнут` и пропусти его.
2. Каждый незачёркнутый пункт проверь отдельно по текущему снимку кода и контракта. Зафиксируй `Воспроизведение: подтверждено`, `не подтверждено`, `неприменимо` для требования о новом поведении либо `недостаточно данных` с точным названием недостающего доказательства.
3. По каждому незачёркнутому пункту вынеси итоговый вердикт `согласен` или `не согласен`. Используй `согласен`, только если утверждение о дефекте подтверждено либо пункт о новом поведении неприменим к воспроизведению и не противоречит актуальным требованиям, спецификациям, контрактам и правилам, применимым на Define. При неподтверждённом дефекте, недостатке данных или конфликте используй `не согласен`.
4. Обоснование `не согласен` сформулируй как самостоятельный комментарий к issue: назови отклоняемый пункт, условия и фактический результат проверки либо конфликтующее требование с координатой, объясни, почему пункт нельзя принять, и укажи минимально необходимое уточнение или исправление постановки. Не ссылайся на внутренний ход рассуждений и не требуй от читателя контекста из сессии.
5. Покажи пользователю весь список пунктов источника, включая исключённые, в формате `Пункт | Состояние | Воспроизведение | Вердикт | Обоснование`.
   - Для зачёркнутых пунктов укажи `исключён: зачёркнут`, `не выполнялось` и `не требуется`.
   - Для незачёркнутых пунктов укажи `Состояние: активен` и заполни воспроизведение, вердикт и обоснование.
   - Сохрани список и решение пользователя в `notes.md` первой итерации реализации текущего цикла.
   - Это человек-гейт: до явного подтверждения пользователя не фиксируй итоговые требования и не переходи в Implement. После подтверждения включи в scope и требования только незачёркнутые пункты с вердиктом `согласен`; пункты с вердиктом `не согласен` явно пометь как `исключён: отклонён`.

Зафиксируй цель, scope и единый набор обязательных требований с наблюдаемыми критериями проверки. Включай в него обязательные ограничения безопасности, совместимости, миграций, данных и применимых project/policy-правил; отдельной классификации обязательных требований по источнику или виду не вводи. Безопасные допущения, не меняющие обязательств, фиксируй отдельно. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Путь вида `/api/...`, указанный в задаче, относится к дорабатываемому сервису, если задача явно не говорит обратного. Сам по себе такой путь — координата контракта внутри этого сервиса: не считай его отдельным источником требований или указанием на другой компонент при Define.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `state.md`. Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы одно high-risk условие:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен конкретизировать выполнение уже зафиксированных требований: инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. План не добавляет требований к задаче. Если требуется архитектурное решение, создай `<TASK_DIR>/adr.md` с вариантами, выбранным решением и последствиями, а в `plan.md` укажи ссылку на ADR. Перед Implement передай план пользователю на человек-гейт и дождись явного подтверждения.

Перед переходом в `implement` зафиксируй неизменный `base` текущего цикла по его виду (`Циклы и доработки`).

## Implement

Используй созданную в Define итерацию `implementation-<N>` и веди её `notes.md`.

Перед первым изменением прочитай отдельные правила Implement и их приоритет, явно названные применимыми профилями, и разреши конфликты по этому приоритету.

Для HTTP JSON-входа до первого изменения сверяй [профиль HTTP/API](../../profiles/http-api.md): простые условия наличия или отсутствия поля по значению соседнего поля (`required_if`, `required_unless`, `excluded_if`, `excluded_unless`) объявляй в binding-тегах и проверяй до usecase; условия с несколькими альтернативами или нетривиальным сравнением значений, проверки коллекций, сущностей и бизнес-инварианты, которые нельзя однозначно выразить тегами, оставляй в domain/usecase. Binding не заменяет доменную защиту для не-HTTP вызовов; при дублировании сверяй одинаковые поле, код и смысл ошибки.

Перед первым изменением сверь в `notes.md` применимые обязательные требования и известные ограничения. Если для их выполнения нужен выбор реализации, зафиксируй его как рабочее решение без расширения scope, требований или критериев приёмки.

Затем выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать обязательному требованию; технические решения, примеры и порядок реализации сами по себе не становятся критериями приёмки. Контракты вне scope сохраняй.

Для issue с типом `Bug` в конце Implement добавь в `notes.md` текущей итерации секцию `Bug-Causal-Analysis`.

Включи отдельную запись по каждому незачёркнутому пункту Issue с вердиктом `согласен`; пункты, исключённые как `исключён: зачёркнут` или `исключён: отклонён`, перечисли отдельно без записи причинного анализа. Каждая запись содержит `Первопричина`, `Пропуск исходной задачей` и `Профилактика`. Заверши раздел до Accept.

Если подтверждённое техническое замечание из discussions требует доработки, до изменения реализации проверь, отражена ли его общая причина или нарушенное требование в применимых версионируемых правилах.

Если отражения нет, сначала добавь обобщённый проверяемый инвариант в самый узкий доступный для записи источник правил, охватывающий сценарий.

Перед записью сверь Git-статус его репозитория и не затрагивай чужие изменения. Не переноси отклонённые замечания, требования только конкретной задачи, неподтверждённые выводы и смысловые дубли. Проверяемый checkout MR остаётся read-only.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения.

До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`. После merge базы повтори prepare и все проверки.

Выполни запланированные проверки. Если профиль задаёт read-only project verify, выполни его. При ненулевом результате или предупреждении, требующем исправления, верни задачу в `implement`, устрани проблему и повтори весь затронутый набор проверок. Если проверка изменила рабочее дерево, проверь diff, прими только допустимые изменения и повтори зависимые проверки; не фиксируй evidence до получения стабильного clean candidate.

После успешных проверок и получения стабильного clean candidate создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `candidate` цикла, сверь `base..candidate` с требованиями и переведи задачу в `accept`. Хешируй файл вне Git SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Для каждого репозитория сверь, что его `HEAD == candidate`, task-ветка верна, рабочее дерево чисто и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256. Прочитай отдельные правила Accept и их приоритет, явно названные применимыми профилями.

Для issue с типом `Bug` передай checker секцию `Bug-Causal-Analysis` из `notes.md` как обязательный артефакт и критерий её полноты: отдельная запись по каждому незачёркнутому пункту Issue с вердиктом `согласен` с заполненными полями `Первопричина`, `Пропуск исходной задачей` и `Профилактика`; пункты, перечисленные в Define как `исключён: зачёркнут` или `исключён: отклонён`, причинного анализа не требуют.

Подготовь в маршруте checker самодостаточные объекты проверки для отдельных `reviewer`.

Передай каждый объект отдельному reviewer-thread; reviewer выполняет единственный независимый проход по правилам checker.

После завершения используй статус и путь каждого назначенного `result` для продолжения приёмки.

Допускай в одном цикле задачи один первичный и не более четырёх повторных завершённых агрегированных проходов checker. Считай два child-thread режимов `requirements` и `technical` одним проходом `review-<M>`, а не двумя.

Лимит считай по итерациям `review-<M>`, отнесённым в `state.md` к текущему циклу: сквозной номер итерации в лимит не переносится, проходы прошлых циклов в него не входят, `stale` и `blocked` проходами не считаются.

### Immutable вход checker и recovery

Перед созданием любого reviewer атомарно подготовь `<TASK_DIR>/review-<M>/manifest`; он является единственным замороженным входом прохода и не изменяется после запуска reviewer.

Manifest фиксирует режим, репозитории, `BASE`/`CANDIDATE` Git trees, digest правил и evidence и абсолютные пути child- и aggregate-result. Для каждого сочетания режима и репозитория вычисли `input_digest` по канонической сериализации его входов, исключив номер review, output paths и runtime-состояние, чтобы одинаковый результат можно было переиспользовать независимо от других репозиториев.

Запиши manifest во временный файл в том же каталоге, проверь snapshots, ancestry, clean worktrees, правила и evidence, затем атомарно переименуй его и только после этого запиши его путь в `state.md`. При несовпадении входов не запускай reviewer и не меняй `checked_candidate`: сдвиг snapshot возвращает задачу в `implement`, повреждённый manifest/evidence/result — в `accept` или `blocked` с причиной и `next`.

Переиспользуй только завершённый child-result с тем же `input_digest`, подтверждёнными final snapshot и SHA-256 evidence. При recovery собери aggregate-result из таких child-result и выполни protocol-gate без reviewer, если aggregate-result отсутствует; запускай reviewer только для отсутствующих или изменившихся режимов и репозиториев. Для принятых открытых целей запускай только `requirements-fix` с `checked_candidate`, а не полный `requirements`/`technical`.

До открытия нового цикла проверь, что `status: completed` подтверждён принятым aggregate-result, завершёнными checker и protocol-gate, Git-финализацией, evidence и QA-комментарием. Иначе продолжи текущий цикл с последнего валидного состояния и не запускай полный аудит.

### Подготовка и запуск checker

1. Проверь наличие перечня итераций цикла, `checked_candidate`, предыдущих manifest и result в `state.md`; валидные результаты с совпадающим `input_digest`, final snapshot и SHA-256 evidence переиспользуй.
2. Проверь перед созданием итерации, достигнут ли лимит пяти завершённых проходов текущего цикла:
   - при достижении лимита установи `blocked`, запиши в `state.md` перечень нерешённых блокеров и первое действие в `next`, затем останови маршрут;
   - при отсутствии лимита перейди к шагу 3.
3. Заведи следующую итерацию `review-<M>`.
4. Назначь пути `progress` и `result` для режимов и aggregate-result; включи их в manifest, атомарно проверь его до reviewer и передай только путь manifest, `input_digest`, режим и `result`.
5. Собери в manifest mode-specific входы по правилам режимов; для `requirements-fix` используй `BASE = checked_candidate` и только принятые открытые цели.
6. Перед новым проходом подтверди обязательные проверки и evidence текущего clean candidate; при изменении дерева верни задачу в `implement` и повтори затронутые проверки.
7. Запусти только отсутствующие режимы и репозитории, одновременно для первичных `requirements`/`technical` и отдельно для `requirements-fix`; неизменившиеся результаты переиспользуй.
8. Дождись запущенных thread, прочитай result и собери aggregate-result и protocol-gate из полного набора; отсутствие только aggregate-result не запускает reviewer.
9. При `stale`, несовпадении manifest, отсутствии result, `failed` или `blocked` не обновляй `checked_candidate`; сдвиг snapshot верни в `implement`, остальные причины запиши как `blocked` с первым действием в `next`.

Выполни общий protocol-gate после получения всех обязательных результатов:

1. Объедини кандидатов всех запущенных наборов и сохрани их источник.
2. Отбрось один раз кандидатов с confidence `Вероятно`.
3. Проверь scope, включая предварительные `out-of-scope` из requirements и технические кандидаты без task-контекста.
4. Выполни общую дедупликацию по реестру.
5. Проверь наличие кандидатов:
   - при отсутствии заверши gate без countercheck;
   - при наличии:
     1. Передай countercheck immutable снимки, кандидатов, task-контекст, применимые правила и evidence.
     2. Поручи countercheck только поиск опровержения каждого кандидата и запрети ей проводить новое полное ревью или менять файлы и Git.
     3. Запусти одну независимую countercheck для объединённого списка.
6. Оставь только кандидатов со статусом `confirmed` из ответов `confirmed`, `rejected` или `unproven`.

После protocol-gate запиши в агрегированный `result` `input_digest`, режим, запущенные и reused наборы проверок, проверенные диапазоны и репозитории, состояния всех child-проходов, итоговое состояние `completed`, `stale` или `blocked`, рекомендацию `accepted` или `revision-required`, решения scope и дедупликации, подтверждённые countercheck findings с источниками, результаты целей и открытые вопросы. Перечитай записанный `result`; нечитаемый результат или несовпадение с manifest означает `blocked`.

После завершения protocol-gate вычисли по итоговой классификации подтверждённых открытых блокеров всех репозиториев и всех запущенных наборов `score = 2 × High + Medium`.

После protocol-gate выполни финализацию, включая countercheck при наличии кандидатов:

1. Внеси итерацию с её итогом и score в `state.md`.
2. Сохрани проверенный `CANDIDATE` по каждому репозиторию как его новый `checked_candidate`.
3. Сопоставь подтверждённые findings, существенные открытые вопросы и результаты целей текущего прогона с каноническим реестром по правилу дедупликации.
4. Обнови существующие записи и назначь ID только новым проблемам.
5. Прими итоговое решение по реестру.

Со второго прохода считай результат улучшением, только если score уменьшился и число `High` не выросло; результат без блокеров принимай без сравнения.

При отсутствии улучшения новый checker не запускай.

Откатывай коммиты последнего пакета доработки отдельным `git revert` только когда доказано, что этот пакет создал новый блокер или повысил его severity; после отката реализуй альтернативу. Иначе сохрани полезные исправления и не выполняй автоматический откат.

Открытый блокирующий finding или существенный открытый вопрос возвращает задачу в `implement` внутри текущего цикла.

Обнови реестр, устрани все принятые блокеры одним пакетом, повтори проверки и commit, обнови `candidate`, затем определи их статус по текущему снимку и обязательным проверкам.

Если блокеров больше нет, продолжай приёмку без отдельного прохода checker. Повторный проход запускай только когда этих доказательств недостаточно для итогового решения.

Если после пяти завершённых проходов остаётся неподтверждённое устранение или открытый блокер, установи `blocked` с их конкретным перечнем вместо нового прохода.

Оставшийся открытым `Low` сохраняй как неблокирующий; открытые `Medium+` и существенные открытые вопросы блокируют приёмку.

После итогового принятия и до сбора комментария для QA выполни Git-финализацию по [разделу «Результат» в `git-lifecycle.md`](references/git-lifecycle.md#результат).

После успешной финализации собери комментарий для QA по разделу «Комментарий для QA», покажи его пользователю, повторно сверь manifest, aggregate-result, все обязательные child-result, Git, snapshots и evidence и только после этого атомарно установи `status: completed` и очисти `next`. При любой несогласованности сохрани `accept` или `blocked` с причиной и первым действием в `next`; новый reviewer из-за этого не запускай.

Task-ветка остаётся локально; push и создание MR/PR выполняются только по отдельной явной команде пользователя.

Сразу после показа QA-комментария, если задача выполнялась в отдельном task worktree, обязательно предложи удалить именно этот task worktree.

Это человек-гейт: по явной команде пользователя удаляй только этот task worktree через `remove-task-worktree.sh` по разделу «Уборка деревьев» `git-lifecycle.md`; task-ветку всегда сохраняй и не предлагай её удаление. Без команды task worktree убирает следующая доработка репозитория.

## Описание результата

Запрос описания сделанного — отчёт заказчику, разбор для смежной команды, ответ о состоянии задачи — собирай по этому формату из текущего снимка задачи. Это внутреннее описание: оно называет координаты и адресовано тому, кто может открыть код. Комментарий для QA собирается иначе — см. следующий раздел.

1. Координаты: ключ задачи, ветка, диапазон `base..candidate`, объём diff.
2. Суть: не более трёх строк о том, что изменилось по существу.
3. Изменения контракта: строка на изменение в виде «было → стало» с координатой. Несовместимое изменение помечай отдельно.
4. Данные и миграции: идентификатор миграции, её действие над существующими данными и обратимость.
5. Проверки: имя команды, её результат и координата сохранённого вывода. Невыполненную обязательную проверку называй невыполненной.
6. Вне scope и ограничения: строка на пункт, включая известные риски для проверяющего.

Каждое утверждение описания подтверждай координатой из снимка; непроверенное называй допущением. Аналитику, историю итераций и реестр findings и вопросов в описание не включай: их носители — `state.md` и каталоги итераций. Секреты и пути вне репозитория не публикуй. Само описание отдавай пользователю; публикация во внешнюю систему выполняется только по его явной команде.

## Комментарий для QA

Комментарий для QA — обязательный шаг Accept: собери его после итогового принятия и до перевода задачи в `completed`. До итогового принятия его не готовь: в процессе могут измениться требования, `candidate` или реестр findings.

Адресат комментария — тестировщик, предмет — наблюдаемое поведение внешнего контракта.

Координаты кода, имена файлов, слоёв, функций и миграций в него не входят: проверяющий воспроизводит изменение через контракт, а не читает реализацию.

Источник — весь результат задачи: от `base` её первого цикла до текущего `candidate` каждого репозитория, а не диапазон одного цикла.

Комментарий всегда описывает задачу целиком: изменение, отменённое последующим циклом или не наблюдаемое снаружи, в него не включай.

Каждую уникальную пару `[METHOD] /path` выводи во всём QA-блоке не более одного раза. Если endpoint одновременно добавлен и доработан, не повторяй его в разных группах или строках: выбери одну группу по итоговому контракту и объедини в одной строке все его наблюдаемые изменения; группы описывают уникальные единицы контракта, а не этапы или циклы работы.

Состав:

1. Целевой стенд, если проект его называет.
2. Изменения контракта, сгруппированные по виду: доработанные, добавленные, удалённые. Пустую группу не выводи.
3. На каждое изменение — единица контракта и суть изменения одной строкой, в терминах наблюдаемого поведения.
4. Несовместимое изменение помечай явно.
5. Недостаточно подтверждённое выноси отдельной строкой в конце как требующее уточнения, а не растворяй в описании изменений.

Форму разметки задаёт проектный слой: комментарий вставляется в трекер как есть, и его синтаксис принадлежит продукту трекера, а не этому документу.

Если у проекта есть шаблон, следуй ему дословно: прочитай шаблон перед сборкой и сверь с ним готовый текст. Не добавляй заголовки, группы и секции сверх шаблона.

Готовый комментарий выведи в сессию дословно одним блоком, пригодным для копирования целиком; пересказ, ссылка на файл и цитата по частям его не заменяют.

Ключ задачи и ветку назови рядом с блоком, а не внутри него.

В трекер комментарий не публикуй: вставка всегда остаётся ручным шагом человека.

## Завершение

Завершай задачу, когда требования и критерии подтверждены, обязательные проверки успешны, все обязательные checker-thread и protocol-gate завершены без `stale` или `blocked`, protocol принял итоговый реестр, открытых блокирующих findings и существенных открытых вопросов нет, локальный результат закоммичен, комментарий для QA собран и отдан пользователю, а `state.md` содержит `status: completed`.

Пользовательские предпочтения храни в `AGENTS.md`, актуальное состояние одной задачи — в её `state.md`, историю её итераций — в каталогах итераций, порядок работы, scope задачи, итоговую классификацию и реестр findings и вопросов — в `protocol`, независимую проверку findings одного прогона — в `checker`. Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.
