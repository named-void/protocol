# Протокол задачи

## Bootstrap

Перед первым действием протокола:

1. Разреши физический корень protocol и каталог справочников через установленный skill-link:

   ```bash
   PROTOCOL_SKILL="$(realpath "$AGENT_SKILLS_DIR/protocol")"
   PROTOCOL_SRC="$(cd "$PROTOCOL_SKILL/../.." && pwd -P)"
   PROTOCOL_INSTRUCTIONS="$PROTOCOL_SRC/instructions"
   ```

2. До первой shell-команды, проверки, ожидания или файловой правки прочитай `$PROTOCOL_INSTRUCTIONS/environment.md` и справочник `$PROTOCOL_INSTRUCTIONS/agent-<имя-исполнителя>.md` текущего CLI. Имя оболочки не является именем CLI; отсутствующий справочник не блокирует маршрут. До этого чтения разрешены только symlink-aware обход каталога skills и вычисление путей выше.
3. Получи корень карт командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" projects-root`. Данные периметра находятся в `<projects-root>/<project>/`, локальные секреты — в `<project>/.data/config.toml`; секреты в Git не включай.

Протокол выполняется в подготовленном пользователем Git-репозитории и не инициализирует его. Репозиторий, содержащий сам `protocol`, не используй как каталог исполнения задачи.

## Вход и рабочий каталог

### Jira URL

Для одного явного Jira URL сначала выполни `"$PROTOCOL_SKILL/scripts/resolve_issue.py" '<ISSUE_URL>'`. Resolver принимает абсолютный HTTP(S) URL с точным путём `/browse/<KEY>` и возвращает ключ, проект и разрешённые корни. Неизвестный host, ключ, неоднозначный проект или недоступный корень блокирует маршрут.

Прочитай задачу через `adapter-issues`, затем через confidence gate `adapter-vcs` выбери один checkout по данным задачи и VCS. При нескольких равнозначных кандидатах попроси пользователя выбрать репозиторий.

### `/protocol`

Без Jira URL используй текущий Git-репозиторий. Идентификатором служит один явный ключ из команды или текущей ветки. При конфликте или нескольких ключах спроси пользователя. Если ключа нет, выдели `common-N` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" allocate-common-task`.

Issue key проверь по `issue_tracker.key_pattern` текущей карты и нормализуй в верхний регистр; `common-N` сохраняй как есть. Завершённую задачу не клонируй в `<KEY>-2`: при явной доработке добавь в её журнал новый цикл и верни состояние в `define`.

### Task worktree и правила проекта

1. Прочитай `$PROTOCOL_SKILL/references/git-lifecycle.md`, выполни Branch-Sync и продолжай только в полученном `WORKTREE_ROOT`.
2. Разреши проект и применимые профили:

   ```bash
   python3 "$PROTOCOL_SRC/lib/skills_config.py" project --path "$WORKTREE_ROOT"
   python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path "$WORKTREE_ROOT"
   ```

   Полностью прочитай каждый возвращённый профиль до Define. Ответ `- outside` означает отсутствие проектных профилей. Ошибка команды, отсутствующий или нечитаемый профиль блокирует маршрут. Явно названные профилем обязательные policy-файлы прочитай до действия, которое от них зависит; не обходи остальные каталоги проекта.
3. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root` и используй `<DATA_ROOT>/tasks/<task>/` как `TASK_DIR`.

## Журнал задачи

Единственный обязательный runtime-файл — `<TASK_DIR>/task.md`. Храни в нём текущее состояние `define`, `implement`, `accept` или `completed`, номер цикла, `WORKTREE_ROOT`, task-ветку, `BASE`, актуальный `CANDIDATE`, цель, scope, требования, критерии приёмки, решения, findings и результаты проверок.

Записывай только проверенные решения и результаты. Для события достаточно одной строки с локальным временем `MM-DD HH:MM`, действием и итогом. Не дублируй содержимое входных источников: сохрани координату и доступный маркер версии. Копируй источник в `<TASK_DIR>/inputs/` только когда без локального снимка нельзя воспроизвести решение; секреты не копируй.

Перед переходом обнови `task.md`, затем немедленно продолжай следующее состояние. Остановись только на человек-гейте, блокере, конфликте требований или недоступной обязательной проверке.

## Define

Зафиксируй цель, scope, обязательные требования, безопасные допущения и наблюдаемый критерий успеха. Спрашивай только о неоднозначности, заметно меняющей поведение, объём или результат.

Для обычной задачи запиши минимальный порядок работ и проверки прямо в `task.md`. Создай `<TASK_DIR>/plan.md`, когда решение меняет публичный контракт, владение данными, топологию компонентов или способ хранения либо выполняется хотя бы один high-risk критерий:

- затронуты два и более репозитория или независимо развёртываемых компонента;
- нужна миграция, backfill или преобразование существующих данных;
- внедрение требует нескольких фаз, обратной совместимости или согласованного переключения;
- решение состоит минимум из трёх независимо проверяемых блоков в разных подсистемах.

High-risk план должен содержать инварианты, отказные сценарии, порядок внедрения и отката, артефакты и способы проверки критериев. Если требуется архитектурное решение, добавь ADR с вариантами и последствиями. Перед Implement передай план пользователю на человек-гейт и дождись явного подтверждения.

Перед переходом в `implement` зафиксируй текущий полный SHA `HEAD` как неизменный `BASE` текущего цикла.

## Implement

Выполни минимальное корректное изменение. Каждое содержательное изменение должно соответствовать требованию; контракты вне scope сохраняются.

Если профиль задаёт mutating prepare, выполни его и прими только допустимые изменения. До финальных проверок один раз обнови task-ветку по правилам `git-lifecycle.md`; после merge базы повтори prepare и все проверки. Выполни запланированные проверки и read-only project verify, если он задан профилем.

После успешных проверок создай локальный commit по `git-workflow`, зафиксируй его полный SHA как `CANDIDATE`, сверь `BASE..CANDIDATE` с требованиями и переведи задачу в `accept`. Файл вне Git хешируй SHA-256 только когда он является обязательным доказательством критерия приёмки.

## Accept

Убедись, что `HEAD == CANDIDATE`, task-ветка верна, worktree чист и обязательные внешние evidence-файлы сохранили зафиксированный SHA-256. Затем прочитай и примени `checker`, передав `WORKTREE_ROOT`, `BASE`, `CANDIDATE`, требования, критерии, применимые профили и policy-файлы, `task.md`, условный `plan.md` и обязательные внешние evidence-файлы.

`revision-required` возвращает задачу в `implement`: сохрани findings, исправь результат, повтори проверки и commit, обнови `CANDIDATE`, затем полностью повтори Accept. `stale` также возвращает задачу в `implement` для восстановления снимка; `blocked` останавливает маршрут. `Low` сохраняй, но он не блокирует приёмку.

После `accepted` снова сверь `HEAD`, чистоту worktree и внешние SHA-256, затем установи `status: completed`. Task-ветка и worktree остаются локально; push, создание MR/PR и удаление worktree выполняются только по отдельной явной команде пользователя.

## Завершение

Задача завершена, когда требования и критерии подтверждены, обязательные проверки успешны, checker вернул `accepted`, открытых findings `Medium+` нет, локальный результат закоммичен и `task.md` содержит `status: completed`.

Пользовательские предпочтения храни в `AGENTS.md`, runtime одной задачи — в её `TASK_DIR`, порядок работы — в `protocol`, классификацию findings — в `checker`. Изменённое правило применяй к последующим действиям; уже завершённые действия пересматривай только по явной команде пользователя.
