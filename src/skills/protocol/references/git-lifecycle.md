# Жизненный цикл Git

## Branch-Sync

1. Засей конфигурацию командой `eval "$(python3 "$PROTOCOL_SRC/lib/skills_config.py" export-env)"`.
2. Для issue выбери тип из `vcs.branch_types`: явный тип приоритетен, `Bug` даёт `bugfix`, срочное исправление продуктивного сбоя — `hotfix`, остальное — `feature`. Для `common-N` используй `protocol`.
3. Выполни `"$PROTOCOL_SKILL/../git-workflow/scripts/sync-branch.sh" <task> <type>`. Если `origin` не настроен и проект намеренно локальный, добавь `AGENTS_LOCAL_ONLY=1`; настроенный `origin` этим флагом не обходи.
4. Ненулевой код блокирует маршрут. Из строки `created:`, `switched:` или `current:` получи task-ветку и `WORK_ROOT`, сверь `git status --short` и продолжай только в этом дереве.

Ветка `<type>/<task>` одна на задачу и на все её циклы. Номер цикла в имя ветки не добавляй: цикл живёт в `state.md`, а не в refs. Отдельной агентской или интеграционной ветки нет.

Новая ветка растёт из того, где стоит репозиторий: из текущей ветки, если она не проектная базовая, иначе из проектной базовой. Стоя на task-ветке другой задачи, доработку продолжают отсюда — иначе в базе не будет кода, ради которого её заводят. Выбранную базу скрипт печатает в строке `created:`; сверь её и запиши в `state.md`. Флага для этого нет и не нужно: чтобы взять проектную базовую ветку, переключи на неё репозиторий.

## Изоляция

Дерево выбирает скрипт, а не исполнитель. Изолированный worktree `<repo>-<task>` создаётся, только когда основной checkout занят: он не чист, стоит не на проектной базовой и не на самой task-ветке, или в репозитории уже есть другое зарегистрированное дерево. Свободный checkout получает ту же ветку на месте. Работа с ветки другой задачи поэтому всегда уходит в worktree, а её ветка остаётся выкачанной.

Изоляция свободного репозитория ничем не оплачена, а её цена наблюдаема: в свежем worktree нет gitignored артефактов, его удаление уносит evidence вне Git, кэш линтера холодный, а имя каталога протекает в логику прогонов. Disposable-проверка `verify` свой worktree создаёт сама и от этого выбора не зависит.

`AGENTS_TASK_WORKTREE=always` навязывает worktree по названной причине — например, пользователь параллельно работает в этом же репозитории. Полученное дерево и вид изоляции запиши в `state.md`.

## Обновление базы

Непосредственно перед финальными проверками цикла один раз выполни fetch `origin`, если remote настроен. Для существующей remote task-ветки:

- если `origin/<type>/<task>` является предком `HEAD`, продолжай;
- если `HEAD` является предком remote-ветки, выполни fast-forward;
- если ветки разошлись, выполни обычный merge remote-ветки, разреши конфликт и повтори prepare и все проверки.

В local-only режиме fetch пропускается. После обновления базы зафиксируй итоговый `base..candidate`; последующее внешнее обновление обрабатывается человеком перед разрешённым push.

Обновление базы принадлежит циклу, а не задаче: между циклами базовая ветка продвигается, поэтому каждый цикл выполняет его заново, а после него перепроверяет инварианты, зависящие от состояния базы. Первый такой инвариант — номера миграций: параллельная ветка могла занять номер, подтверждённый в прошлом цикле.

## Доработка после MR

Открытый MR: доработка идёт новыми коммитами в ту же ветку и приходит в тот же MR.

Влитый MR: ветка переиспользуется. Она целиком содержится в базовой, поэтому до фиксации `base` нового цикла подтяни её до базовой ветки fast-forward; тогда влитые коммиты становятся предками и `base..candidate` содержит только новую работу. Новый MR создаётся отдельной явной командой пользователя.

## Результат

Принятая task-ветка и её дерево остаются локально. Не удаляй worktree, не push ветку и не создавай MR/PR без отдельной явной команды пользователя.

Перед разрешённым удалением worktree скопируй обязательные evidence-файлы вне Git в каталог текущей итерации `implementation-<N>`: они живут только внутри worktree, и после удаления зафиксированные SHA-256 нечем сверить.
