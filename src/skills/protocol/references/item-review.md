# Разбор пунктов и маршрут MR

Процедура разбирает пункты двух источников: постановку issue с типом `Bug` на Define и незакрытые треды MR (раздел "Маршрут MR").

## Общий порядок

1. Составь перечень пунктов источника по правилам его раздела ниже.
2. Проверь каждый пункт отдельно по снимку источника с учётом требований задачи, применимых правил, спецификаций и контрактов.
3. Вынеси вердикт:
   - `согласен`: пункт подтверждён доказательством и не противоречит требованиям, правилам и контрактам;
   - `согласен с уточнением`, только для тредов MR: замечание верно по сути, но требует уточнения объёма, способа исправления или формулировки;
   - `не согласен`: пункт не подтверждён, противоречит требованиям, правилам или контракту либо для его проверки недостаточно данных.
4. Для вердиктов `не согласен` и `согласен с уточнением` сформулируй самостоятельный комментарий.
   Назови пункт, проверенные условия и фактический результат либо конфликтующее требование с координатой, а для уточнения - что именно уточняется и почему.
   Не ссылайся на внутренний ход рассуждений и не требуй от читателя контекста из сессии.
5. Покажи пользователю весь перечень таблицей в формате раздела источника. Это человек-гейт.
   После ответа сохрани перечень и решение пользователя в `notes.md` итерации реализации текущего цикла; для тредов MR момент записи задаёт раздел "Маршрут MR".

## Пункты Bug

Снимок - текущий код и контракт дорабатываемого сервиса.

1. Сохрани порядок и идентификаторы всех пунктов источника; составной пункт раздели только на независимые требования.
   Зачёркнутые пункты и фрагменты явно пометь как `исключён: зачёркнут`; не воспроизводи их, не выдавай по ним вердикт, не переноси их в требования или scope и не задавай о них вопросов.
   Если зачёркнута только часть пункта, анализируй оставшийся текст; если содержательного текста не осталось, пометь весь пункт как `исключён: зачёркнут` и пропусти его.
2. По каждому незачёркнутому пункту зафиксируй `Воспроизведение: подтверждено`, `не подтверждено`, `неприменимо` для требования о новом поведении либо `недостаточно данных` с точным названием недостающего доказательства.
3. Выноси `согласен`, только если утверждение о дефекте подтверждено либо пункт о новом поведении неприменим к воспроизведению и не противоречит актуальным требованиям, спецификациям, контрактам и правилам, применимым на Define.
   При неподтверждённом дефекте, недостатке данных или конфликте выноси `не согласен`.
4. Комментарий к `не согласен` адресуй в issue: объясни, почему пункт нельзя принять, и укажи минимально необходимое уточнение или исправление постановки.
5. Выведи таблицу `Пункт | Состояние | Воспроизведение | Вердикт | Обоснование`:
   - для зачёркнутых пунктов укажи `исключён: зачёркнут`, `не выполнялось` и `не требуется`;
   - для незачёркнутых пунктов укажи `Состояние: активен` и заполни воспроизведение, вердикт и обоснование.

После подтверждения гейта включи в scope и требования только незачёркнутые пункты с вердиктом `согласен`; пункты с вердиктом `не согласен` явно пометь как `исключён: отклонён`.

## Треды MR

Снимок - head MR. Тред - один discussion со всеми его комментариями в порядке публикации; обозначай его native id discussion.

Если тред уже разобран в прошлом заходе этой задачи и в нём нет новых комментариев, а затронутые им файлы не менялись между сохранённым и текущим head MR, оставь вердикт из `notes.md` без повторной проверки.

Комментарий к вердикту - ответ в тред. Выведи таблицу `Тред | Автор | Координата | Суть | Вердикт | Обоснование или ответ` и на гейте предложи выбрать треды для доработки.

## Маршрут MR

Маршрут запускает сообщение из одного URL GitLab MR после `read-protocol`.
  До подтверждения выбора тредов пользователем файлы, Git и `state.md` не меняй; исключение - временный worktree и артефакты раздела "Ревью MR без задачи".

### Поиск задачи

1. Разреши MR командой `python3 "$PROTOCOL_SKILL/scripts/resolve_mr.py" '<MR_URL>'`: она выводит JSON с `host`, `project_path`, `iid`, проектом `profile` и локальным checkout `local_path`.
   Код 2 блокирует маршрут. Код 3 означает, что локальный checkout не совпадает с MR; JSON при этом выведен, и для поиска задачи его достаточно.
2. Получи `DATA_ROOT` командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" data-root --project <profile>`, а source-ветку MR через `adapter-vcs`.
3. Найди задачи, у которых в `<DATA_ROOT>/tasks/*/state.md` поле `mr` указывает на этот MR либо `branch` совпадает с source-веткой MR.
   - Задача не найдена: перейди к разделу "Ревью MR без задачи".
   - Найдено несколько задач: покажи их и дождись выбора пользователя; дальше работай с выбранной задачей.
   - У задачи `status: blocked`: покажи блокер и `next` из её `state.md` и останови маршрут до решения пользователя.
   - У задачи другой статус: перейди к разбору тредов.

### Разбор тредов

1. Через `adapter-vcs` получи SHA head MR и все discussions с учётом pagination. Оставь незакрытые треды: discussions, которые можно закрыть и которые ещё не закрыты.
2. Разбери треды по общему порядку и разделу "Треды MR".

После подтверждения выбора открой доработку в задаче MR по её `status`:

- `completed`: открой следующий цикл вида `extend` по правилу "Циклы и доработки" `SKILL.md`; выбранные треды становятся источниками требований цикла, а подтверждённый выбор тредов заменяет человек-гейт Define этого цикла;
- `define`: добавь выбранные треды в источники требований текущего цикла;
- `implement` или `accept`: внеси выбранные треды в реестр findings текущего цикла со статусом `open` и severity, которую назначает protocol, и верни задачу в `implement`.

Открыв доработку, сохрани перечень, решение пользователя, SHA head MR и ответы в треды в `notes.md` итерации реализации текущего цикла; при `completed` это первая итерация нового цикла.
  В реестре findings ссылайся на треды по native id discussion.
  Дальше веди задачу с `work_root` и `branch` из её `state.md`, начиная с раздела "Рабочее дерево и правила проекта" `SKILL.md`.

### Правила из замечаний

Если подтверждённое техническое замечание из discussions MR требует доработки, до изменения реализации проверь, отражена ли его общая причина или нарушенное требование в применимых версионируемых правилах.

Если отражения нет, сначала добавь обобщённый проверяемый инвариант в самый узкий доступный для записи источник правил, охватывающий сценарий.

Перед записью сверь Git-статус его репозитория и не затрагивай чужие изменения. Не переноси отклонённые замечания, требования только конкретной задачи, неподтверждённые выводы и смысловые дубли. Проверяемый checkout MR остаётся read-only.

### Ревью MR без задачи

Ревью проверяет технические дефекты MR без требований задачи и дополняет tech-review: соответствие policy шаблона проверяет он, поэтому сюда policy не входит.
  Не читай issue tracker и wiki, не создавай `state.md` и `TASK_DIR`.

1. Если `resolve_mr.py` вернул код 3, остановись: снимку нужен локальный checkout `local_path` с совпадающим `origin`; репозиторий не клонируй.
2. Через `adapter-vcs` получи `diff_refs` MR и все discussions с учётом pagination. `BASE` - `diff_refs.base_sha`, `CANDIDATE` - `diff_refs.head_sha`.
3. Каталог ревью - `<DATA_ROOT>/mr-reviews/<имя local_path>-mr<iid>/`, проход - его следующая итерация `review-<M>`.
4. Подготовь снимок, не меняя ветки и рабочее дерево `local_path`:
   - если каталог `<local_path>-mr<iid>` уже существует, остановись и назови его пользователю: принадлежность каталога этому ревью не доказана, поэтому не удаляй и не переиспользуй его;
   - иначе выполни `git -C <local_path> fetch origin refs/merge-requests/<iid>/head` и `git -C <local_path> worktree add --detach <local_path>-mr<iid> <CANDIDATE>`.
5. Получи профили командой `python3 "$PROTOCOL_SRC/lib/skills_config.py" profiles --path <local_path>` и передай их в `rule_files`. Policy шаблона (`--policies`) не передавай.
6. Собери manifest режима `technical` по разделу "Manifest" `accept.md` с `work_root` временного worktree, запечатай его в `review-<M>/technical/manifest` и запусти reviewer.
7. Отбери кандидатов по разделу "Protocol-gate" `accept.md`; ключ задачи для сверки с открытыми MR бери из source-ветки или заголовка ревьюимого MR.
   Scope и реестра нет: вместо дедупликации по реестру исключи уже опубликованные в discussions замечания без нового доказательства.
   Итог отбора запиши в `review-<M>/result`.
8. Удали worktree, созданный на шаге 4, командой `git -C <local_path> worktree remove <local_path>-mr<iid>`, в том числе после `stale` или `blocked`.
9. Выдай подтверждённые findings нумерованным списком по убыванию severity: confidence, `path:line`, проблема, доказательство, последствие, правило и направление исправления.
   При чистом результате напиши `findings нет`; открытые вопросы перечисли отдельно.

Публикация findings в MR - отдельный маршрут по команде `/external-write vcs <действие> <цель>`.
