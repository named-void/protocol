# Проход checker

Проход готовит самодостаточный вход каждого режима и передаёт его отдельному reviewer; reviewer выполняет единственный независимый проход по правилам checker.
  После завершения используй статус и путь каждого назначенного `result` для продолжения приёмки.

## Лимит проходов

Допускай в одном цикле задачи один первичный и не более четырёх повторных завершённых проходов.
  Лимит считай по итерациям `review-<M>`, отнесённым в `state.md` к текущему циклу: сквозной номер итерации в лимит не переносится, проходы прошлых циклов в него не входят, `stale` и `blocked` проходами не считаются.

## Подготовка и запуск

Если цикл `extend` открыт только тредами MR, которые не меняют цель, scope и критерии приёмки, первичный проход составь из `requirements-fix` и `technical`, без `requirements`.
  Целями `requirements-fix` служат выбранные треды, `BASE` - `checked_candidate` прошлого цикла; `technical` проверяет `base..candidate` текущего цикла.

1. Проверь наличие перечня итераций цикла, `checked_candidate`, предыдущих manifest и result в `state.md`; переиспользуй результаты по разделу "Переиспользование и recovery".
2. Перед созданием итерации проверь, исчерпан ли лимит завершённых проходов текущего цикла:
   - если лимит исчерпан, установи `blocked`, запиши в `state.md` перечень нерешённых блокеров или неподтверждённых устранений и первое действие в `next`, затем останови маршрут;
   - иначе перейди к шагу 3.
3. Заведи следующую итерацию `review-<M>`.
4. Назначь пути `progress` и `result` режимов и aggregate-result `review-<M>/result`.
5. Собери черновик manifest каждого режима с mode-specific входами; для `requirements-fix` используй `BASE = checked_candidate`, только принятые открытые цели и, если `BASE` уже не предок `CANDIDATE`, `checked_tree = BASE^{tree}`.
6. Перед новым проходом подтверди обязательные проверки и evidence текущего clean candidate; при изменении дерева верни задачу в `implement` и повтори затронутые проверки.
7. Запечатай manifest каждого режима по разделу "Manifest" и передай reviewer только путь manifest, `input_digest`, режим и `result`.
8. Запусти недостающие режимы: первичные `requirements`/`technical` одновременно, `requirements-fix` отдельно.
9. Дождись запущенных reviewer, прочитай result и собери aggregate-result и protocol-gate из полного набора; отсутствие только aggregate-result не запускает reviewer.
10. При `stale`, несовпадении manifest, отсутствии result, `failed` или `blocked` не обновляй `checked_candidate`; сдвиг snapshot верни в `implement`, остальные причины запиши как `blocked` с первым действием в `next`.
    Повторный проход открывает новую `review-<M>` со всеми режимами: неизменившийся режим перезапечатай в ней и переиспользуй его child-result по разделу "Переиспользование и recovery".
    Aggregate-result повторного прохода пиши в `review-<M>/result` этой итерации.

## Manifest

Перед созданием reviewer запечатай для каждого режима `<TASK_DIR>/review-<M>/<режим>/manifest`: это единственный вход прохода, после запечатывания он не меняется.

Manifest - JSON-объект со следующими полями:

- `mode`;
- `repositories`: запись на репозиторий с `name`, абсолютным `work_root`, `base`, `candidate`, обязательными внешними `evidence` в виде списка `{"path": ...}`, а для `requirements-fix` после переписывания `BASE` также `checked_tree`;
- `rule_files`: абсолютные пути файлов и каталогов применимых правил в виде списка `{"path": ...}`. Содержимое правил не фиксируется: правила развиваются во время прохода, и результат по любой их версии действителен;
- `sources`: файлы задачи из `TASK_DIR`, кроме `state.md`, например снимки `inputs/` и `plan.md`, в виде списка `{"path": ...}`; их SHA-256 фиксируется, как у evidence;
- абсолютные `progress` и `result` режима;
- `targets`: непустой список целей, только для `requirements-fix`;
- mode-specific view по правилам режима; для `requirements` и `requirements-fix` view содержит scope, требования и критерии из части "Задача" `state.md`.

Номер review, цикл и runtime-состояние в manifest не включай: они меняют `input_digest` и мешают переиспользованию.

Запиши черновик manifest и запечатай его: `python3 "$PROTOCOL_SKILL/../checker/scripts/review_manifest.py" seal <черновик> <TASK_DIR>/review-<M>/<режим>/manifest`.
  Скрипт разрешает полные SHA и trees, проверяет `HEAD == candidate`, чистоту дерева, ancestry либо `checked_tree`, наличие правил, считает SHA-256 evidence и `sources` и `input_digest`, атомарно пишет manifest и отказывает, если файл уже есть.

- Код 0: запиши в `state.md` путь manifest и его `input_digest`.
- Код 3 (`stale`): не запускай reviewer и не меняй `checked_candidate`. По `reasons` сдвиг snapshot возвращает задачу в `implement`, отсутствующий или изменённый evidence либо источник - в `accept` или `blocked` с причиной и `next`.
- Код 2 (`blocked`): черновик повреждён, правило отсутствует или лежит в `TASK_DIR`, `state.md` указан в `sources`, либо manifest уже существует; установи `accept` или `blocked` с причиной и `next`.

## Переиспользование и recovery

Переиспользуй только завершённый child-result, чей manifest проходит `review_manifest.py verify <manifest>` с кодом 0.
  В новой итерации `review-<M>` дополнительно сверь его `input_digest` с `input_digest` запечатанного manifest того же режима.
  При recovery собери aggregate-result из таких child-result и выполни protocol-gate без reviewer, если aggregate-result отсутствует; запускай reviewer только для отсутствующих или изменившихся режимов.
  Для принятых открытых целей запускай только `requirements-fix` с `checked_candidate`, а не полный `requirements`/`technical`.

## Protocol-gate

Выполни общий protocol-gate после получения всех обязательных результатов:

1. Объедини кандидатов всех запущенных наборов и сохрани их источник.
2. Отбрось один раз кандидатов с confidence `Вероятно`.
3. Проверь scope, включая предварительные `out-of-scope` из requirements и технические кандидаты без task-контекста.
4. Выполни общую дедупликацию по реестру.
5. Проверь наличие кандидатов:
   - при отсутствии заверши gate без countercheck;
   - при наличии:
     1. Передай countercheck immutable снимки, кандидатов, task-контекст, применимые правила и evidence.
     2. Поручи countercheck только поиск опровержения каждого кандидата и запрети ему проводить новое полное ревью или менять файлы и Git.
     3. Запусти один независимый countercheck для объединённого списка.
6. Оставь только кандидатов со статусом `confirmed` из ответов `confirmed`, `rejected` или `unproven`.

## Финализация прохода

После protocol-gate выполни финализацию прохода:

1. Запиши в агрегированный `result` следующие данные:
   - `input_digest`, режим, запущенные и переиспользованные наборы проверок, проверенные диапазоны и репозитории;
   - состояния всех child-проходов, итоговое состояние `completed`, `stale` или `blocked` и рекомендацию `accepted` или `revision-required`;
   - решения scope и дедупликации, подтверждённые countercheck findings с источниками, результаты целей и открытые вопросы.
2. Перечитай записанный `result`. Если он нечитаем или не совпадает с manifest, установи `blocked` и останови финализацию.
3. Вычисли по итоговой классификации подтверждённых открытых блокеров всех репозиториев и всех запущенных наборов `score = 2 * High + Medium`.
4. Внеси итерацию с её итогом и score в `state.md`.
5. Сохрани проверенный `CANDIDATE` по каждому репозиторию как его новый `checked_candidate`, а tree этого `CANDIDATE` - как `checked_tree`.
6. Сопоставь подтверждённые findings, открытые вопросы и результаты целей текущего прогона с каноническим реестром по правилу дедупликации.
7. Обнови существующие записи и назначь ID только новым проблемам.
8. Прими итоговое решение по реестру.

Со второго прохода считай результат улучшением, только если score уменьшился и число `High` не выросло; результат без блокеров принимай без сравнения.

Откатывай коммиты последнего пакета доработки отдельным `git revert` только когда доказано, что этот пакет создал новый блокер или повысил его severity; после отката реализуй альтернативу.
  Иначе сохрани полезные исправления и не выполняй автоматический откат.

Продолжение после финализации выбирай по разделу "Решение после прохода" `SKILL.md`.
