# VCS host

Работает с Merge Request в хосте VCS по параметру `vcs_host.product` (по
умолчанию — `gitlab`): определяет host, project и IID из URL, текущего remote
или имени ветки, получает metadata, diff, discussions, review и pipeline
state. Используй для чтения MR, discussions, review comments, reviewer queues
и статуса MR текущей задачи.

## Границы (read-only инварианты)

- Обязательно: без точной команды `/external-write vcs-host <действие> <цель>` работай с хостом только в режиме read-only.
- Используй этот навык для доступа к хосту и операций с MR. Findings, severity, test gaps и качество реализации — вне этого адаптера: он собирает контекст, а не оценивает код.
- Push, создание, изменение и удаление branches, tags и releases разрешены только точной командой `/external-write vcs-host <действие> <цель>` и только для названных действия и цели.
- Не создавай, не редактируй и не удаляй comments, discussions или reviews; не выполняй resolve/reopen, approve/unapprove, merge/rebase; не меняй MR, labels, assignees, reviewers или milestone.
- Не запускай, не повторяй и не отменяй pipelines или jobs.
- Не переключай branch и не изменяй пользовательский worktree без явной необходимости. Никогда не перезаписывай и не очищай локальные изменения ради анализа MR.
- Запрос про MR или его обсуждения не разрешает изменяющие действия. Разрешение
  действует только на явно названное действие и конкретную цель; перед
  выполнением повторно проверь host, project, IID и итоговое изменение.

## Порядок работы

1. Определи host, project и IID из URL или текущего remote; не угадывай отсутствующие значения.

   Множество известных self-hosted хостов — `vcs_host.hosts` (подсказка-параметр): по нему выбираешь и авторизуешь хост, когда он не выводится из remote однозначно (например, при поиске проекта в confidence gate до появления локального checkout).
   Отличаешь «свои» хосты от `gitlab.com`.
   Это подсказка, а не жёсткий фильтр — хост из явного URL или remote приоритетен.
2. Получи metadata, diff, discussions/comments, reviewers, review state и
   pipeline status с учётом pagination.
3. Если вызывающему нужен зафиксированный снимок, синхронизируй base/head refs
   без checkout и верни точные SHA. Вывод о базе ветки, влитости или составе
   target делай после `git fetch` и по `origin/*`.
4. Разбирай JSON структурированным инструментом, например `jq` или
   `python3 -c`; крупный diff сохраняй в `$TMPDIR`.
5. Если доступ заблокирован, сообщи конкретную ошибку и повтори тот же
   workflow после устранения причины.

## Доступ к API

Файл доступа к API выбирается по `vcs_host.product`: `gitlab` —
`references/api-access.md` (`glab api`, fallback на `curl`). Для другого
значения продукта такого файла в репозитории нет: команды GitLab к нему не
применяй, а недостающий reference назови человеку как блокер конфигурации.

## MR по имени ветки

Когда пользователь просит показать MR, статус, discussions или комментарии «своей»/текущей задачи без явного MR URL — определи MR по имени source-ветки вместо запроса ссылки.


1. Запусти `"$AGENT_SKILLS_DIR/adapter-vcs/scripts/find-mr.sh" [branch]` — путь проходит через установленный симлинк; без аргумента берётся текущая checked-out ветка.
   Для явно названного issue key передай `<type>/<KEY>` (например `feature/ABC-635`).
   Host и project скрипт определяет из origin; ветку не угадывай, если она не определена однозначно.
2. Скрипт печатает один из трёх исходов:
   - `count=0` — MR для ветки ещё не создан; сообщи об этом и не создавай его.
   - `count=1 iid=<IID>` — используй этот IID дальше (metadata/diff/discussions/comments, «Порядок работы» и «Доступ к API»).
   - `count=<N>` со списком `iid=… state=… updated=…` — покажи кандидатов пользователю и дай выбрать; не выбирай сам.
   Коды выхода: `10` не определить ветку, `11` нет origin, `12` запрос к хосту не удался.
3. Дальше действуй по общим границам read-only и «Порядок работы»; это только способ определить IID без ссылки, а не отдельный набор прав.

## Определение рабочей директории для задачи (confidence gate)

Применимо, когда поручение содержит ровно один issue key и явное намерение
начать работу. Адаптер сам не создаёт ветку или worktree: он определяет
рабочую директорию проекта и передаёт её вызывающему.

Перед confidence gate разреши абсолютный путь `SKILLS_CONFIG`. При вызове из `protocol` используй `$PROTOCOL_SRC/lib/skills_config.py`. При самостоятельном вызове вычисли путь от абсолютного пути, по которому загружен этот `SKILL.md`:

```bash
ADAPTER_VCS_SKILL_FILE='<абсолютный путь загруженного adapter-vcs/SKILL.md>'
ADAPTER_VCS_SKILL="$(dirname "$(realpath "$ADAPTER_VCS_SKILL_FILE")")"
SKILLS_CONFIG="$(cd "$ADAPTER_VCS_SKILL/../../.." && pwd -P)/lib/skills_config.py"
test -r "$SKILLS_CONFIG"
```

Сохрани абсолютный `SKILLS_CONFIG` в контексте сессии и присваивай его в каждом shell-вызове, где он нужен.

1. Опознай проект по ключу задачи — `python3 "$SKILLS_CONFIG" project --key <KEY>`.
   Ответ `- outside` означает, что префикса нет ни в одной карте: остановись и спроси пользователя. Затем определи группу проектов в хосте по тому же префиксу через `dispatch.key_prefix_map` опознанной карты (префикс ключа → путь группы).
2. Прочитай issue через адаптер трекера. Сначала извлеки `components`, `labels` и явные ссылки на репозиторий — это самый надёжный маппинг.
3. Если маппинга нет, прочитай связанный эпик и примени к нему тот же поиск: поля, ссылки и компоненты.
   Затем обойди связанные issues, применяя те же правила к каждой; веди множество уже прочитанных ключей, чтобы не зациклиться, и не переходи к следующему источнику, если предыдущий дал однозначный репозиторий.
4. Получи разрешённые локальные корни командой `python3 "$SKILLS_CONFIG" roots --project <PROJECT>` и найди Git checkout только под ними; домашний каталог не обходи.
   Для каждого checkout нормализуй `origin` и сопоставь его с явными ссылками, components, labels и другими данными трекера.
   Содержимое репозитория используй только для подтверждения уже суженного кандидата.
5. Если данные трекера однозначно указывают на репозиторий и ему соответствует ровно один локальный `origin`, используй этот checkout как `<PATH>` без обращения к хосту VCS.
6. Только если подтверждённого локального кандидата нет или кандидатов несколько, найди проекты в хосте VCS: перечисли проекты разрешённой группы, сузь их по данным трекера и при необходимости проверь дерево репозитория.
   Сначала проверь авторизацию на хосте, определённом из локальных remote или `vcs_host.hosts`; не подменяй self-hosted хост публичным сервисом. Сопоставь выбранный remote с локальными `origin`, если checkout существует.
7. Оцени уверенность (confidence gate):
   - **Уверен** — данные issue, эпика или связанной задачи однозначно сопоставлены с одним локальным `origin` либо кандидат подтверждён хостом VCS. Используй локальный checkout, если он существует.
   - **Не уверен** — осталось несколько равнозначных кандидатов или нет подтверждаемого маппинга. Перед запуском покажи источники и кандидатов, попроси пользователя выбрать репозиторий и не угадывай по текущему каталогу.
8. Если выбранный репозиторий не заклонирован локально, целевой `<PATH>` выводи из первого разрешённого корня: `<project.roots[0]>/<хвост пути репозитория в remote>`.
   Нижняя часть `<PATH>` должна иметь с нормализованным путём репозитория в remote (без схемы/host и `.git`) общий завершающий путь не короче двух сегментов, включая имя репозитория; более длинное совпадение предпочтительно.
   Подтверждение на создание отсутствующей папки внутри корня проекта не требуется, если его снял проектный слой — карта проекта или её профиль; **вне корней проекта — обязательно получи подтверждение пользователя**.
