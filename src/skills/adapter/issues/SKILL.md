# Issue tracker

Работает с трекером задач по параметру `issue_tracker.product` (значение `jira` подразумевает остальные дефолты клиента — имя сервера и префикс инструментов; без явного `product` адаптер выключен, см. «Границы»): ищет и читает задачи, проекты, доски, спринты, комментарии и development info, а по прямому запросу изменяет конкретные объекты трекера.
Используй для URL задачи, issue key, JQL, явно указанного backlog внешнего трекера, спринта и полей трекера; не используй для самостоятельных команд `backlog` и «бэклог» навыков, MR хоста или wiki-страниц.

## Границы

- Обязательно: без точной команды `/external-write issue-tracker <действие> <цель>` работай с трекером только в режиме read-only. Обычная подкоманда `call` технически отклоняет инструмент, у которого MCP-сервер не объявил `annotations.readOnlyHint=true`; для разрешённой записи используй только отдельную подкоманду `write-call`.
- Режим `issue_tracker.product = "none"`: внешнего трекера нет — источник issue передаёт вызывающий (файл или текст поручения); читай только его, сетевых вызовов не делай, операции записи (transition, comment) не выполняются. Пустое значение `product` и отсутствие ключа выключают адаптер так же. Клиент в этом режиме отказывает кодом 2, не открывая соединения: код 2 означает выключенный адаптер, а не битые креды.
- Используй on-demand клиент `TRACKER="$AGENT_SKILLS_DIR/adapter-issues/scripts/tracker.py"`; путь через установленный симлинк одинаков для всех CLI. Не регистрируй MCP-сервер трекера в конфигурации агента (держи `mcp_servers.*` выключенным, в `enabled = false`).
- Вызывай `python3 "$TRACKER" …` из рабочего каталога проекта: конфигурация и секреты принадлежат периметру, а он резолвится по рабочему каталогу (`AGENTS_PROJECT_PATH` или `AGENTS_PROJECT` задают его явно). Вызов из каталога навыка читает общий периметр и не видит конфигурацию целевого проекта. Ниже команды записаны коротким `tracker.py`.
- Доступ к серверу (URL, заголовки, токен) — секция
  `[mcp.<имя-сервера>]` живого конфига; заполнение и проверка —
  `../references/credentials.md`. Ошибка авторизации или отсутствие секции —
  блокер конфигурации: сообщи и остановись, не подбирай заголовки сам.
- Создание, изменение, удаление, transition, comment, watcher, worklog, sprint и link разрешены только точной командой `/external-write issue-tracker <действие> <цель>` и только для названных действия и цели.
- Текст комментария готовь в нативной разметке продукта по `references/comment-markup.md`: клиент при чтении конвертирует разметку в markdown, поэтому вид прочитанного комментария образцом не является.
- Перед изменением повторно проверь issue key, project, текущий state и итоговое изменение. Не расширяй разрешение на соседние issues.
- Оценка качества кода — вне этого адаптера.

## Операции

Клиент `scripts/tracker.py` предоставляет классовые операции:

- `resolve-key` — разрешить issue key в полные данные задачи (`tracker.py issue <KEY>`).
- `fetch-issue` — получить задачу по ключу или запросу, включая normalized поля (спринт и т.п.).
- `my-issues` — личный список задач пользователя (`tracker.py mylist --limit 50`), закреплённый фильтр из `issue_tracker.my_issues_query`.
- `remote-links` — remote links задачи (панель Links, в т.ч. привязанные wiki-страницы), которых нет ни в полях issue, ни среди MCP-инструментов (`tracker.py remote-links <KEY>`).
- `transition-status` — перевести задачу в новый статус после точной команды `/external-write issue-tracker transition-status <KEY>` (`tracker.py write-call <tool> --arguments ...`).

## Порядок работы

1. Для чтения задачи сразу используй стабильную команду без `tools/list`:
   `tracker.py issue ABC-490`.
   Комментарии включены по умолчанию: последние 20 (`--comments N` меняет лимит, `--comments 0` отключает). Поле комментариев команда дописывает к набору полей сама, поэтому ни набор из конфигурации, ни `--fields` комментарии не отключают. При необходимости добавь `--fields` или `--expand`.
   Дефолтный набор команда дополняет полями `components`, `issuelinks` и
   `parent`; запрошенные контекстные поля, которых нет в ответе сервера,
   перечисляет в `_adapter.missing_context_fields` верхнего уровня ответа
   клиента. Явный `--fields` заменяет дефолтный набор и сохраняет только
   перечисленные поля вместе с комментариями.
   Если вызывающий workflow определяет репозиторий по контексту задачи, читай источники по порядку: сама задача → её эпик → связанные issues, из каждого — поля, ссылки и компоненты. Остановись на первом источнике с однозначным маппингом; один ключ повторно не обходи.
2. Для поиска также не запрашивай схему:
   `tracker.py search 'project = ABC ORDER BY updated DESC' --limit 10`.
   Объемный ответ сразу записывай через `--output`, чтобы не повторять запрос при обрезанном stdout. Команда подтверждает запись строкой `saved: <путь> (<N> chars)`; перечитывать файл не нужно.
3. `issue` всегда передает `update_history=false`, чтобы чтение не меняло историю просмотров.
4. Только если готовой команды нет и схема инструмента неизвестна, получи актуальный список:
   `tracker.py tools`.
   Для поиска id конкретного поля по ключевому слову есть короткая подкоманда:
   `tracker.py fields sprint`.
   Привязанные к задаче remote links (панель Links, в т.ч. wiki-страницы) читаются
   отдельной подкомандой: `tracker.py remote-links ABC-490`.
   Она идёт прямым REST-GET (эндпоинт remotelink), переиспользуя заголовки
   MCP-шлюза с базовым URL продукта и personal-token (`issue_tracker.rest.url_header`,
   `issue_tracker.rest.token_header`), и возвращает нормализованный список
   `{title, url, application_type, page_id}`; `page_id` заполнен для wiki-URL.
5. Выбери только инструмент с префиксом из `issue_tracker.tool_prefix` (по умолчанию `jira_`); клиент отклоняет остальные namespaces.
6. Для универсального read-only вызова передай JSON-объект:
   `tracker.py call jira_search --arguments '{"jql":"project = ABC ORDER BY updated DESC","limit":10}'`.
7. Для сложного JSON сохрани аргументы во временный файл и используй `--arguments-file`; не помещай токены или секреты в аргументы.
8. Обрабатывай pagination до требуемой полноты (у готовых подкоманд — `--start-at`). Не считай первую страницу полным результатом.
9. После разрешённого Write-вызова через `write-call` перечитай измененный объект и проверь наблюдаемый результат.

## Личный список задач

- Личный рабочий список пользователя — сохранённый фильтр трекера (`issue_tracker.my_issues_query`; значение установки, дефолта нет — без ключа команда отказывает). Сам сохранённый фильтр не меняй; для отображения фильтруй/сортируй только клиентский вывод.
- Получай его готовой подкомандой `my-issues`. Объемный результат сразу сохраняй через `--output`.
- Поле спринта (`issue_tracker.fields.sprint`, id узнан через `fields sprint`) уже возвращается в нормализованном виде.
- Формат отображения: столбцы `Key | Тип | Спринт | Статус | Приоритет | Исполнитель | Summary`. По умолчанию скрывай закрытые issues и issues не на текущем исполнителе; при нескольких спринтах показывай активный. Это фильтрация только отображения.

## Ошибки

- Если инструмент вернул `isError`, не интерпретируй content как успешный результат.
- При ошибке авторизации или конфигурации сообщи сервер, операцию и безопасный текст ошибки; не выводи HTTP headers и токены.
- Не включай зарегистрированный MCP как workaround: это изменит поведение всех следующих сессий.
