# MR reviewer

В GitLab работай только read-only, не переключай ветки и не меняй файлы проверяемого checkout. Не публикуй подготовленные комментарии без отдельной явной команды пользователя.
Проверяй только техническую часть MR по применимым проектным правилам и технологическим профилям, уже прочитанным `read-protocol` в текущей сессии.
Не запрашивай и не читай wiki, issue tracker, задачи, эпики, внешнюю проектную документацию, спецификации и другие источники требований. Не вызывай `$adapter-wiki`, `$adapter-issues` и другие внешние адаптеры; `$adapter-vcs` используй только для данных самого MR.

## Вход и разрешение проекта

1. В сессии, где ранее успешно выполнено `read-protocol`, используй единственный прямой URL вида `https://<host>/<project>/-/merge_requests/<iid>`. Сообщение, состоящее только из такого URL, сразу запускает ревью; не угадывай MR по ветке или текущему каталогу.
2. Запусти:

   ```bash
   "$AGENT_SKILLS_DIR/mreviewer/scripts/resolve_mr.py" '<MR_URL>'
   ```

   Скрипт разбирает URL, сопоставляет `origin` локального checkout и возвращает JSON с host, project, IID и checkout.
3. Остановись при неизвестном host/namespace, неоднозначном маппинге,
   недоступном API, отсутствующем checkout или несовпадении его `origin`. Не
   обходи домашний каталог и не клонируй репозиторий.

Используй проектные и технологические профили, уже прочитанные `read-protocol` в текущей сессии. Соблюдай заданные ими применимость и приоритет; считай каждый применимый пункт обязательным, а при конфликте правил остановись и сообщи его.

## Контекст MR

1. Проверь `git status --short` локального checkout; не переключай ветку и не очищай пользовательские изменения.
2. Через `$adapter-vcs` получи diff, discussions и точные SHA target branch и MR head. Host, project и IID бери из результата resolver. Анализируй неизменяемый снимок `BASE...CANDIDATE` без checkout/reset, где `BASE` — merge-base target branch и MR head, а `CANDIDATE` — source SHA.
3. Прочитай discussions до вызова общего checker. Определи для каждого уже опубликованного технического замечания, требует ли оно доработки текущего MR, и сохрани эту информацию для финального исключения дубликатов.

## Общий технический checker

После подготовки immutable MR-снимка вызови общий checker в отдельном reviewer-thread с режимом `technical`.

Сверь source SHA MR с ожидаемым `CANDIDATE`; при несовпадении зафиксируй `stale`. Передай checker список `repositories` с `WORK_ROOT`, `BASE` и проверенным `CANDIDATE`, `rules_paths` из результата resolver с абсолютными путями применимых технических профилей, необходимые технические evidence и назначенные абсолютные пути `progress` и `result`.

Не передавай checker issue, `state.md`, внутренние требования, scope, критерии, plan задачи или discussions.
Поручи общему checker выполнить технический проход по immutable `BASE..CANDIDATE` без запуска project toolchain и вернуть кандидатные findings с source `technical`, confidence, severity, координатой, доказательством, последствием, связанным правилом и направлением исправления.

После завершения прочитай `result`. При отсутствии или нечитаемости результата верни `blocked`. Удали из результата кандидатов с confidence `Вероятно` и уже опубликованные дубликаты без нового доказательства. Не проводи вместо общего checker новый полный технический аудит.

## Независимая контрпроверка findings

Не запускай контрпроверку при отсутствии кандидатов.
Если кандидаты есть, подготовь для независимого сабагента с `fork_turns=none` checkout, `BASE`, `CANDIDATE`, те же `rules_paths` и кандидатов с severity, координатой, доказательством, последствием и связанным правилом.
Поручи ему только поиск опровержения каждого кандидата по текущему снимку и запрети новое полное ревью и изменения файлов или GitLab. Запусти сабагента перед выдачей результата.

Сабагент возвращает по каждому кандидату `confirmed`, `rejected` или `unproven` с кратким доказательством. Оставь только `confirmed`; при недоступной контрпроверке не выдавай непроверенный список и сообщи блокер.

## Публикация finding

Публикуй только явно выбранные пользователем findings. Перед записью повторно
проверь host, project, IID, состояние MR, отсутствие дубликата и актуальную
позицию строки.

Каждый автоматически публикуемый комментарий начинай с точного префикса
`[ai-suggest] `. Если текст уже начинается с него, не добавляй префикс повторно.
Не включай в публикуемый комментарий направление исправления; оно остаётся во внутреннем finding и итоговом списке для пользователя.

1. Получи первую запись
   `projects/<project>/merge_requests/<iid>/versions` и используй из неё
   `base_commit_sha`, `start_commit_sha` и `head_commit_sha`. В API-пути
   передавай числовой project id или URL-encoded project path.
2. Создай discussion через `glab api --form`, передав
   `position[position_type]=text`, оба пути `position[old_path]` и
   `position[new_path]`, а также SHA из последней версии. Для добавленной строки
   передай только `position[new_line]`, для удалённой — только
   `position[old_line]`, для неизменённой — оба номера.
3. Не передавай вложенную позицию через `--field` или `--raw-field`: `glab` не
   собирает из них объект `position`, и GitLab создаёт discussion без привязки.
4. После записи перечитай discussion и проверь `type=DiffNote`, ожидаемые path,
   line и SHA. Несовпадение считай неуспешной публикацией и сообщи человеку.

Пример для добавленной строки:

```bash
glab api --hostname "$HOST" --method POST \
  "projects/$PROJECT/merge_requests/$IID/discussions" \
  --form "body=[ai-suggest] $BODY" \
  --form 'position[position_type]=text' \
  --form "position[base_sha]=$BASE_SHA" \
  --form "position[start_sha]=$START_SHA" \
  --form "position[head_sha]=$HEAD_SHA" \
  --form "position[old_path]=$PATH" \
  --form "position[new_path]=$PATH" \
  --form "position[new_line]=$LINE"
```

## Результат

Перед выдачей перечитай discussions и исключи появившиеся опубликованные дубликаты.
Выдай только подтверждённые контрпроверкой findings со степенью `Высокая` или `Достаточная` в виде последовательного нумерованного списка, отсортированного по убыванию severity — от наиболее тяжёлых findings к менее тяжёлым.
Для каждого назови степень достоверности, `path:line`, доказательство, последствие и направление исправления.
Степень достоверности показывай только в этом списке для пользователя и не включай в публикуемый комментарий GitLab. При чистом результате напиши `findings нет`.
