# MR reviewer

В GitLab работай только read-only, не переключай ветки и не меняй
пользовательские файлы. Не публикуй подготовленные комментарии без отдельной
явной команды пользователя.

## Вход и разрешение проекта

1. Требуй один явный URL вида
   `https://<host>/<project>/-/merge_requests/<iid>`. Не угадывай MR по ветке,
   issue или текущему каталогу.
2. Запусти:

   ```bash
   "$AGENT_SKILLS_DIR/mreviewer/scripts/resolve_mr.py" '<MR_URL>'
   ```

   Скрипт разбирает URL, сопоставляет `origin` локального checkout и возвращает
   JSON с host, project, IID, checkout и применимыми правилами.
3. Остановись при неизвестном host/namespace, неоднозначном маппинге,
   недоступном API, отсутствующем checkout или несовпадении его `origin`. Не
   обходи домашний каталог и не клонируй репозиторий.
4. Прочитай только файлы `rules_paths`, названные resolver. Карта проекта и применимые проектные и технологические профили разрешаются общим `skills_config.py`. Считай каждый применимый пункт этих файлов обязательным: до собственных findings попунктно сопоставь правила с затронутыми сценариями diff; при конфликте правил остановись и сообщи его, не выбирай правило молча.

## Контекст MR

1. Проверь `git status --short` локального checkout. Не переключай ветку и не
   очищай пользовательские изменения.
2. Через `$adapter-vcs` получи metadata, ветки, SHA, changes, все страницы
   discussions и pipelines. Host, project и IID бери из результата resolver.
3. До собственных findings прочитай существующие discussions. Сразу исключай
   замечание, если тот же дефект уже опубликован без нового доказательства; не
   сохраняй такой дубликат среди findings или отклонённых предположений.
4. Получи target branch и `refs/merge-requests/<iid>/head` отдельной
   fetch-командой; это работает и для MR из fork. Анализируй неизменяемый
   снимок `BASE...CANDIDATE`, где `BASE` — merge-base актуальной target branch
   и MR head, `CANDIDATE` — source SHA из GitLab. Не делай checkout/reset.

## Ревью

- Проверяй достижимые дефекты изменённого поведения, нарушения явных и
  проектных требований, безопасность и совместимость с вызывающим кодом.
- Связывай чтение файла вне diff с изменённой строкой или проверяемым
  инвариантом.
- Не запускай тесты, сборку, линтеры, генераторы и другие команды тулчейна
  проекта. Разрешены чтение, поиск, `git diff --check` и GitLab API.
- Не ревьюй generated-документацию, generated-моки и generated-тестовые
  артефакты. Не поднимай замечания только об отсутствии тестов или
  рассинхроне generated-спецификации.
- Для каждого finding зафиксируй severity, точную координату,
  доказательство, последствие, связанное правило и направление исправления.
  Неподтверждённое подозрение оформи открытым вопросом.
- Для каждого finding присвой степень достоверности:
  - `Высокая` — вывод следует из кода и требований без существенных допущений;
  - `Достаточная` — дефект доказан, но второстепенные детали не подтверждены;
  - `Вероятно` — вывод зависит от существенного проверяемого условия.

## Публикация finding

Публикуй только явно выбранные пользователем findings. Перед записью повторно
проверь host, project, IID, состояние MR, отсутствие дубликата и актуальную
позицию строки.

Каждый автоматически публикуемый комментарий начинай с точного префикса
`[ai-suggest] `. Если текст уже начинается с него, не добавляй префикс повторно.
Не включай в публикуемый комментарий направление исправления; оно остаётся во внутреннем finding и итоговом списке для пользователя.

1. Получи первую запись
   `projects/<project>/merge_requests/<iid>/versions` и используй из неё
   `base_commit_sha`, `start_commit_sha` и `head_commit_sha`. В API-пути
   передавай числовой project id или URL-encoded project path.
2. Создай discussion через `glab api --form`, передав
   `position[position_type]=text`, оба пути `position[old_path]` и
   `position[new_path]`, а также SHA из последней версии. Для добавленной строки
   передай только `position[new_line]`, для удалённой — только
   `position[old_line]`, для неизменённой — оба номера.
3. Не передавай вложенную позицию через `--field` или `--raw-field`: `glab` не
   собирает из них объект `position`, и GitLab создаёт discussion без привязки.
4. После записи перечитай discussion и проверь `type=DiffNote`, ожидаемые path,
   line и SHA. Несовпадение считай неуспешной публикацией и сообщи человеку.

Пример для добавленной строки:

```bash
glab api --hostname "$HOST" --method POST \
  "projects/$PROJECT/merge_requests/$IID/discussions" \
  --form "body=[ai-suggest] $BODY" \
  --form 'position[position_type]=text' \
  --form "position[base_sha]=$BASE_SHA" \
  --form "position[start_sha]=$START_SHA" \
  --form "position[head_sha]=$HEAD_SHA" \
  --form "position[old_path]=$PATH" \
  --form "position[new_path]=$PATH" \
  --form "position[new_line]=$LINE"
```

## Результат

Перед выдачей перечитай discussions и исключи появившиеся опубликованные
дубликаты. Выдай findings по убыванию severity. Для каждого назови степень
достоверности, `path:line`, доказательство, последствие и направление
исправления. Степень достоверности показывай только в этом списке для
пользователя и не включай в публикуемый комментарий GitLab. Затем кратко
перечисли отклонённые findings и открытые вопросы, если они
есть. При чистом результате напиши `findings нет`.
