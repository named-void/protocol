# MR reviewer

В GitLab работай только read-only, не переключай ветки и не меняй файлы проверяемого checkout. Не публикуй подготовленные комментарии без отдельной явной команды пользователя.
Проверяй только техническую часть MR по применимым локальным проектным правилам и технологическим профилям. Не запрашивай и не читай wiki, issue tracker, задачи, эпики, внешнюю проектную документацию, спецификации и другие источники требований. Не вызывай `$adapter-wiki`, `$adapter-issues` и другие внешние адаптеры; `$adapter-vcs` используй только для данных самого MR.

## Вход и разрешение проекта

1. Требуй один явный URL вида
   `https://<host>/<project>/-/merge_requests/<iid>`. Не угадывай MR по ветке или
   текущему каталогу.
2. Запусти:

   ```bash
   "$AGENT_SKILLS_DIR/mreviewer/scripts/resolve_mr.py" '<MR_URL>'
   ```

   Скрипт разбирает URL, сопоставляет `origin` локального checkout и возвращает
   JSON с host, project, IID, checkout и применимыми правилами.
3. Остановись при неизвестном host/namespace, неоднозначном маппинге,
   недоступном API, отсутствующем checkout или несовпадении его `origin`. Не
   обходи домашний каталог и не клонируй репозиторий.
4. Читай `rules_paths` в порядке, который вернул resolver. Профили сами задают применимость и приоритет своих разделов; для UPL первым идёт `upl-services.md` с обязательными правилами ревью MR, затем технологические профили. Пути, которых resolver не вернул, не читай. Считай каждый применимый пункт обязательным: при конфликте правил остановись и сообщи его, не выбирай правило молча.

## Контекст MR

1. Проверь `git status --short` локального checkout; не переключай ветку и не очищай пользовательские изменения.
2. Через `$adapter-vcs` получи diff, discussions и точные SHA target branch и MR head. Host, project и IID бери из результата resolver. Анализируй неизменяемый снимок `BASE...CANDIDATE` без checkout/reset, где `BASE` — merge-base target branch и MR head, а `CANDIDATE` — source SHA.
3. До собственных findings прочитай discussions, определи для каждого технического замечания, требует ли оно доработки текущего MR, и исключи уже опубликованный дубликат, если нет нового доказательства.

## Ревью

- Проверяй достижимые дефекты изменённого поведения, нарушения применимых технических правил, безопасность и совместимость с вызывающим кодом.
- Связывай чтение файла вне diff с изменённой строкой или проверяемым
  инвариантом.
- Не запускай тесты, сборку, линтеры, генераторы и другие команды тулчейна
  проекта. Разрешены чтение, поиск, `git diff --check` и GitLab API.
- Не ревьюй generated-моки и generated-тестовые артефакты. Не поднимай замечания только об отсутствии тестов.
- Для каждого потенциального finding присвой степень достоверности:
  - `Высокая` — вывод следует из кода и применимых технических правил без существенных допущений;
  - `Достаточная` — дефект доказан, но второстепенные детали не подтверждены;
  - `Вероятно` — вывод зависит от существенного проверяемого условия.
- Кандидата со степенью `Вероятно` сразу отбрось: не продолжай его анализ, не сохраняй как finding или открытый вопрос и не публикуй.
- Для каждого оставшегося finding зафиксируй severity, точную координату, доказательство, последствие, связанное правило и направление исправления.

## Независимая контрпроверка findings

Если кандидатов нет, контрпроверку не запускай. Иначе перед выдачей результата запусти одного независимого сабагента с `fork_turns=none`. Передай ему checkout, `BASE`, `CANDIDATE`, `rules_paths` и кандидатов с severity, координатой, доказательством, последствием и связанным правилом. Поручи только контрпроверку: искать опровержение каждого кандидата по текущему снимку, не проводить новое полное ревью и не менять файлы или GitLab.

Сабагент возвращает по каждому кандидату `confirmed`, `rejected` или `unproven` с кратким доказательством. Оставь только `confirmed`; при недоступной контрпроверке не выдавай непроверенный список и сообщи блокер.

## Вызов из protocol

При вызове из protocol получи маркер `mreviewer_role: reviewer`, один явный `MR_URL`, ожидаемый `CANDIDATE` и абсолютные пути `progress` и `result`.

Выполняй только полный технический проход MR. Вызов для режима `fixes` не выполняй; protocol использует `mreviewer` только для первичного `full` прохода.

Сверь source SHA MR с ожидаемым `CANDIDATE`; несовпадение зафиксируй в `result` как `stale`.

В `progress` записывай только локальное время и этап `resolve`, `context`, `review`, `countercheck` или `done`.

В `result` запиши состояние `completed`, `stale` или `blocked`, рекомендацию `accepted` или `revision-required`, MR, `CANDIDATE` и только подтверждённые findings с severity, степенью достоверности, координатой, доказательством, последствием, связанным правилом и направлением исправления. При чистом результате рекомендация — `accepted`.

При вызове из protocol после записи `result` сообщи только состояние завершения и путь к нему; findings в GitLab не публикуй.

## Публикация finding

Публикуй только явно выбранные пользователем findings. Перед записью повторно
проверь host, project, IID, состояние MR, отсутствие дубликата и актуальную
позицию строки.

Каждый автоматически публикуемый комментарий начинай с точного префикса
`[ai-suggest] `. Если текст уже начинается с него, не добавляй префикс повторно.
Не включай в публикуемый комментарий направление исправления; оно остаётся во внутреннем finding и итоговом списке для пользователя.

1. Получи первую запись
   `projects/<project>/merge_requests/<iid>/versions` и используй из неё
   `base_commit_sha`, `start_commit_sha` и `head_commit_sha`. В API-пути
   передавай числовой project id или URL-encoded project path.
2. Создай discussion через `glab api --form`, передав
   `position[position_type]=text`, оба пути `position[old_path]` и
   `position[new_path]`, а также SHA из последней версии. Для добавленной строки
   передай только `position[new_line]`, для удалённой — только
   `position[old_line]`, для неизменённой — оба номера.
3. Не передавай вложенную позицию через `--field` или `--raw-field`: `glab` не
   собирает из них объект `position`, и GitLab создаёт discussion без привязки.
4. После записи перечитай discussion и проверь `type=DiffNote`, ожидаемые path,
   line и SHA. Несовпадение считай неуспешной публикацией и сообщи человеку.

Пример для добавленной строки:

```bash
glab api --hostname "$HOST" --method POST \
  "projects/$PROJECT/merge_requests/$IID/discussions" \
  --form "body=[ai-suggest] $BODY" \
  --form 'position[position_type]=text' \
  --form "position[base_sha]=$BASE_SHA" \
  --form "position[start_sha]=$START_SHA" \
  --form "position[head_sha]=$HEAD_SHA" \
  --form "position[old_path]=$PATH" \
  --form "position[new_path]=$PATH" \
  --form "position[new_line]=$LINE"
```

## Результат

Перед выдачей перечитай discussions и исключи появившиеся опубликованные дубликаты. Выдай только подтверждённые контрпроверкой findings со степенью `Высокая` или `Достаточная` в виде последовательного нумерованного списка, отсортированного по убыванию severity — от наиболее тяжёлых findings к менее тяжёлым. Для каждого назови степень достоверности, `path:line`, доказательство, последствие и направление исправления. Степень достоверности показывай только в этом списке для пользователя и не включай в публикуемый комментарий GitLab. При чистом результате напиши `findings нет`.
