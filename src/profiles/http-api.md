# HTTP/API

- Без явного требования возвращать полную модель держи write API минимальными: create возвращает `id`, update/save/delete — `204 No Content`, актуальное состояние читается отдельным GET.
- Для известных resource-сценариев возвращай доменно-конкретные not found ошибки вместо общего сообщения, если это помогает клиенту определить отсутствующую сущность.
- В request/query binding принимай только документированные имена параметров; для новых и изменяемых query-параметров используй snake_case и не добавляй camelCase/legacy aliases без явного требования. При удалении alias синхронизируй код, тесты и локальную документацию.
- Валидацию JSON-тела держи целиком на binding-тегах через `httperrors.BindJSON` — отдельного ручного post-bind слоя (`validate*Request`) не заводи. BindJSON обрезает краевые пробелы в строках и валидирует до передачи в usecase. Присутствие/непустоту/длину задавай стандартными тегами (`required`; непустота — `notblank`, не `min=1`; длина — `min`/`max`).
  Формат (символы, телефон, email, URL, цифровые реквизиты) и кросс-полевые правила тоже задавай тегами: встроенными (`oneof`, `required_without` и т.п.) или кастомными валидаторами, зарегистрированными в `binding_validation.go`; код и текст ответа для кастомного тега задаёт `fieldErrorMapper`. Имя поля в тексте ошибки не дублируй — клиент видит его из JSON-пути в `field`. Query-параметры и заголовки binding-тегами не покрываются — их валидируй вручную.
- Доменное поле request- или response-DTO с конечным набором значений типизируй именованным domain-типом (`type VendorType string`) с типизированными константами; свободные коды и текст оставляй строками. Именованный тип сериализуется исходной строкой, поэтому проволочный JSON не меняется.
- Поле request- или response-DTO с контрактом календарной даты типизируй `dto.Date` (`YYYY-MM-DD`), валидируй тегом `date` через `time.Parse(time.DateOnly)` и помечай `swaggertype:"string" format:"date"`.
- Если typed enum-поле должно отклоняться на binding, валидируй его кастомным валидатором, названным по доменному термину и зарегистрированным через `sync.Once`; обёртка вызывает `IsValid()`. Иную проверку enum оставляй в domain/usecase по месту ответственности.
- Замену встроенного тега кастомным сохраняй для клиента: `fieldErrorMapper` возвращает прежние код и сообщение, а платформенный путь поля сохраняется без изменений. Для enum-валидаторов используй `ONEOF` + `InvalidOneOfMessage`; код ошибки формата даты сохраняй сервисным (`VALIDATION_ERROR` в user-service, `DATETIME` в ord-service).
- Условный маппер ошибок выбирай по паре тега и JSON-пути; простой кастомный enum- или форматный тег может маппиться только по тегу. При появлении другого DTO с теми же именами полей дорабатывай маппер в его цикле.
- Простое условие JSON-входа, сводящееся к наличию или отсутствию поля при конкретном значении соседнего поля, выражай binding-тегами `required_if`, `required_unless`, `excluded_if` или `excluded_unless` и проверяй до usecase; ручную проверку такого условия в transport не добавляй. Условные теги ставь до `omitnil`/`omitempty`, иначе условная обязательность не срабатывает на nil-поле.
  Параметры — пары поле-значение: в `required_if` и `excluded_if` несколько пар означают AND, в `required_unless` и `excluded_unless` — OR; повтор поля в `*_if` не выражает альтернативы и паникует. Для `*string` заполнение означает non-nil. Условие с несколькими альтернативами одного поля, нетривиальным сравнением, проверкой коллекции или существования сущности выражай кастомным binding-валидатором либо проверяй в domain/usecase по месту ответственности.
- Binding-валидация является ранней проверкой transport-слоя и не заменяет domain-проверку бизнес-инварианта, если вход может поступить через другой transport или напрямую в usecase/domain. Дублирование допустимо только как ранний отказ с теми же полем, кодом и смыслом ошибки; проверки уникальности, согласованности сущностей и целостности состояния оставляй в domain/usecase.
- `ErrorResult.Errors` содержит элемент на каждую `FieldError`, поэтому при нескольких одновременных нарушениях 400-ответ шире доменного «первой ошибки»; это платформенный стандарт, а не дефект.
- JSON-путь повторяет алгоритм приватного `httperrors.fieldErrorPath` из v1.1.1; сохраняй паритет локальным хелпером или сторож-тестом по `field` реального `ErrorResult` и направляй доработку платформы на экспорт хелпера.
- Общие для domain и binding сообщения объявляй экспортируемыми константами domain и используй их с обеих сторон.
- Ожидание HTTP-теста задавай точным кодом ответа и наблюдаемым эффектом (достигнутый вызов слоя, изменённое состояние), а не отрицанием кода: ассерт «код не 400» удовлетворяется любым отказом, включая 500 от паники в обработчике, и остаётся зелёным при полностью сломанном пути. Стенд собирай с рабочим usecase на моках; роутер с `nil`-зависимостью проверяет только binding, и проверки на теле ответа сверяются с пустой строкой.
- Обязательность поля в swagger (`required`) swaggo выводит из тега `binding:"required"`, а не из `json`-тега (проверено `make swagger`): finding вида «`omitempty` скрывает обязательность в swagger» неверен по обоснованию. Но `omitempty` на required-поле снимай всё равно — по другой причине: при сериализации он выкидывает нулевое значение (`0`, `""`, `false`, `nil`) из ответа, и обязательное поле с легитимным нулём молча исчезает из payload.
  Итог: обязательность задаёт `binding:"required"`, а `omitempty` на required-полях не оставляй.
- Не заводи отдельный response DTO только для сокрытия необязательного вложенного поля. Продолжай использовать общий тип, а когда вложение не запрошено или не должно возвращаться, оставляй поле `nil`; его JSON-представление (`null` или отсутствие при `omitempty`) должно сохранять действующий контракт endpoint.
