# PostgreSQL implementation

- Локальной БД управляй через `psql` внутри compose-контейнера БД (обычно `db`, у части сервисов `<service>-db`), например `docker exec db psql -U postgres ...`; не полагайся на локальный `psql` хоста.
- Операционные SQL-скрипты (разовый разбор данных, подготовка к миграции) пиши чистым SQL без мета-команд `psql` (`\set`, `\if`, `\echo`): их запускают в консоли произвольного клиента БД, где такие строки падают с syntax error. Режимы «показать план» и «применить» разделяй отдельными запросами, атомарность обеспечивай одним statement (`DO $$ ... END $$`), а не ручными `BEGIN`/`COMMIT`.
- Изменения схемы выполняй через миграции; не меняй зафиксированные миграции без явного запроса, незакоммиченные можно править до фиксации.
- Миграции задачи проверяй up/down в изолированной БД (`CREATE DATABASE <key>_check` в том же контейнере), а не на общей dev-БД: параллельные ветки занимают номера миграций и версию `schema_migrations`, поэтому `migrate up` на общей базе даёт ложное «up to date». Номер новой миграции сверяй с базовой веткой и каноническими ветками параллельных задач **после догона базы** (rebase/merge), а не до него: свободный на старте номер занимает любая ветка, влитая за время работы. Сверку подтверждай прогоном `migrate up` — дубликат ловит он (`duplicate migration file`), а не чтение списка файлов. Коллизию номеров решает перенумерацией тот, кто вливается вторым.
- Номер миграции обязан быть строго выше максимального номера базовой ветки на момент влития, а не только незанятым: миграция с номером ниже `schema_migrations.version` целевой БД не применяется никогда, а `migrate up` отвечает `up to date, no migrations to apply` и кодом 0. Дубликата такой номер не образует, поэтому прогон в изолированной БД его не ловит — там накат идёт с нуля и проходит по порядку. Свои номера сверяй с максимумом базы перед влитием, а не только после догона; на стенде сопоставляй `schema_migrations.version` с номерами файлов задачи.
- Миграцию, пропущенную на стенде из-за номера ниже его версии, накатывай её же SQL по месту и `schema_migrations` не правь: таблица хранит одну строку (`version`, `dirty`) без журнала применённых версий, поэтому схема совпадает с чистым накатом, следующая по номеру миграция применяется штатно, а `down` остаётся консистентным, пока файлы миграции на месте. Перенумерация файлов ломает базы, где миграция уже применена, — оставляй её случаю, когда пропуск затронул больше одной базы.
- Тип и ограничения колонки сверяй с итоговым состоянием схемы — по всем миграциям колонки и документации БД, а не по первой найденной миграции.
- В опасных местах миграций (`ADD COLUMN`, `CREATE TABLE`/`INDEX`, `DROP COLUMN`/`CONSTRAINT`/`INDEX`) добавляй нативные `IF [NOT] EXISTS`. Операции без нативной поддержки (`ADD CONSTRAINT`, `COMMENT ON`) не оборачивай в `DO $$ ... END $$` только ради идемпотентности.
- Для новых или измененных таблиц и колонок добавляй или обновляй `COMMENT ON`; пиши комментарии краткими и доменными, без технического шума вроде `PK`, `FK`, `ID` или `table.column`.
- При `Scan` заполняй поля результирующей сущности напрямую и держи перечисление компактным; промежуточные переменные используй только для преобразований.
- В многострочном `SELECT` задавай явный `AS`-алиас каждому полю проекции; алиасы пиши в `snake_case`.
- Используй короткие алиасы таблиц (`usr`, `ur`, `up`, `prt` и т.п.). Квалифицируй поля алиасом только в запросах с `JOIN` или подзапросами и не повторяй там полное имя таблицы.
- При insert/update таблиц ассоциаций не делай предварительную `JOIN`-проверку существования; вставляй связь напрямую и позволяй foreign key проверять связанные сущности.
- Не скрывай блокировку в read-методе: делай ее явной через `withLock bool`.
- Предпочитай короткие статичные запросы; объединяй операции только ради атомарности, производительности или целостности.
- Не собирай SQL через шаблоны с подстановкой таблиц, алиасов или `JOIN`; предпочитай отдельные repository-методы.
- Не открывай транзакцию вокруг одиночного repository-вызова без практической необходимости; используй ее для атомарности нескольких операций или явного consistency-риска.
- Для enum/status с бизнес-порядком задавай явную сортировку (`CASE`, lookup/rank и т.п.) и покрывай тестом все значимые значения.
