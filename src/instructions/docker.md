# Работа с Docker

Факты о докере рабочей станции: чужое состояние, запуск демона, проверка
настройки контейнера, монтирование. Читать перед первой docker-командой.
Остальные факты станции — `environment.md` этого же каталога.

- Локальное состояние Docker (контейнеры, стеки compose, тома, сети) принадлежит
  человеку: `down`, `stop`, `rm` и любое удаление — только по явному спросу,
  удаление тома не предлагай вовсе. `up` с фиксированным `container_name` тоже
  деструктивен — он пересоздаёт одноимённый чужой контейнер, включая
  остановленный, поэтому свой стек поднимай изолированно: отдельное имя проекта
  (`-p <задача>`) и override, снимающий `container_name`. Уборку своего стека
  предлагай человеку, а не выполняй. Восстановление состояния, которое снёс сам,
  подтверждай содержимым данных, а не тем, что контейнер поднялся.
- Docker Desktop обычно не запущен: `open -a Docker`, дождаться демона. Демон
  может не подняться и при запущенном приложении: привилегированную настройку он
  ведёт через `osascript … with administrator privileges` и ждёт GUI-диалог с
  паролем, а `docker info` не показывает при этом сведения сервера. Пароль вводит
  человек, поэтому без него нужен путь без Docker: локальный кластер поднимается
  драйвером `vfkit` (`brew install vfkit`, Virtualization.framework,
  `--network nat`) — прав администратора он не требует.
- Настройку контейнера (порт, env, healthcheck) проверяй отдельным `docker run
  --rm --name <probe>` на свободном порту, а не `docker compose up <сервис>`:
  при `container_name` up переиспользует контейнеры стенда, то есть чужое
  состояние.
- Перед первой docker-командой, меняющей состояние, снимай `docker ps -a` и
  `docker volume ls`: буфер `docker events` короткий, и восстановить по нему, кто
  удалил контейнер или том, обычно уже нельзя. Носитель данных ищи по
  `docker volume ls` с размерами и датами: объект контейнера говорит о проекте,
  но не о том, где лежат данные.
- Точку монтирования файла внутри уже примонтированного каталога создавай на
  хосте до запуска контейнера: docker её не создаёт и отказывает — `create
  mountpoint … is outside of rootfs`. Bind-mount источника, которого нет,
  наоборот создаёт каталог с именем файла по обе стороны границы, и приложение
  получает каталог вместо файла.
- Диагностику с сетевым ожиданием внутри контейнера (например DNS-пробу
  `docker exec db getent hosts …`) запускай с дедлайном: без него висящая
  команда держит шаг до общего таймаута ячейки. GNU `timeout` на станции нет
  (`environment.md`), поэтому фоновый запуск с `kill` по `$!` после `SECONDS`-цикла.
