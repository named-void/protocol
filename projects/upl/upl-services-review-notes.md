# Замечания принятых ревью UPL-сервисов

Выборка из discussion-веток слитых MR проектов `getblogger/upl/services/*` за 2026-09-09…2026-09-23: исходный комментарий оставил ревьювер, ветку закрыл он же. Исключены комментарии с маркером `[ai-suggest]` и замечания, уже покрытые правилами `upl-services.md` и политик шаблона `templ-service`. Формулировки обобщены для применения в любом UPL-сервисе; в скобках — MR-источник. При Implement, Accept и ревью принимай список во внимание вместе с правилами профиля и шаблона.

## Миграции и данные

- Номер новой миграции — очередной свободный; при параллельных MR в сервисе сверь нумерацию. (auth-service!57)
- Не дублируй в коде заполнение значений, которое уже выполняет миграция. (auth-service!62)

## Архитектура

- Копии файлов политик в сервисном репозитории не держи: правила живут в шаблоне `templ-service`. (catalog-service!51)
- Устаревшие таблицы, хендлеры и пути зачищай в запланированном MR цепочки. (catalog-service!40, catalog-service!41, catalog-service!43)
- Дублирующуюся логику и проверки выноси в общий хелпер. (catalog-service!42, catalog-service!44, user-service!97)
- Работающую, но громоздкую реализацию упрощай до очевидной. (catalog-service!45)

## Транзакции

- Подготовку данных и ветвление сценария выполняй внутри транзакции; читай сущность один раз и валидируй на прочитанном. (catalog-service!42)
- Повторная проверка доступа внутри транзакции — защита от гонки; дубли кода убирай хелпером, сетевые вызовы под транзакцией не держи. (user-service!97)

## Данные

- Выборка с лимитом должна возвращать полный ожидаемый набор: достаточный лимит или постраничное дочитывание. (catalog-service!42)
- Историю агрегата связывай по уровням: изменение дочерней сущности отражается в истории родительской без дублей записей. (catalog-service!55)

## API и конфигурация

- Имя переменной окружения для базового URL указывает на целевой сервис без опечаток (`CATALOG_SERVICE_BASE_URL`). (ord-service!3)
- Забытые служебные роуты, включая раздачу Swagger, не оставляй: регистрируй их только там, где это предусмотрено конвенцией. (ord-service!4)

## Стиль

- Новое поле или параметр добавляй рядом с тематически связанным либо в конец; существующий порядок без необходимости не меняй. (bff!2, catalog-service!49, catalog-service!50, tracking-service!9, user-service!93, user-service!94)
- Переименование доменного термина доводи до конца во всех слоях и тестах; имя метода отражает операцию (`CreateOrUpdate`). (catalog-service!40, ord-service!3, user-service!97)

## Открытые архитектурные вопросы

- Целостность данных между БД сервисов при разделении хранения не защищена: проработай событийную синхронизацию. (catalog-service!43)
