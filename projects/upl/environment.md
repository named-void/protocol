# Среда UPL-сервисов

Операционные ограничения локального тулчейна и стенда. Читай перед первым запуском проектной команды, подготовкой локальной инфраструктуры или проверкой, способной обратиться к данным.

## Тулчейн

- `PATH` инструментов прогона: `/usr/local/go/bin`, `$HOME/go/bin`, `/opt/homebrew/bin` — go, затем mockery и goimports, затем golangci-lint. `$HOME/go/bin` в `PATH` по умолчанию нет, поэтому `go generate` вызывай с явным `PATH` или целью `make generate-mocks`.
- Используй mockery `v2.53.6` с легаси-флагами `--name` и `--exported`. Версия в репозитории не закреплена: `go generate` берёт бинарник из `PATH`.

## Локальный стенд и конфиг

- Проверки на Develop выполняй через версионированные сценарии `test-dev-rights`; read-only остаётся режимом по умолчанию для неописанных запросов,
  а POST/PUT/PATCH/DELETE разрешены только в сценарии с минимальным изменением, уникальным fixture или восстановлением и обязательным cleanup.

## Локальная инфраструктура и сквозной прогон через gateway

- Инфраструктура - один постоянный compose-блок `upl-infra` (`projects/upl/infra/compose.yaml`):
  единый postgres 17 (контейнер `db`, host 5432: auth, user, catalog, ord, report, tracking),
  redis 6379, kafka 9092/9094, rabbitmq 5672, minio 9000, jaeger 16686, envoy 8110.
  Подъём: `upl-infra.sh infra up` (скрипт рядом с профилем, `projects/upl/infra/`).
- Экземпляры сервисов поднимает `upl-infra.sh svc up <svc>` на хосте из основного чекаута:
  auth 8100, user 8101, catalog 8102, report 8103, tracking 8108, ord 8666, bff 8113.
  envoy (gateway) - тот же реестр: `svc up/down/status/logs envoy` держит контейнер compose с рендер-конфигом (8110).
  Develop-экземпляр требует, чтобы чекаут сервиса стоял на `develop`; код задачного сервиса гоняется
  только как экземпляр задачи: `svc up <svc> --task UPL-XXXX`
  (worktree `services/<repo>-UPL-<N>`, ветка `feature/UPL-XXXX`, порт 9000+(порт-8000), БД `<db>_<N>`).
- Супервизор экземпляра перезапускает процесс при изменении исходников; логи в `~/_dev/git/obs/upl/.infra/log/`,
  статусы - `svc status`; конфиг экземпляра рендерится в `.infra/env/<имя>.env` из `configs/.env.example`.
- Основная БД каждого сервиса без суффикса = develop и живёт в общем блоке.
- БД задачи `<db>_<N>` создаётся `svc up <svc> --task UPL-XXXX` только если в diff задачи против `origin/develop` есть файлы `migrations/`.
  Созданная БД - клон основной БД сервиса на том же инстансе (pg_dump в пустую БД; останавливать develop-экземпляр не нужно), поверх клона накатываются миграции задачи.
  Задача без новых миграций гоняет код на общей БД сервиса и ничего к ней не применяет.
  Данные за прогоном на общей БД убирай по дисциплине интеграционных тестов против dev-БД (раздел ниже): уникальный fixture, фильтр по своему ключу, очистка в cleanup.
- До `task close` миграции задачного дерева исполняются только в БД задачи и в изолированной `<key>_check`; `svc migrate <svc> --task` отказывает, когда env экземпляра не указывает на его `<db>_<N>`.
  Env, поднятый до появления миграций задачи, указывает на общую БД - отказ требует повторного `svc up <svc> --task UPL-XXXX`.
- Создание идемпотентно: повторный `svc up --task` переиспользует существующую `<db>_<N>`, вне `task close` она не удаляется.
  При `task close UPL-XXXX` задача с миграциями применяет их на основную БД своего сервиса, затем снимает свои экземпляры, БД `<db>_<N>`, worktree и ветку (слитую).
  Характер миграций (включая breaking: DROP/RENAME/`SET NOT NULL`/смена типа) на создание БД не влияет - он задаёт пометку `breaking:` в QA-комментарии.
- Экземпляр сервиса на время теста - ресурс одной сессии: перед `svc up <svc> --task UPL-XXXX` глянь `svc status`; занятый порт чужим экземпляром даёт отказ `up` до операций с env и БД.
- Чужой экземпляр, его env и БД задачи не трогаются; отказ "порт занят" называет держателя - жди остановки или договаривайся; одновременный старт двух сессий не атомарен.
- После прогонов сразу гаси экземпляр задачи командой `svc down <svc> --task UPL-XXXX`, кроме экземпляров приёмки, ожидающих проверки человеком (раздел "Приёмка на стенде" профиля `upl-services.md`).
  Разв-экземпляры постоянны и не гасятся, финальную уборку делает `task close`.
- Приёмку на стенде выполняет `upl-infra.sh accept UPL-XXXX`; когда и как её проводить, задаёт раздел "Приёмка на стенде" профиля `upl-services.md`.
  Команда поднимает envoy с конфигом из worktree `envoy-UPL-XXXX` (если есть) и экземпляры всех затронутых задачей сервисов. Уже поднятые экземпляры задачи она перезапускает на актуальный код: не считай accept идемпотентным bulk-up.
  Затем печатает ссылки на swagger-UI изменённых методов: это diff `api/docs/swagger.json` обоих деревьев (для bff - diff `aggregation.yaml`).
  Строку сервиса с совпадающими спеками команда пропускает, а при несгенерированной спеке выводит ссылку с пометкой ручной сверки.
- Данные каталога для фильтров засевай `services/catalog-db-smoke.sql`: `upl-infra.sh seed catalog`.
- Дефолтные БД общего блока (`auth`, `user`, `catalog`, `ord`, `report`, `tracking`) — общий ресурс параллельных сессий: их могут чистить и перезаливать данными с develop вне вашей сессии. Перед прогоном с данными проверяй счётчиками непустость целевых таблиц и пересечение фикстур с ними; совпадающе пустой результат у отфильтрованного и неотфильтрованного запроса доказательства не даёт.
- Envoy - полноправный сервис реестра: конфиг рендерится в `.infra/envoy/` из основной ветки чекаута или из worktree задачи (`envoy-UPL-XXXX`); чекаут envoy на задачную ветку не ставится.
  Основная ветка репозитория - develop, если есть, иначе канон (первая из master/main); `develop|master|main` в `svc switch` - синонимы "на основную ветку", правило считается на каждом запуске.
  File provider подхватывает рендер без рестарта; `svc up/down` сами переписывают `backends.yaml` на порты живых экземпляров (экземпляр задачи приоритетнее develop).
- Локальную сессию получай `POST /auth/dev/login` с телом `{"role": "<код роли>"}` - локально роль
  в запросе передаётся, в отличие от develop. С `user_id` auth ищет пользователя через
  user-service по `USER_SERVICE_BASE_URL` из своего env.
  Адреса пиров в разв-экземплярах актуализирует сам `upl-infra.sh`: `svc up/down <svc> --task UPL-XXXX` и `task close` перерендеривают env задетых разв-экземпляров и перезапускают их; ручной перезапуск не нужен.
  Роль бери с реальным доступом к проверяемому методу: у `reg` почти нет доступов, у `super_admin` почти всё;
  доступы смотри в `role_permission` БД auth (контейнер `db`).
- Сквозной прогон идёт через envoy `http://localhost:8110`; когда он нужен, задаёт раздел "Приёмка на стенде" профиля `upl-services.md`.
  Если bff недостижим, primary принимает запрос сам и молча игнорирует не свои параметры, поэтому каждый новый фильтр bff проверяй отдельным запросом через gateway.
- Роуты сверяй с `services/envoy/config/routes.yaml`: у HTTPRoute `bff` query-матчер видит только первое
  значение ключа, регэкспы требуют полного совпадения значения.
  Задача с bff-блоком в `aggregation.yaml` обязана включать правило envoy (см. профиль upl-services) -
  отсутствие правила ловит только этот прогон.
- `final-checks.sh` для проверки миграций берёт контейнер из `DB_CONTAINER`,
  иначе находит общий postgres `db` стенда сам.
- Креды и туннель develop-postgres: `projects/upl/.data/config.toml`, секция `[develop_db]`
  (рыба и объяснение схемы - соседний `develop-db.env.example`; .data gitignored).
  Канонический интерфейс - `upl-infra.sh dev sync` (отчёт - `dev check`): read-only зашит в conninfo
  (переменную PGOPTIONS host-psql shim не пробрасывает), креды из config.toml в сессию не выводятся.
  Пайплайн: БД существуют/создаются; подключение обязано пройти в read-only (иначе стоп);
  миграции всех сервисов из origin/develop; версии миграций разошлись - стоп;
  схемы сверяются построчным diff - расхождение = human-gate (клон полным дампом с develop / пропустить);
  строки любой таблицы разошлись - перелив данных этой БД целиком; совпали - БД не трогается
  (волатильна из параллельных сессий). Перелив безусловный: локальные записи,
  которых нет на develop, не сохраняются. Запись на develop запрещена.

## Dev-авторизация для `test-dev-rights`

- Все запросы к Develop идут через общий домен `https://develop.getblogger.ru` (или `UPL_DEV_BASE_URL`); сервис определяется только path.
  `test-dev-rights` не читает auth-service и не извлекает из него роли или permission.
- Базовый URL для user-service-прогонов — только apex `https://develop.getblogger.ru`: сервисный `user.develop.getblogger.ru` целиком за oauth2-proxy — неаутентифицированные запросы, включая `/auth/dev/login`, отдают `302` на Keycloak OIDC, и dev-login без SSO-сессии там не работает; cookie-сессия apex принимается и на `user.develop`, поэтому обходить SSO не нужно.
  Apex периодически не резолвится с рабочей машины (Errno 8, DNS/VPN-зависимость): при отказе резолва повтори пробу и проверь VPN — сменять домен не пытайся.
- Пользователей ролей резолвирует `test_dev_rights_auth.py` через API: `GET /api/v1/users?role_codes=<role>&is_deleted=false` от bootstrap супер-админа;
  не подставляй идентификатор из примера, локальной БД или Jira и не передавай роль, не подтверждённую резолвом.
- Получай cookie-сессию отдельным запросом на `POST https://develop.getblogger.ru/auth/dev/login` с телом:

  ```json
  {
    "user_id": "<user_id активного пользователя роли>",
    "auth_type": "cookie"
  }
  ```

- Поле `role` в запрос dev login не передавай: роль определяется авторизацией по пользователю UPL-сервиса. Для каждого пользователя или роли используй отдельную cookie-сессию, затем вызывай проверяемый метод с этой cookie.
- Запрос dev login является служебным шагом получения сессии. Для POST/PUT/PATCH/DELETE на удалённом стенде используй только описанный manifest-сценарий с минимальным payload и cleanup; произвольные или массовые изменения запрещены.
- Cookie, токены и секреты не сохраняй в логах, `state.md`, evidence или комментарии для QA.
- Локальный флоу двухвариантный: инфраструктура в compose плюс приложение на хосте, либо всё в compose. Адреса и порты стенда обязаны работать в обоих сценариях: один и тот же адрес внешней системы видят и браузер с хоста, и процесс внутри сети compose.
- Конфиг читается из файла `CONFIG_PATH` с приоритетом над переменными окружения: для прогона против другой БД правь временную копию `.env`, переопределение `DB_NAME` через env не сработает. Копия обязана оканчиваться на `.env` — парсер выбирается по расширению, файл без него роняет загрузку конфига. Изолированную БД удаляй `DROP DATABASE ... WITH (FORCE)`.
- Конфигурация идёт по стандартному сценарию cleanenv: обязательность — тег `env-required`, значение по умолчанию — тег `env-default` (применяется только к отсутствующей переменной). Deployment-шаблон не определяет переменную пустой строкой: compose-маппинг переменной с дефолтом задаётся как `${VAR:-default}`, argocd-шаблон проставляет значение или не создаёт ключ. Пустая подстановка отсутствующей переменной — дефект шаблона: чинят шаблон, а не код.
- Dev-цель отката миграций обязана передавать `-steps 1`: при `steps == 0` откатываются все миграции, а dev-БД общая. Цель без флага и расходящийся с кодом текст справки пришли из шаблона — в сервисах их не правь.
- Имя compose-проекта у всех сервисов upl одинаковое - `compose` (выводится из каталога `deployments/compose`),
  а `container_name` и порты в `docker-compose.yml` захардкожены (`db`, `redis`, 5432, 6379).
  Поэтому `make dev-up` из одного сервиса пересоздаёт контейнер `db` чужого стека под своим именем.
  Россыпь отдельных compose-стеков сервисов и `make dev-up` не используй:
  инфраструктуру поднимает общий блок `upl-infra.sh infra up`
  (см. «Локальная инфраструктура и сквозной прогон через gateway»), экземпляры сервисов - `upl-infra.sh svc up`.

## Интеграционные тесты

- Перед локальным прогоном интеграционных тестов автоматически накатывай все ожидающие миграции на выбранную локальную БД командой `CONFIG_PATH=<абсолютный путь к .env> go run ./cmd/migrate -direction up`, предварительно подтвердив, что конфиг и контейнер относятся к локальному стенду текущего сервиса. После команды проверь, что `schema_migrations.version` равна максимальному номеру доступной миграции и `dirty=false`. Автоматический откат не выполняй; `migrate down` запускай только по явной команде пользователя.
- Подключение к БД читай так же, как приложение — из файла `CONFIG_PATH`; при пустой конфигурации используй `t.Skip`, отдельную переменную окружения для тестов не заводи. Запускай `make test-integration` с абсолютным `CONFIG_PATH`: рабочая директория прогона — каталог пакета, поэтому относительный путь не находится и тест пропускается. Тесты идут против dev-БД: изолируй данные случайными UUID, фильтруй ассерты по своему ключу и очищай данные в `t.Cleanup`.
