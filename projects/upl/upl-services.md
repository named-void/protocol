# UPL-сервисы (шаблон templ-service)

> ## ⚠️ Задача затрагивает несколько сервисов
>
> Перечисли до начала работы все сервисы, которых касается задача. Типичный случай: методы в `user-service` + права `permission`/`role_permission` в `auth-service`; выкат — сначала auth-service, иначе метод отвечает 403 всем, включая `super_admin`. Перечисление не означает начало правки: порядок входа в чужой репозиторий задаёт свод (`instructions/AGENTS.md`).
>
> Финальные проверки прогоняй по каждому сервису отдельно: забытый сервис уедет в MR неполным. Ветку, `base`, `candidate` и приёмку фиксируй в `state.md` отдельно для каждого репозитория. После обновления базы повтори прогон миграций во всех сервисах, где они есть — параллельная ветка занимает номер (`profiles/postgresql.md`).

## Bug-разбор: причинность и профилактика

- Для issue типа Bug в конце Implement добавляй в `notes.md` текущей итерации реализации секцию `Bug-Causal-Analysis` с отдельной записью по каждому дефекту из Issue: `Первопричина`, `Пропуск исходной задачей` и `Профилактика`. Раздел должен быть завершён до Accept.
- Передавай завершённый раздел в checker вместе с diff; checker проверяет его и не формирует causal-разбор заново.

## Обратная связь ревью

- Сразу после решения, что техническое замечание из discussions требует доработки, и до изменения кода или продолжения ревью проверь, отражена ли его общая причина или нарушенное требование в разделе «Обязательные правила Implement, Accept и ревью MR». Если правила нет, первым изменяющим действием добавь в этот раздел обобщённый проверяемый инвариант без координат, IID и текста конкретного комментария. Не дублируй существующее правило и не переноси замечания, которые отклонены, относятся только к требованиям конкретной задачи или не подтверждены текущим кодом и применимыми техническими правилами.
- Перед записью сверь Git-статус репозитория-владельца этого профиля и не затрагивай чужие изменения. Проверяемый checkout MR остаётся read-only; task checkout в маршруте protocol меняй только после актуализации правила.

## Обязательные правила Implement, Accept и ревью MR

Этот раздел имеет максимальный приоритет среди проектных правил Implement, Accept и ревью MR и заменяет противоречащие ему правила шаблона до их обновления. Каждый пункт обязателен, когда diff затрагивает соответствующий сценарий. Подтверждай достижимое нарушение кодом или контрактом. Если пункт противоречит актуальной постановке или спецификации, остановись и явно сообщи конфликт. При Define правила этого раздела не применяй; исключение — его пополнение по разделу «Обратная связь ревью».

### Данные и конкурентность

- Если `OFFSET` выходит за последнюю строку, возвращай пустой результат с `total=0`: это осознанное упрощение, потому что рабочий клиент не запрашивает страницы за пределами известного количества. Не добавляй отдельный count или CTE только для сохранения `total` в этом сценарии.
- В многострочном `SELECT`, который сканируется позиционно в составную модель, задавай явный `AS`-алиас каждому полю проекции; алиасы пиши в `snake_case` по полям модели и держи в том же порядке, что аргументы `Scan`.

### Авторизация и сессии

- Новый HTTP-метод проверяй вместе с `permission` и `role_permission` в auth-service; отсутствие права в fail-closed схеме блокирует метод для всех ролей.
- Regex-права сопоставляют путь целиком, компилируются безопасно и не паникуют на невалидном шаблоне из БД; не компилируй один шаблон заново для каждого запроса или права.
- CSRF/XSRF-токен генерируй криптографически непредсказуемо для новой сессии; детерминированное значение от user ID не переживает переавторизацию безопасно.
- Logout и refresh инвалидируют все токены, которые позволяют восстановить закрытую сессию; ротация удаляет старый refresh token, а выбор токена однозначно учитывает обычную и impersonated-сессию.
- Если разрешены несколько сессий пользователя, ключи cache и удаление выбирают конкретную сессию детерминированно; операция не должна удалять случайную сессию.
- Поиск пользователя по нескольким альтернативным identity выполняй с семантикой OR или последовательным fallback, если контракт не требует одновременного совпадения; AND-поиск не должен создавать дубль существующего пользователя.
- После обновления identity или прав проверяй и выдавай токен по актуальным данным, а не авторизуй новый токен значениями старой сессии.

## Границы правок

- Проект-шаблон целевой структуры — `upl/templates/templ-service`; по умолчанию инструкции наивысшего проектного приоритета находятся во всех файлах `upl/templates/templ-service/policy`. Загрузи весь этот каталог до начала работы. На Implement и Accept раздел «Обязательные правила Implement, Accept и ревью MR» имеет более высокий проектный приоритет и заменяет противоречащие ему правила шаблона. Сам шаблон только для чтения: не вноси в него правки без явной команды.
- Перед первым изменением в Implement перечитай раздел «Обязательные правила Implement, Accept и ревью MR» и попунктно примени относящиеся к задаче правила. Проверь этот набор первым; он имеет максимальный приоритет среди проектных правил реализации, включая временный приоритет над противоречащими policy шаблона до их обновления.
- Дефект, пришедший в сервисы из шаблона, не правь ни в одном сервисе: он воспроизводится в каждом новом сервисе, а копии расходятся. Оповести человека о необходимости правки шаблона и остановись. Наличие дефекта проверяй только в локально существующих сервисах и только на ветке `develop`, read-only поиском по тексту, без запуска тулчейна и бинарников сервиса. Сервиса нет локально — он вне объёма проверки.
- Ветку для правки кода сервиса заводи только с именем, заданным маршрутом задачи, порядком работы по записи бэклога или существующим MR; имя сам не выбирай — не заданное, его называет человек. Ветку и ключ задачи, в которые вошла правка, назови человеку в сессии рядом с QA-комментарием — в шаблон комментария их не вставляй.
- Название коммита начинай с ключа задачи из имени текущей ветки без префикса типа; одна строка не длиннее 100 символов, на русском, латиницей только идентификаторы кода, API/CLI и названия технологий.
- Факт о поведении CI сверяй с включаемым шаблоном (`.gitlab-ci.yml` сервиса → проект `getblogger/devops/gitlab-templates`), а не по составу репозитория: состав git о том, что делает job, ничего не говорит.
- Требования по методам живут на контрактных страницах Confluence, корни дискавери — `spec_roots` проектного слоя. Документации в сервисном репозитории нет: пункт «обновить документацию в репозитории» в чек-лист не вноси, finding «doc не обновлён» по её отсутствию не поднимай.

## Финальные проверки

- Финальные проверки проекта выполняет соседний с этим профилем `final-checks.sh`; разреши его путь относительно каталога загруженного профиля и запускай из сервисного репозитория. Корень без `go.mod` скрипт отвергает блокером 99. Прогон нужен только при изменениях Go-кода, миграций или сборочных файлов; дифф из одних текстов прогона не требует.
- В конце Implement до commit выполни `final-checks.sh prepare`. После созданных им изменений обнови task-ветку по protocol, повтори проверки и включи принятый diff в commit. На чистом `candidate` выполни `CANDIDATE_REF=<full-sha> final-checks.sh verify`: режим проверяет SHA в disposable worktree и не меняет target. Для обязательных evidence-логов зафиксируй путь и SHA-256 в `state.md`. При findings исправь результат до Accept.
- Название коммита и комментарий для QA предлагай, только когда каждая находка, включая Low, исправлена или явно отклонена пользователем с обоснованием. Форма комментария — соседний с этим профилем `qa-comment.md`; следуй ему дословно и сверь с ним готовый текст.
- На Accept перечитай раздел «Обязательные правила Implement, Accept и ревью MR», попунктно сопоставь применимые правила с `base..candidate` и передай этот профиль `checker`. Набор имеет максимальный приоритет среди проектных критериев приёмки: проверь его первым; при любом подтверждённом нарушении, включая Low, checker рекомендует `revision-required`, а вызывающая сторона сохраняет finding блокирующим и не принимает результат. Конфликт с явным требованием или актуальной спецификацией блокирует приёмку до явного разрешения.
- Сигналы скрипта триажь против диффа. Сигнал вне диффа — включая репортящиеся отдельно от `make pre-commit` — исправляй на месте в том же worktree, помечай отдельно («lint-правки вне scope задачи», файлы и находки) и вноси в бэклог, а не откладывай дефектом базовой ветки. Изменения, вносимые тулчейном в pre-commit, **принимай в коммит, не откатывай**.
- Миграции скрипт гоняет на временной БД в контейнере стенда сервиса; глубину откатов задаёт `MIGRATION_DOWN_STEPS`. Стенд не поднят — прогони против любого поднятого postgres-контейнера (`DB_CONTAINER=<имя>`), временная БД чужие данные не трогает.
- Отказ сборки с `cannot find module providing package .../api/docs` в свежем worktree — след generated-артефактов из `.gitignore`. Режим `verify` переносит `api/docs` из target и проверяет неизменность; дополнительные относительные пути передай через `FINAL_CHECKS_VERIFY_SEED_PATHS`. Для каждого обязательного generated-файла вне Git зафиксируй путь и SHA-256 в `state.md`.
- Активный `go version` обязан совпадать с directive `go` в `go.mod`. `panic: file requires newer Go version` от golangci-lint — несовместимость тулчейна, а не finding по коду: `go build` и `go test` при этом проходят.

## Тулчейн станции

- Утверждённая версия Go — 1.25.\*. Go ≥ 1.26 в `PATH` держать нельзя:
  golangci-lint падает с `panic: file requires newer Go version`. Активный Go —
  `/usr/local/go`; найденный в `PATH` go ≥ 1.26 удаляй.
- `PATH` инструментов прогона: `/usr/local/go/bin`, `$HOME/go/bin`,
  `/opt/homebrew/bin` (go, затем mockery и goimports, затем golangci-lint).
  `$HOME/go/bin` в `PATH` по умолчанию нет, поэтому `go generate` вызывай с
  явным `PATH` или целью `make generate-mocks`.

## Локальный стенд и конфиг

- Проверки, способные создать, изменить или удалить данные, выполняй только на локальной инфраструктуре задачи. На удалённых стендах такие проверки запрещены. На удалённых стендах выполняй только read-only запросы.
- Локальный флоу двухвариантный: инфраструктура в compose плюс приложение на хосте, либо всё в compose. Адреса и порты стенда обязаны работать в обоих сценариях: один и тот же адрес внешней системы видят и браузер с хоста, и процесс внутри сети compose.
- Конфиг читается из файла `CONFIG_PATH` с приоритетом над переменными окружения: для прогона против другой БД правь временную копию `.env`, переопределение `DB_NAME` через env не сработает. Копия обязана оканчиваться на `.env` — парсер выбирается по расширению, файл без него роняет загрузку конфига. Изолированную БД удаляй `DROP DATABASE ... WITH (FORCE)`.
- Тег `env-default` применяется только к отсутствующей переменной, а compose и argocd подставляют пустую строку для каждой переменной, которой нет в env-файле. Значение по умолчанию задавай в коде, а не только тегом.
- Dev-цель отката миграций обязана передавать `-steps 1`: при `steps == 0` откатываются все миграции, а dev-БД общая. Цель без флага и расходящийся с кодом текст справки пришли из шаблона — в сервисах их не правь.
- Имя compose-проекта у всех сервисов upl одинаковое — `compose` (выводится из каталога `deployments/compose`), а `container_name` и порты в `docker-compose.yml` захардкожены (`db`, `redis`, 5432, 6379). Поэтому `make dev-up` из одного сервиса пересоздаёт контейнер `db` чужого стека под своим именем. Свой стек поднимай изолированно: `docker compose -p <KEY> -f deployments/compose/docker-compose.yml -f <override с container_name и ports: !override> --env-file <копия .env> up -d db redis`, а в копии `.env` разведи `DB_PORT`, `REDIS_PORT` и `HTTP_PORT` (5432 и 6379 обычно заняты стеком auth-service, 5433 — catalog-service). Копию `.env` держи вне worktree: скрипт приёмки коммитит всё содержимое рабочего дерева. Уборку своего стека (`docker compose -p <KEY> down`) предлагай человеку.
- `make dev-up` собирает образ `migrate` из приватного registry и падает на `403 Forbidden`: для локального прогона поднимай только `db redis`, а миграции катай `CONFIG_PATH=<копия .env> go run ./cmd/migrate -direction up`.

## Авторизация и identity

- Полный запрет или разрешение метода по роли — scope Auth и API Gateway (envoy), внутри сервисов не дублируется. Требование «добавить в ролевую доступ к методу» выполняй в auth-service записями `permission`/`role_permission`; их id задавай явными UUID-литералами в миграции, чтобы последующие миграции ссылались на них на всех стендах. Правки `permission`/`role_permission` и их миграции, вытекающие из методов задачи, — выданное заранее разрешение свода на смежный сервис: входи в auth-service и делай их без отдельного спроса. Остальные правки auth-service — по спросу, как любой смежный сервис.
- Ролевую логику внутри сервиса заводи только там, где правило специфично для ролей самого сервиса и вынос его в auth-service означал бы перенос туда бизнес-знаний. Валидация назначаемых ролей и партнёров при create/update пользователя под этот запрет не подпадает — это проверка консистентности данных, а не авторизация запроса.
- Контур партнёров — доменный тип, который собирается в транспорте из `X-PUBLISHER-IDS` и идёт в use case отдельным аргументом, а не полем пользовательского фильтра: у операций над одним объектом — гейт до открытия транзакции с отказом «не найдено», у списков — предикат SQL. Покрытие сверяй грепом по вызовам `bindPublisherScope`, а не списком в профиле; регрессию ловит сквозной тест маршрутов того же пакета. Расширение контура на непокрытый метод делай отдельной задачей, а не попутно.
- Требование спецификации вида «роль X — доступен с учётом партнёрского заголовка» реализуй ячейкой «маршрут + роль» (карта `publisherContourRoutes`): контур применяется только к роли, которую таблица методов ограничивает сноской на этом маршруте, а сверку карты с реальным роутером держит тест-сторож. Устарело: отсутствие партнёрского заголовка не означает пустой контур. Роль вне ячейки заголовок не читает вовсе и полный набор сохраняет при любом его значении, включая непарсящееся, и 400 по значению заголовка ей не отдаётся. Фильтрация по одному наличию заголовка, одинаковая для всех акторов, запрещена: auth-service ставит заголовок по непустому портфелю без учёта роли и пути, поэтому она сужает выборку ролям, которым таблица даёт всех партнёров. Контур рекламодателя под запрет не подпадает — он ждёт своей таблицы методов, finding по нему не поднимай.
- Идентичность и принадлежность пользователя приходят из заголовков, проставляемых Auth через API Gateway (envoy); их отдаёт `infrastructure/middelware/v2`. Сервис доверяет им максимально — защита инфраструктурная. Заголовок, на который опирается требование задачи, хендлер обрабатывает и объявляет параметром Swagger по канону ниже, чтобы метод тестировался без Auth+envoy; опирайся на заголовок только в том правиле, которое оправдало чтение. Обязательными их не делай — ни binding-тегом и `true` в Swagger, ни ручной проверкой на непустоту с 400: envoy проставляет заголовки только для клиентских запросов, поэтому вызов от другого сервиса приходит без них. Отсутствующий заголовок трактуй как отсутствие identity, а не как ошибку валидации.
- Для `X-USER-ID`, `X-USER-ROLE` и списочных заголовков принадлежности сначала различай отсутствие поля заголовка и переданное значение. Если заголовок отсутствует, не применяй зависящие от него ограничения по пользователю, роли или связанным партнёрам. Партнёрское ограничение выбирается по роли: если поле `X-USER-ROLE` отсутствует, не читай и не проверяй списки партнёров независимо от их наличия и значения. Если списочный заголовок присутствует, но после удаления внешних пробелов пуст, считай его переданным пустым набором и там, где документация закрепляет ограничение по этому списку для маршрута и роли, применяй ограничение по пустому списку. Непустое значение разбирай по контракту заголовка. В коде, где отсутствие отличается от пустого значения, не определяй наличие через один `GetHeader`: проверяй наличие поля отдельно.

Канон объявления identity-заголовков:

```
// @Param        X-USER-ID header    string                    false "ID пользователя"
// @Param        X-USER-ROLE header  string                    false "Роль пользователя"
// @Param        X-ADVERTISER-IDS header  string               false "Принадлежность к рекламодателю"
// @Param        X-PUBLISHER-IDS header  string                false "Принадлежность к паблишеру"
```

Написание имён берётся из этого блока и из кода auth-service, а не из Confluence — там встречаются варианты, расходящиеся с кодом. Верхний регистр держи всюду, где имя написано текстом: аргумент чтения заголовка, тексты сообщений об ошибке и имя поля в 400-ответе (внешний контракт клиента). Механизм описан здесь целиком и вопросом не является: не выноси доверие к этим заголовкам в findings, остаточные риски, вопросы приёмки и QA-комментарии и не проси человека проверить на стенде, что клиентский заголовок затирается шлюзом. Механизм кажется неполным или противоречит наблюдаемому поведению — уточняй сам механизм и правь это правило, а не приписывай задаче сопроводительный вопрос.

- User-service — авторитетный источник ролей, привязок пользователей к партнёрам, переопределений прав и партнёрских сущностей. Auth-service опрашивает его на **каждом** `/validate`, поэтому правка этих таблиц, их семантики или DTO внутреннего ответа меняет авторизацию всей платформы: типы между репозиториями не разделяются, переименование поля проходит все тесты user-service и ломает авторизацию на стенде — проверяй потребителя в auth-service.
- «Все роли рекла» и «все роли паблишера» в постановках означают роли с префиксом `advertiser_` и `publisher_` — без `super_admin`, `support`, `treasurer` и прочих ролей вне префикса.

## Архитектура templ-service

- В `internal/repository/postgres` relation-фабрику храни рядом с целевым доменом: её SQL/JSON и вложенные relation — в `<domain>_include_query.go` (например, `legalRelation` — в `legal_include_query.go`). Несколько тесно связанных relation одного доменного контекста держи в одном таком файле.
- Реестр доступных include оставляй рядом с корневым query. Общие compiler/scan helpers (`include_query.go`, `include_scan.go`) не дублируй; одну relation-фабрику переиспользуй из нескольких реестров.
- Проверки существования партнёра размещай в репозитории того же партнёрского контура, а не в unrelated repository.
- При чтении партнёров сохраняй фильтр по неудалённым; в запросе с алиасом фильтруй по алиасу.

## Реализация и тесты

- Депгард разрешает testify в тест-файлах через lax-правило; строгие слои обязаны исключать тест-файлы паттерном `!**/*_test.go` в своём `files`, иначе депгард запретит testify в их тестах.
- Версия mockery — `v2.53.6` (легаси-флаги `--name`/`--exported`; в репозитории не закреплена — `go generate` берёт бинарник из PATH). Сгенерированные моки и Swagger-артефакты помечай в `.gitattributes` атрибутами `gitlab-generated=true linguist-generated=true`, чтобы GitLab сворачивал их в MR. В шаблон эту разметку не переноси. После генерации сверь `git status` и откати моки, чей дифф не относится к изменённым интерфейсам: генератор переписывает форматирование импортов во всех моках пакета, и посторонние файлы уходят в коммит задачи.
- Тесты правил валидации веди через вход usecase, а не вызовом внутренней функции валидации: нормализация и достройка входа выше по пути делают часть состояний недостижимыми. Для каждого правила разбирай путь от входа usecase до него, чтобы подтвердить достижимость состояния. Кейсы изолируй своей сущностью на подтест, иначе отказ по нарушению уникальности читается как подтверждение проверяемого правила. Ожидания моков ставь по фактическому пути: при отбитой валидации транзакция не открывается.
- Интеграционные тесты гейтятся build-тегом `integration`, поэтому обычный прогон их не компилирует; в `.golangci.yml` держи этот тег в `run.build-tags`, иначе lint молча пропускает такие файлы. Подключение к БД читай так же, как приложение — из файла `CONFIG_PATH`, при пустой конфигурации — `t.Skip`; отдельную переменную окружения под тесты не заводи. Запуск — `make test-integration` с абсолютным `CONFIG_PATH`: прогон идёт с рабочей директорией пакета, относительный путь молча не найдётся и тест скипнется. Тесты идут против dev-БД, поэтому данные изолируй случайными UUID, ассерты фильтруй по своему ключу и чисти в `t.Cleanup`.

## Ревью MR

- MR с новым HTTP-методом ревьюй вместе с ролевой в auth-service: домен права выводится из пути метода — сегменты после `api/v1/` через дефис, идентификаторы отбрасываются, — проверка fail-closed, поэтому без записей `permission`/`role_permission` метод отвечает 403 всем ролям, включая `super_admin`. Наличие домена проверяй грепом по миграциям auth-service и поиском MR того же ключа задачи там; отсутствие — finding о неполноте задачи, а не замечание к диффу сервиса.

## HTTP binding и семантика обновления

- Query-параметры endpoint описывай одним актуальным DTO и связывай ровно один раз через `httperrors.ReportBindError(c, c.ShouldBindQuery(&request))`; тот же DTO объявляй в Swagger как `@Param request query dto.<Query>`. Типы, значения по умолчанию, диапазоны, enum, UUID, CSV и формат дат задавай тегами DTO. После binding оставляй только преобразование DTO в domain filter, построение `IncludeTree` и преобразования значений, которые нельзя выразить тегами; не разбирай отдельные поля через `GetQuery`, `Query` или `QueryArray`.
- UUID в query связывай непосредственно в `uuid.UUID`, `*uuid.UUID` или `[]uuid.UUID`; для Gin v1.12 используй `parser=encoding.TextUnmarshaler`, а для CSV-списка дополнительно `collection_format:"csv"`.
- `PUT` применяет полную замену без presence-флагов: отсутствующее необязательное поле очищает текущее значение. Для nullable-поля `PATCH` различай отсутствующее поле и явный `null` через presence-aware DTO; если контракт требует анализ исходного JSON, разбирай и кэшируй карту полей один раз на запрос.
- Восстановление источника, одиночное и массовое, атомарно снимает `deleted_at`, переводит источник в `moderation` и очищает `decline_cause`; оба пути сохраняй семантически одинаковыми.
- Внутри пакета `transport/http/v1` считай публичный HTTP-контракт контекстом по умолчанию: локальные функции пакета называй по поведению или результату без префиксов `api` и `public`, а `internal` указывай только для отдельного контракта или поведения. Реальные термины `OpenAPI` и `API Gateway` сохраняй.
