# Правила ревью UPL из принятых комментариев

Источник — обсуждения MR ниже `gitlab.obs.getblogger.ru/getblogger/upl/services`, включая незавершённый `user-service!68`; снимок на 2026-08-21. Включены замечания, принятие которых подтверждено смысловым ответом либо положительной emoji-реакцией; конкретные случаи и смысловые дубли удалены.

Каждый пункт обязателен, когда diff затрагивает соответствующий сценарий. Подтверждай достижимое нарушение кодом или контрактом. Если пункт противоречит актуальной постановке или спецификации, остановись и явно сообщи конфликт. Конфликт с другим применимым профилем разрешай только по приоритету, явно заданному вызывающим workflow; если приоритет не задан, остановись.

## Слои и зависимости

- Transport работает с интерфейсом use case, внешний client DTO не проникает в domain.
- Применение update/replace-входа к существующей domain-сущности, включая объединение, полную замену, очистку отсутствующих полей и обновление вложенных значений, выполняй методом domain; use case загружает сущность и оркестрирует сохранение, но не собирает новое доменное состояние по полям.
- Ручной разбор JSON оставляй только для различения отсутствия поля и явного `null` либо условия, которое нельзя выразить binding-тегом.
- Переиспользуй утверждённые модули `getblogger/upl/infrastructure`; не держи локальную копию config, logger, HTTP, PostgreSQL, tracing или другого общего инфраструктурного кода.

## Данные и конкурентность

- Если `OFFSET` выходит за последнюю строку, возвращай пустой результат с `total=0`: это осознанное упрощение, потому что рабочий клиент не запрашивает страницы за пределами известного количества. Не добавляй отдельный count или CTE только для сохранения `total` в этом сценарии.

## Авторизация и сессии

- Новый HTTP-метод проверяй вместе с `permission` и `role_permission` в auth-service; отсутствие права в fail-closed схеме блокирует метод для всех ролей.
- Regex-права сопоставляют путь целиком, компилируются безопасно и не паникуют на невалидном шаблоне из БД; не компилируй один шаблон заново для каждого запроса или права.
- CSRF/XSRF-токен генерируй криптографически непредсказуемо для новой сессии; детерминированное значение от user ID не переживает переавторизацию безопасно.
- Logout и refresh инвалидируют все токены, которые позволяют восстановить закрытую сессию; ротация удаляет старый refresh token, а выбор токена однозначно учитывает обычную и impersonated-сессию.
- Если разрешены несколько сессий пользователя, ключи cache и удаление выбирают конкретную сессию детерминированно; операция не должна удалять случайную сессию.
- Поиск пользователя по нескольким альтернативным identity выполняй с семантикой OR или последовательным fallback, если контракт не требует одновременного совпадения; AND-поиск не должен создавать дубль существующего пользователя.
- После обновления identity или прав проверяй и выдавай токен по актуальным данным, а не авторизуй новый токен значениями старой сессии.

## Конфигурация, сборка и сопровождение

- Логи описывают фактическую операцию и используют согласованные полные имена полей.
- Соблюдай проектный naming: таблицы и колонки БД — `snake_case`, даты-время — суффикс `_at`, даты — `_date`, имена без неочевидных сокращений и магических литералов.
