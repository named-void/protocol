# Правила ревью UPL из принятых комментариев

Источник — обсуждения MR ниже `gitlab.obs.getblogger.ru/getblogger/upl/services`, включая незавершённый `user-service!68`; снимок на 2026-08-21. Включены замечания, принятие которых подтверждено смысловым ответом либо положительной emoji-реакцией; конкретные случаи и смысловые дубли удалены.

Каждый пункт обязателен, когда diff затрагивает соответствующий сценарий. Подтверждай достижимое нарушение кодом или контрактом. Если пункт противоречит актуальной постановке или спецификации, остановись и явно сообщи конфликт. Конфликт с другим применимым профилем разрешай только по приоритету, явно заданному вызывающим workflow; если приоритет не задан, остановись.

## Поток управления и ошибки

- После записи ошибки или HTTP-ответа заверши текущий путь выполнения; success path не должен продолжаться и менять ответ или состояние.
- До разыменования указателя и обращения к полю результата обработай допустимое отсутствие значения, включая nullable-поля внешнего API и результат `nil` вместе с ошибкой.
- Различай отсутствие сущности, невалидный ввод, запрет доступа, конфликт и инфраструктурный сбой; не маскируй ошибку БД или клиента под `not found` и не возвращай успешный статус при ошибке.
- Функция, которая не получила требуемое значение из cookie, cache, БД или внешнего сервиса, возвращает явную ошибку, а не пустую строку или нулевую структуру, если пустота не является частью контракта.
- Ошибка должна описывать фактическую операцию и сохранять исходную причину; не возвращай `nil`-ошибку из негативной ветки и не используй сообщение о другой операции.
- Конструктор, инициализатор или router setup возвращает `error`, если может завершиться ожидаемым отказом; безошибочный конструктор возвращает конкретный тип без искусственной ошибки. Библиотечный слой не завершает процесс через `log.Fatal`, `os.Exit` или `panic` для ожидаемого сбоя конфигурации.
- Ресурсы закрывай на всех путях: для `rows` обязателен `Close`, для HTTP-body и потоков — завершение чтения или закрытие; ошибка чтения не должна превращаться в `200` с повреждённым ответом.

## Слои и зависимости

- Transport работает с интерфейсом use case, внешний client DTO не проникает в domain.
- Use case владеет бизнес-сценарием, порядком операций и транзакцией; repository получает подготовленные данные и выполняет простые операции хранения без скрытой бизнес-валидации, каскадной оркестрации или выбора HTTP-поведения.
- Transport вызывает один use case целевого сценария и не оркестрирует несколько use case между собой.
- В update-сценарии use case сам загружает актуальное состояние и применяет изменение; transport не выполняет предварительный `Get` и не собирает обновлённую сущность.
- Изменение бизнесовых полей, требующее проверки внутренних инвариантов сущности, держи в методах domain и применяй этот подход единообразно к связанным типам; repository может технически обогатить сущность значениями, созданными БД, например `ID` и `CreatedAt`.
- Проверки формата и присутствия входа выполняй в transport binding, доменные инварианты — в use case; одну проверку не дублируй в обоих слоях без различающегося контракта.
- Переиспользуй утверждённые модули `getblogger/upl/infrastructure`; не держи локальную копию config, logger, HTTP, PostgreSQL, tracing или другого общего инфраструктурного кода.
- Клиенты, валидаторы, скомпилированные regex и другие неизменяемые зависимости создавай при сборке приложения и переиспользуй, а не создавай на каждый запрос.
- Production-граф зависимостей собирай только из рабочих обязательных компонентов; не допускай `nil`-handler и условные ветки, добавленные только для упрощения тестов.
- Разделяй крупные handler/use case/repository по доменным областям; не складывай независимые сущности и сценарии в один общий файл или абстракцию.
- Метод чтения или изменения сущности размещай в repository этой сущности и переиспользуй существующую операцию вместо её копии в соседнем repository.
- Удаляй мёртвый код, неиспользуемые аргументы, интерфейсы, типы, обёртки и дублирующие helpers; не оставляй каркас «на потом» без отдельного согласованного сценария.
- Название функции и типа должно описывать наблюдаемое поведение, включая проверку доступа, блокировку и побочные эффекты; не скрывай дополнительное удаление, сетевой вызов или `FOR UPDATE` за нейтральным именем.

## HTTP и контракт

- Сверяй route, HTTP-метод, path/query/body-параметры, response schema и status codes между router, handler, клиентами сервиса и OpenAPI; изменение контракта считается неполным, пока потребители и спецификация расходятся.
- Swagger-аннотации должны описывать фактические параметры и ответы: path-параметры записываются как `{name}`, body описывается моделью, обязательность и допустимые коды соответствуют реализации; hardcoded host стенда не добавляй.
- Query-параметры endpoint описывай единым актуальным DTO и переиспользуй его для `ShouldBindQuery` с `httperrors.ReportBindError` и Swagger `@Param request query`; ручной разбор и отдельные `@Param` оставляй только для правил, которые нельзя выразить DTO и binding-тегами.
- Не отклоняй неизвестные поля JSON без явного требования строгого контракта: input binding должен сохранять прямую совместимость с расширенным payload.
- Формат ошибки соответствует платформенному контракту: машинный `code` стабилен и записан в `UPPER_SNAKE_CASE`, field указывает реальное входное поле, сообщение конкретизирует отсутствующий или неверный ресурс.
- Если нулевое значение поля допустимо, отличай его от отсутствующего поля указателем и валидируй присутствие; `omitempty` не должен скрывать обязательный ноль в ответе.
- Валидируй все внешние идентификаторы, enum, длины, пробельные строки, URL-схемы и специальные символы до use case; SQL `LIKE` не должен интерпретировать пользовательские `%` и `_` как шаблон без явного контракта.
- Фильтр поиска обязан требовать безопасный критерий либо иметь явное ограничение; пустой фильтр не должен возвращать произвольную первую запись или запускать неограниченную выборку.
- Заявленные pagination, sort и filter должны влиять на запрос; бизнесовый порядок статусов задавай явно, а не алфавитной сортировкой.
- При альтернативных способах авторизации отсутствие cookie не является ошибкой до проверки Bearer-пути; transport читает правильный источник — header, query, form или body — согласно контракту.

## Данные и конкурентность

- Все запросы атомарного сценария выполняй через переданную транзакцию, а не через pool; проверку и последующее изменение защищай блокировкой либо одной атомарной операцией.
- Не выполняй запросы к БД или внешнему сервису в цикле, если данные можно получить пакетом; count и page должны использовать одинаковые условия либо единый согласованный запрос.
- Инварианты данных закрепляй ограничениями БД там, где это возможно: uniqueness, foreign key и допустимая nullable-модель не должны существовать только как предварительная проверка приложения.
- Для одного поля используй одно представление отсутствия: nullable-колонке не добавляй одновременно sentinel `none` и такой же default без отдельного доменного смысла.
- Константа статуса или отсутствующего значения принадлежит своему доменному типу; не переиспользуй константу соседней сущности с совпавшим строковым значением.
- При смене типа или статуса перепроверяй все уже связанные сущности, чья валидность зависит от нового значения; проверка только создаваемой или дефолтной связи оставляет противоречивое состояние.
- Операция над сущностью проверяет принадлежность связанных объектов, а не только их существование; решение о partner scope применяется до открытия транзакции и не дублируется внутри repository.
- Cache read-modify-write и one-time значения реализуй атомарно (`SETNX`, `GETDEL` или эквивалентом); предварительный `GET` перед отдельным `SET` не защищает от параллельных запросов.
- Ограничивай конкурентность на hot path: не запускай по горутине на запрос без пула или backpressure, особенно если при сбое брокера горутина ждёт timeout и пишет в БД.

## Авторизация и сессии

- Новый HTTP-метод проверяй вместе с `permission` и `role_permission` в auth-service; отсутствие права в fail-closed схеме блокирует метод для всех ролей.
- Regex-права сопоставляют путь целиком, компилируются безопасно и не паникуют на невалидном шаблоне из БД; не компилируй один шаблон заново для каждого запроса или права.
- CSRF/XSRF-токен генерируй криптографически непредсказуемо для новой сессии; детерминированное значение от user ID не переживает переавторизацию безопасно.
- Logout и refresh инвалидируют все токены, которые позволяют восстановить закрытую сессию; ротация удаляет старый refresh token, а выбор токена однозначно учитывает обычную и impersonated-сессию.
- Если разрешены несколько сессий пользователя, ключи cache и удаление выбирают конкретную сессию детерминированно; операция не должна удалять случайную сессию.
- Поиск пользователя по нескольким альтернативным identity выполняй с семантикой OR или последовательным fallback, если контракт не требует одновременного совпадения; AND-поиск не должен создавать дубль существующего пользователя.
- После обновления identity или прав проверяй и выдавай токен по актуальным данным, а не авторизуй новый токен значениями старой сессии.

## Асинхронные сценарии и интеграции

- Запись состояния и публикация команды или события должны иметь определённый атомарный протокол, например outbox; сбой между ними не должен оставлять orphan-задачу или безвозвратно терять событие.
- Consumer коммитит offset только после устойчивого терминального состояния; для зависших `processing` нужны lease/reclaim, а ошибки `MarkDone` и `MarkFailed` не считаются успешной обработкой.
- Retry имеет ограничение, интервал и наблюдаемый итог; производительность recovery worker должна разгребать реалистичный объём быстрее его накопления.
- Временные файлы во внешнем storage получают срок жизни или гарантированное удаление; presigned URL содержит доступный клиенту hostname, а не имя контейнера внутренней сети.
- Экспорт больших наборов не полагается на два независимых прохода count+rows без snapshot: изменение данных между проходами не должно ломать лимит, полноту или порядок.
- Consumer-процесс запускает только выбранный consumer и необходимые health/metrics endpoints; он не поднимает повторно публичный API-сервер.

## Конфигурация, сборка и сопровождение

- Адреса, credentials, topics, timeouts и другие параметры окружения не хардкодь; секреты не копируй в image и не коммить в `.env`, репозиторий хранит только безопасный `.env.example`.
- Проверяй обязательную конфигурацию при старте соответствующего процесса; migrator требует только DB-настройки, consumer — только свои зависимости, а отсутствующий необязательный компонент не блокирует их запуск.
- Значение по умолчанию должно работать и при отсутствующей, и при переданной пустой env-переменной, если deployment-шаблон подставляет пустую строку.
- Dockerfile, compose, Makefile и README должны ссылаться на реальные binary paths, targets, service names и файлы; образ не содержит migrator, миграции или generated-артефакты, если их запускает отдельный job.
- Health, readiness и metrics endpoints регистрируй в каждом процессе согласно платформенному шаблону; middleware не должен затирать уже установленный trace ID и использует одинаковые типизированные context keys с logger.
- Логи описывают фактическую операцию и используют согласованные полные имена полей; один сбой не логируй повторно на соседних слоях без нового диагностического контекста. Каждый слой логирует только относящийся к его ответственности факт, а достаточный контекст входа добавляется без секретов и персональных данных.
- Соблюдай проектный naming: таблицы и колонки БД — `snake_case`, даты-время — суффикс `_at`, даты — `_date`, имена без неочевидных сокращений и магических литералов.
- Интеграционные тесты отделяй build-тегом `integration`, unit-тесты пиши на `testify` с generated mockery mocks; formatter, generator и линтер запускай через закреплённый проектом toolchain.
- README и локальная документация описывают реальный способ запуска и архитектуру процесса; generated OpenAPI обновляй или исключай из Git строго по действующей конвенции конкретного сервиса.
